# Contract: Connector manifest `connector/v1`

The structure is defined by `schemas/connector-v1.schema.json`; `connectors/paystack/manifest.yaml` is the reference example. `engine/connector.ValidateManifest` enforces the schema plus these registration rules:

1. Every write action has a `class` (schema-enforced; there is no default).
2. `idempotent_write` actions declare `idempotency`; `reconcilable_write` actions declare `reconcile`; `read` actions declare neither `idempotency` nor `compensate`.
3. `reconcile` names a `read` action in the same manifest. `compensate`, when not null, names a write action in the same manifest.
4. The idempotency encoding fits the provider: `prefix` plus `length` encoded characters must fall within `limits.min_length`/`max_length`, and every character the encoding and prefix can produce must be in `limits.charset` (see [idempotency.md](idempotency.md)). The encoded hash must carry at least 128 bits.
5. `auth.test.action` names a `read` action.
6. Every `pii` field names a property of the action's input schema, or a place in its output as `output.<key>[.<key>|.*]...` (`*` for every array element) that the output schema describes. Input fields are sealed when the step is scheduled; output places when its result is written, whether or not a detector recognises the value (names, dates of birth and addresses usually are not recognised).
7. Webhook triggers declare `verify`. Schemes: `hmac_sha256`, `hmac_sha512` and `hmac_sha1` over the raw body (`encoding` hex by default, with an optional `sha256=` prefix; or `base64`, or `base64_of_hex`; `key_derivation: sha256_hex` keys the MAC with the hex SHA-256 of the secret instead of the secret), `header_secret` (the header carries the shared secret itself, compared in constant time), `hmac_sha256_timestamped` over `<timestamp>.<raw body>` with the timestamp in `timestamp_header` and deliveries outside `tolerance` (default 5m) refused, `bearer`, `basic`, `none`. `query_secret` compares a URL parameter (`query`) with the secret, for providers that sign nothing (the callback URL is registered with the token; the parameter never reaches expressions or runs); `basic` expects HTTP Basic credentials equal to the secret `user:password`; `connector` hands the delivery to the connector's own verifier for the trigger (`Connector.Verifiers`), for signatures no scheme describes, such as OPay's HMAC-SHA3-512 over fields inside the body; a trigger with no verifier refuses everything. `slack_v0` signs `v0:<timestamp>:<raw body>` with HMAC-SHA256, the header carrying `v0=<hex>`, with the same timestamp rules. A trigger may declare a `handshake` for the provider's endpoint check: `{method: GET, token_query, secret_field, respond}` answers a GET whose `token_query` parameter equals the connection's `secret_field` with `respond` (an expression over `query`) as text, as Meta does with `hub.challenge`; `{method: POST, when, respond}` answers a verified delivery for which `when` holds with `respond` instead of delivering it, as Slack does with `url_verification`. Form-encoded deliveries (`application/x-www-form-urlencoded`) reach expressions as `body.<field>`; trigger expressions may call `parseJSON(string)` to read JSON carried in such a field (Slack's interaction `payload`). A provider that batches events in one delivery declares `split`, a list expression: each element is delivered as its own event, and `event_type`, `dedup` and `correlation` see it as `item` (WhatsApp batches up to 1,000). `ack` (`status`, `body`, `content_type`) replaces the default 202 JSON answer to an accepted delivery, for providers that expect a particular reply (Remita: `Ok`).
8. Semver: a workflow pins the major version; minor and patch versions must not remove actions, inputs, or output fields, or change an action's class.
