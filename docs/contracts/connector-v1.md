# Contract: Connector manifest `connector/v1`

The structure is defined by `schemas/connector-v1.schema.json`; `connectors/paystack/manifest.yaml` is the reference example. `engine/connector.ValidateManifest` enforces the schema plus these registration rules:

1. Every write action has a `class` (schema-enforced; there is no default).
2. `idempotent_write` actions declare `idempotency`; `reconcilable_write` actions declare `reconcile`; `read` actions declare neither `idempotency` nor `compensate`.
3. `reconcile` names a `read` action in the same manifest. `compensate`, when not null, names a write action in the same manifest.
4. The idempotency encoding fits the provider: `prefix` plus `length` encoded characters must fall within `limits.min_length`/`max_length`, and every character the encoding and prefix can produce must be in `limits.charset` (see [idempotency.md](idempotency.md)). The encoded hash must carry at least 128 bits.
5. `auth.test.action` names a `read` action.
6. Every `pii` field names a place in the action's input as `<key>[.<key>|.*]...` (optionally prefixed `input.`; `transfers.*.account_name` for a field of every element), or a place in its output as `output.<key>[.<key>|.*]...`, that the input or output schema describes. A place holding a list of values (`to` with several addresses) seals each value; objects keep their shape, so name their fields. Input fields are sealed when the step is scheduled; output places when its result is written, whether or not a detector recognises the value (names, dates of birth and addresses usually are not recognised).
7. Webhook triggers declare `verify`. Schemes: `hmac_sha256`, `hmac_sha512` and `hmac_sha1` over the raw body (`encoding` hex by default, with an optional `sha256=` prefix; or `base64`, or `base64_of_hex`; `key_derivation: sha256_hex` keys the MAC with the hex SHA-256 of the secret instead of the secret), `header_secret` (the header carries the shared secret itself, compared in constant time), `hmac_sha256_timestamped` over `<timestamp>.<raw body>` with the timestamp in `timestamp_header` and deliveries outside `tolerance` (default 5m) refused (or, with `signature_format: t_v1`, timestamp and signatures in one header as `t=<unix>,v1=<hex>[,v1=<hex>...]`, any `v1` value matching, so a provider may sign with its old and new secret while it rotates: PGDock), `bearer`, `basic`, `none`. `query_secret` compares a URL parameter (`query`) with the secret, for providers that sign nothing (the callback URL is registered with the token; the parameter never reaches expressions or runs); `path_secret` is the same for providers whose callback URLs may not carry a query string (MTN MoMo): the delivery comes to the path form `/hooks/{tenant}/connectors/{connector}/{trigger}/{env}/{connection}/{token}`, whose last segment must equal the secret (the path form is refused for any other scheme); `basic` expects HTTP Basic credentials equal to the secret `user:password`; `connector` hands the delivery to the connector's own verifier for the trigger (`Connector.Verifiers`), for signatures no scheme describes, such as OPay's HMAC-SHA3-512 over fields inside the body; a trigger with no verifier refuses everything. `slack_v0` signs `v0:<timestamp>:<raw body>` with HMAC-SHA256, the header carrying `v0=<hex>`, with the same timestamp rules. A trigger may declare a `handshake` for the provider's endpoint check: `{method: GET, token_query, secret_field, respond}` answers a GET whose `token_query` parameter equals the connection's `secret_field` with `respond` (an expression over `query`) as text, as Meta does with `hub.challenge`; `{method: POST, when, respond}` answers a verified delivery for which `when` holds with `respond` instead of delivering it, as Slack does with `url_verification`. Connector events are accepted as POST or PUT (MTN MoMo calls back with either). Form-encoded deliveries (`application/x-www-form-urlencoded`) reach expressions as `body.<field>`; trigger expressions may call `parseJSON(string)` to read JSON carried in such a field (Slack's interaction `payload`). A provider that batches events in one delivery declares `split`, a list expression: each element is delivered as its own event, and `event_type`, `dedup` and `correlation` see it as `item` (WhatsApp batches up to 1,000). `ack` (`status`, `body`, `content_type`) replaces the default 202 JSON answer to an accepted delivery, for providers that expect a particular reply (Remita: `Ok`).
8. **Remote registration** ([decision 0021](../decisions/0021-remote-trigger-registration.md)). A webhook trigger may declare `registration: remote` (default `manual`): Taskiem then creates the provider's subscription itself, and the connector must supply a `Registrar` for the trigger (`Connector.Registrars`; a registrar for a trigger not declared remote, or a remote trigger without one, refuses registration). Its lifecycle:
   - **Deploy records intent.** Deploying a version whose trigger is remote (publish, promote, Git sync) declares the subscription in the deploying transaction; nothing is sent from it. A redeploy keeps the subscription and marks it to be applied again; a version without the trigger, another connector or connection, or `DELETE /v1/workflows/{wf}/deployments/{env}` marks it to be removed.
   - **A reconciler applies it** (the scheduler, and the API right after a publish or undeploy): `Create` with the subscription's name, Taskiem's ingest URL, the workflow's events and options; `Update` on a redeploy (which also repairs: resumes, reinstalls); `Get` every 10 minutes for its health (`healthy`, `failing`, `paused`, `broken`, or `missing` when `Get` answers `ErrNotFound`); `Delete` on removal (`ErrNotFound` is success). Calls are retried with backoff until they succeed; errors wrap the effects sentinels as action errors do.
   - **Names make it crash-safe.** The provider-side name is `taskiem-<subscription id>` and must be stored by the provider so `Find` can return it. A subscription whose provider id was never recorded is looked up by name before one is created (and adopted, with `RotateSecret`, since its secret was never kept) or before it is forgotten (and deleted). Taskiem forgets a subscription only once the provider no longer has it.
   - **Secrets.** The secret `Create` or `RotateSecret` returns is kept in the vault as a platform secret (environment `_remote`), read once per delivery for verification (recorded), and deleted with the subscription. `verify.secret_field` is refused on a remote trigger, and so are schemes that cannot carry a provider-issued secret (`none`, `basic`, `query_secret`, `path_secret`, `connector`).
   - **Deliveries** come to `/hooks/{tenant}/connectors/{connector}/{trigger}?env=&connection=&subscription=`: verified with the subscription's secret, starting only the workflow that owns it; a delivery for a subscription being removed gets 410 so the provider stops retrying it.
   - **Status and repair.** A subscription's health (`ok`, `pending`, `failed`, `failing`, `paused`, `broken`, `missing`, `removing`) is shown on the workflow's triggers, in the publish answer, and summed up on the connection. A health check never repairs; publishing again, even the same version, re-applies every live subscription of the workflow.

   Any trigger may declare `options`, the JSON Schema of the workflow trigger's `config.options` (checked at publish; a trigger without it takes no options), and `test_event`, an expression marking a delivery as the provider's test: it is verified and acknowledged (`"test": true`), recorded on a remote subscription, and starts only workflows that list its event by name. A connector may supply an enricher for a trigger (`Connector.Enrichers`) that completes a verified event before its runs start, given the trigger's options and, on demand, the connection; an error refuses the delivery (503) so the provider sends it again.
9. **Egress.** `egress_hosts` (default: the `base_url` host) lists what the connector may reach; `${connection.<field>}` stands for a connection field, or the host of a URL in it (a database host, a self-hosted provider's server URL), and an empty field adds nothing.
10. **Retry-After.** An action error that carries the provider's `Retry-After` (`RetryAfterDelay()`, as `HTTPError` from `DoJSON` does for 429 and 503) makes the next attempt wait at least that long, up to an hour.
11. Semver: a workflow pins the major version; minor and patch versions must not remove actions, inputs, or output fields, or change an action's class.
12. Ids by origin: built-in connectors have plain ids (`paystack`); a tenant's own WebAssembly connectors start with `x_`; catalogue connectors are `p_<publisher>_<name>`, in a verified publisher's namespace (at most 63 characters, as workflows reference them). The registry refuses to register `x_` and `p_` ids as built-ins. Catalogue connectors also pass the strict lint in `engine/catalogue` ([connector SDK](../connector-sdk.md#2-write-the-manifest)).
