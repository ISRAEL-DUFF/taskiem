# Contract: Workflow Definition `wd/v1`

The structure is defined by `schemas/wd-v1.schema.json`. This document adds the semantic rules a JSON Schema cannot express. `engine/wd.Validate` enforces both.

## Structure in brief

- Top level: `schema`, `id`, `version`, `name`, `trigger`, `steps`, optional `description`, `inputs`, `types`, `settings`. Canvas layout is **not** part of the WD (spec 3.5).
- A **scope** is a list of steps: the top-level `steps`, or the `steps` of a branch path, branch default, parallel branch, foreach body, or `on_error` handler.
- `connector` steps put `connector`, `action`, `input`, `effect`, and `compensate` at the step level. Every other type keeps its settings in `config`; `code`, `container`, `subflow`, and `ai` also take `input`, and `http` and `container` also take `effect`.

## Semantic rules

1. **Unique ids.** Step ids are unique across the whole WD, nested scopes included. Branch path and parallel branch names are unique within their step.
2. **`needs` stay in scope.** A step may only `need` steps in its own scope. A nested step implicitly runs after its parent starts; it does not list the parent.
3. **No cycles.** `needs` within each scope form a DAG.
4. **Ready rule.** A step is ready when every step it needs has completed or been skipped. If its `when` is false, or any needed step was skipped, it is **skipped**. A skipped step has no output.
5. **Expression references.** `steps.<id>` may reference a step that is a transitive `need` of the current step, or of one of its enclosing control steps. Referencing a step that may not have run yet is a validation error.
6. **Foreach scope.** Inside a `foreach` body, `item` and `index` are in scope, and `steps.<id>` for a body step refers to the current iteration. Outside, `steps.<foreach_id>.output` is the list of per-iteration outputs, in item order, each an object keyed by body step id.
7. **Branch output.** `steps.<branch_id>.output` is `{ "path": "<name or default>", "steps": { <id>: output } }`. Paths are tested in order; the first true `when` wins.
8. **Parallel output.** `{ "<branch name>": { <id>: output } }`. With `join: any`, the first branch to finish wins, the output holds only that branch, and the others are cancelled (and compensated if they committed effects).
9. **Writes must be classified.** `http` steps with `POST`, `PUT`, `PATCH`, or `DELETE` must declare `class` other than `read` (schema-enforced). A `container` step's `class` is `read`, `idempotent_write` or `unsafe_write` (the default when absent). `effect` is only meaningful on writes.
10. **Expression roots.** `trigger`, `steps`, `run`, `env`, `secrets`, and inside a foreach `item` and `index`. `secrets` may appear only in `input`, `config.headers`, `config.url`, `config.query`, and `config.body` of the step that uses them, never in `when`, `subject`, `transform` output, or `effect`, so a secret can never be copied into history. An expression that reads `secrets` may read nothing else (`='Bearer ' + secrets.token` is fine; `=secrets.base + trigger.body.path` is not): decide resolves every other expression and leaves secret-only ones for the worker, so secret values meet run data only inside the provider call.
11. **Limits.** At most 500 steps per scope; foreach `max_items` defaults to 10,000; `settings.timeout` may not exceed the plan maximum (spec 9.4).

12. **Container steps.** `config.image` names its registry and is pinned by digest (`registry.example.com/team/tool@sha256:<64 hex>`); a tag is refused, with or without a digest. `command` is required (1–64 strings). `network` is `none` (default) or `egress`; `hosts` is required with `egress` and refused otherwise. `limits` may not exceed the platform maxima: `cpu` 4 cores (at least `100m`), `memory_mb` 4096, `timeout` 30m, `output_bytes` 1 MiB. `secrets` names match `^[A-Za-z_][A-Za-z0-9_]{0,127}$`. See [container steps](../container-steps.md).

Rules 1–5, 9, 10 and 12 are enforced by `engine/wd.Validate`. Rules 6–8 are runtime semantics implemented by `engine/decide`. Rule 11's plan maximum is enforced at publish time once plans exist (Phase 4).

## Runtime semantics (engine/decide)

- **Step instances.** Events name step instances: the step id, prefixed inside a `foreach` by each enclosing iteration (`pay_all[3].pay_employee`, `outer[1].inner[2].x`). Branch and `on_error` steps keep their plain ids.
- **Skipping.** A step whose `when` is false is skipped. A step whose need was skipped, or failed and was handled by `on_error`, is skipped too.
- **Failure.** A step fails when its retries are exhausted, its error is fatal, or an expression it evaluates fails. Its scope then starts nothing new and waits for in-flight steps. With `on_error`, the step's on_error flow runs (with `steps.<id>.error` in scope) and the step counts as handled: its dependents are skipped and the run carries on. A handled step's on_error outputs take its place in the enclosing scope's results, so a `foreach` iteration whose payment failed reports its on_error record. Without it, the failure propagates to the enclosing control step, and at top level the run compensates (reverse completion order) and fails.
- **Default retry policy.** Connector, http and container steps without `retry` get `{max: 3, backoff: exponential, initial: 2s, max_delay: 5m}`; code steps get no retries. Jitter (up to 20%) is derived from the run, step instance, and attempt, so replays agree.
- **Parallel.** Branches start together, at most `max_concurrency` at a time (default: all), in definition order. Branch steps keep their plain ids, as in a `branch`. With `join: all` (the default) the step completes when every branch has; once a branch fails, no branch starts anything new, steps already in flight settle, and the step fails. With `join: any` the first branch to complete wins (definition order breaks a tie within one decision) and is recorded in a second `StepStarted` (`{winner}`), so replays agree. Every losing step that has begun and not finished gets a `StepCancelled` event: its timers, signal waits, open approval, and any task no worker holds are removed. A worker holding a cancelled task drops it unless a write was already under way (its `EffectIntent` recorded, checked under the run lock); the parallel step waits for such writes to settle. Then the losers' completed steps that declare `compensate` are compensated, newest first, and the parallel step completes. It fails only when every branch has failed.
- **Approvals.** With `role`/`count`, that many distinct people holding the role approve (maker-checker applies). With `policy`, the policy version active when the run started (snapshotted into `RunStarted`) routes the approval: the first rule matching the `subject` sets the levels, step-up and constraints, recorded in `ApprovalRequested`; the policy's `timeout`/`on_timeout` apply when the step sets none. No active version, or no matching rule, fails the step with kind `policy`. See [governance](../governance.md).
- **Outputs.** `transform` runs inside decide; `wait` outputs `{fired_at}`; `signal` outputs the signal's payload; `approval` outputs `{decision, decided_by}` (`rejected` with `reason: timeout` by default on timeout); `branch` outputs `{path, steps}`; `foreach` outputs a list, one object per iteration keyed by body step id.
- **Container steps** run on the `container` queue, one sandbox per attempt (`engine/container`). Input is the evaluated `input` as JSON; output is the program's JSON (`null` when it writes nothing); logs are kept up to 16 KB. Failures are classified by what a retry can do: never started is `not_sent`, a non-zero exit or bad output `fatal`, a timeout, out-of-memory, lost Pod or cancellation `unknown_outcome` (an `unsafe_write` then parks). A tenant whose plan has no container minutes, or has used them, gets a `fatal` failure.
- **Not yet executable.** `subflow` and `ai` validate but fail at run time with kind `unsupported` until Phase 3.

## Connector triggers

A `connector_event` trigger's `config` is `connector` (`xenibase@1`), `trigger` (a trigger in its manifest), optional `events` (each one the trigger sends), `connection` and `options`. `options` must match the manifest trigger's `options` schema (a trigger without one takes none); it is checked when the version is published. For a trigger the manifest registers remotely (connector/v1 rule 8, [decision 0021](../decisions/0021-remote-trigger-registration.md)), `events` and `options` say what Taskiem subscribes to at the provider: Xenibase's `row_changed` takes `options.tables`, optional `columns` and `refetch_truncated`. The reserved `database_change` trigger type is not used for Xenibase ([Xenibase](../integrations/xenibase.md#trigger)).

A `capability_event` trigger ([decision 0044](../decisions/0044-rails-and-products.md)) starts on a rail's normalised payment events, whichever rail the business connected: `config.events` lists one or more of `payout.settled`, `payout.failed`, `payout.reversed`, `payment.received`, `payment.returned`, `virtual_account.credited`, `pos.sale` (a POS terminal's transaction, approved or not), `refund.pending`, `refund.processed` and `refund.failed` (a refund of a payment, correlated on its `payment_id`), and the optional `connection` limits it to one connection. The run's `trigger` is `{type: capability_event, event, fields, connector, trigger, body}`: `fields` are the event's fields in Taskiem's words (`schemas/capabilities-v1.json`), the same on every rail; `connector`, `trigger` and `body` are the rail's own delivery. A publish refuses an event no rail sends.

A `storefront` trigger's `config` is `action`: `order`, `enquiry`, `callback` or `booking`, a form on the organisation's public storefront ([storefronts](../storefronts.md)). One workflow per form and environment; the run's `trigger.body` is the submission (reference, the customer, the basket and its total, the payment, and for a booking the service and time). A booking starts a new run each time it is moved, with `trigger.body.event` `rescheduled`.

An `invoice` trigger (an addition, [invoices](../invoices.md#starting-a-workflow-when-an-invoice-is-paid)) starts the workflow on one of the business's invoices. Its `config` is `event`: `paid`, when the invoice is paid in full, or `payment`, for every payment counted towards it (paid in full or not). It starts the version deployed to prod only: `paid` once per invoice and workflow, `payment` once per payment part and workflow. The runs are written in the transaction of the payment that is counted (`engine/invoicing.CountPayment`) and started from there, with the invoice's id (`paid`) or `payment:<part id>` (`payment`) as the dedup key. The run's `trigger` is `{type: invoice, event, body}`; `body` is `id`, `number`, `status`, `amount_kobo`, `amount`, `paid_kobo`, `currency`, `customer` (`{name, phone?, email?}`), `paid_at` and `link`, the invoice's page; for `payment` also `due_kobo`, `payment` (`{id, amount_kobo, amount, how, paid_at}`) and, when a school issued one, `receipt` (`{id, number, link}`, the link being the receipt's public verification page). The customer's name, phone and email and the links are sealed at run start. Any number of workflows may have it. The `invoice.paid` signal is separate: it resumes a run waiting on an invoice and starts none.

## Forms

A `form` trigger (an addition, [decision 0037](../decisions/0037-forms.md), [forms](../spec/forms.md)) puts a hosted form in front of the workflow. Its `config` is `title`, optional `description`, `access` (`public`, the default; `link`, one-time links; or `members`, signed in to Taskiem, optionally limited to `roles`), `verify` (`phone` or `email`: a code sent there before submitting; not on a members form), `pages` (each `{title?, fields, show_if?}`; without pages there is one page with every field), `after` (`mode` `message` (the default), `redirect` with `url`, or `result`) and `once_per` (`phone`, `email` or `member`). The fields are the inputs schema, with display hints in `x-form`. `engine/wd.Validate` checks that every field is on exactly one page or hidden, that `show_if` (CEL over `answers`) compiles and reads only earlier pages, and that no field asks for a password, PIN, card details or a one-time code; BVN, NIN and account numbers need their `x-pii` category and a form that is not anonymous. The run's `trigger.body` is the answers (checked against the inputs schema) and `trigger.form` is `{submission_id, submitted_at, respondent: {kind: anonymous | verified | link | member, phone, email, member_id}, channel, consents}`.

An `email` trigger (an addition, [decision 0038](../decisions/0038-inbound-email.md), [email triggers](../email.md)) starts the workflow when mail arrives at its address, `<id>@<mail domain>`, one per workflow and environment and stable across versions. Its `config` is optional `senders` (addresses, `@domain` or `domain`; mail from anyone else is not taken, and the list trusts only a From the message proves) and `attachments` (`keep` or `ignore`, the default). The run's `trigger.body` is the message: `from` and each of `to`, `cc` and `reply_to` as `{address, name}`, `subject`, `date`, `message_id`, `text`, `latest` (without quoted earlier messages), `html`, `attachments` (kept files, `{id, name, type, size, sha256}`), `skipped` (`{name, type, size, reason}`), `forwarded_by` and `truncated`; `trigger.email` is `{address, received_at, auth: {spf, dkim, dmarc, aligned}}`. Senders, recipients, the subject, the text and the HTML are sealed as personal data at run start. Automatic replies, delivery reports and Taskiem's own mail start nothing, and the same Message-ID at the same address starts one run.

A `template` step (also an addition, [decision 0047](../decisions/0047-composable-templates.md)) uses a callable template inside the workflow: see [template steps](#template-steps).

A `callback` step and a `respond` step (also additions) let a workflow wait for another system to call back, and answer the webhook call that started the run: see [callbacks and responses](#callbacks-and-responses).

A `form` step (also an addition) asks someone for answers mid-run. Its `config` is `title`, optional `description`, `to` (exactly one of `phone` or `email`, expressions over the run, or `role`, members with that role), `via` (`sms`, `email`, in order; default both), `verify`, `schema` (the questions, an inputs schema), `prefill` (field to expression), `timeout` (default `7d`), `remind` (durations after sending, each shorter than the timeout) and `on_timeout` (`fail`, the default, or `continue`). It waits as a `signal` step does, for `form.submitted` correlated by a request id derived from the run and the step instance, so replays agree; cancelling the step or the run withdraws the request. Its output is the answers, checked against `schema`, plus `respondent` (`{kind, phone | email | member_id}`); on timeout with `on_timeout: continue` it is `{timed_out: true}`, and otherwise the step fails with kind `timeout`.

## Capability steps

Added by R2 of [rails and products](../spec/rails-and-products.md) ([decision 0044](../decisions/0044-rails-and-products.md)), as an addition. A `capability` step does one capability of [`schemas/capabilities-v1.json`](../../schemas/capabilities-v1.json) (`pay_bank`, `collect_link`, `balance`…) on whichever rail its `connection` is, so a workflow written once runs on Paystack, iswallet, Moniepoint, Flutterwave or Anchor. Its fields are `uses`, `connection` (left out: the environment's only connection whose rail can do it), `input` (the capability's input: only its fields, every required one; literals are checked against its schema at once) and `effect`, besides the common ones. Its id is at most 40 characters and has no `__`.

- **Expansion.** When a run starts, each capability step is replaced by the rail's own action step, from the rail's manifest ([connector/v1 rule 16](connector-v1.md)): the step keeps its id, name, `when`, `needs`, `retry`, `timeout`, `effect` and `on_error`; its `input` stays the capability's, and a `capability` block (`uses`, the rail's `input` and `output` mappings) tells decide to map it to the action's input and the worker to map the action's output back. A composite (Paystack pays a bank account in two calls) adds the earlier calls before it as steps `<id>__<name>`, each with the same seed and so its own key, and each with a copy of `on_error` whose steps are renamed `<step>__<name>` and read that call (`steps.<id>__<name>.error`). The action's class, idempotency, reconciliation and pii rules apply unchanged. A capability input the rail cannot honour, needs, or takes with one value only is refused before anything is sent, in plain words ("your Paystack connection cannot open a bank account number for a customer to pay into. Connect Moniepoint, which can."). A deploy to an environment whose connection cannot do the step (or where several could and none is named) is refused the same way; one where the connection is not made yet goes through, and its runs are refused until it is.
- **Pinning.** The expanded definition is kept by digest (`workflow_expansions`) and the run pins it (`runs.expansion`): history, the run view, replay and drift checks see the real provider calls, and changing the connection to another rail moves new runs only. A fork keeps its parent's. The deployment records the rails it found (`deployments.rails`).
- **Output.** `steps.<id>.output` is the capability's output on every rail; the rail's own answer is kept beside it as `provider_output`. An answer the mapping cannot read is never guessed at: a write parks for a person to check, a read fails.
- **Waits.** `await_settlement` and `await_reversal` take `payout_id` (reading one payment step's output) and a `timeout`, and use that payment's connection. `await_settlement` races signals on the rail's normalised `payout.settled`, `payout.failed` and `payout.reversed` events (delivered by ingest as `<connector>@<major>:<event>`, correlated on the payout id) against the deadline, and at the deadline looks the payout up (`get_payout`); its output is `status` (`settled`, `failed` or `unconfirmed`), with `settled_at` and `reason` when known. `await_reversal` watches for `payout.reversed` until the timeout: `status` `reversed` or `none`; on a rail that sends no reversal event (Flutterwave) it looks the payout up when the timeout ends. A payment final when it returns has nothing to wait for and is refused. `await_payment` takes `payment_id` (reading a `collect_link` or `collect_transfer` step's output) and a `timeout`: it races the rail's `payment.received` against the deadline and at the deadline looks the payment up (`get_payment`); its output is `status` (`paid`, `failed` or `unpaid`), with `amount_kobo` and `paid_at` when known.

## Template steps

Added by [decision 0047](../decisions/0047-composable-templates.md), as an addition. A `template` step uses a callable template of the [library](../templates.md#callable-templates) inside the workflow. Its fields are `template` (the template's id), `params` (its parameters, as the Start page takes them: values, never expressions, since they can change what the template needs) and `input` (its run inputs, literals or expressions over this workflow), besides the common ones. Its id is at most 14 characters and has no `__`; it takes no `retry` or `timeout` (the template's steps have their own). The input must give every run input the template requires, and none it does not take.

- **Expansion.** Before capability steps are expanded, each template step is replaced by two steps: `<id>__body`, a `branch` with one path (`template`, always taken) that holds `<id>__input` (a `transform` giving the step's `input`) and the template's steps, their ids prefixed `<id>__`; and `<id>`, a `transform` that needs the body and gives the template's outputs. The body takes the step's `needs`, `when`, `description` and `on_error` (whose expressions read the body's failure, `steps.<id>__body.error`). The template's steps that need nothing need `<id>__input`; its reads of `trigger.body` read `steps.<id>__input.output`; its other trigger fields, which it reads only under `has()`, are this workflow's trigger. Each expanded step carries `origin` (`template`, the template `step` it came from, and its `id` inside the template): its output is kept under that id in its scope's results (a `foreach` iteration, a branch's `steps`, a handled step's on_error outputs), so the template's expressions read them as written. `origin` is set by expansion and refused in a definition as written. A capability step from a template keeps its `origin` when it is expanded.
- **Nesting.** A template may use a template. Expansion is recursive, at most three deep counting the workflow (so an id carries at most two prefixes), and refuses a template that uses itself. Each scope keeps the limit of 500 steps (rule 11): a template's steps are in its body's scope. Every expanded id stays a valid step id, and every capability step's at most 40 characters, because a callable template's own ids are at most 31 characters and its capability steps' at most 8. A refusal names the workflow's own template step.
- **Output.** `steps.<id>.output` is the template's outputs, by name. The template step's dependents wait for the whole template, including steps it skips.
- **Failure.** The template's own `on_error` paths run as written. A failure that escapes them fails the body; the step's `on_error`, when it has one, then runs, and the step's dependents are skipped, as for any handled step.
- **Pinning.** Each template a version uses, at any depth, is kept with the version when it is saved (`workflow_template_pins`), and the version is expanded with those copies: a library update never changes a saved version. `GET /v1/workflows/{wf}` lists, in `template_updates`, the templates the latest version pinned that the library has changed since, with their differences; the next version saved takes them. A run pins the expanded definition, as for capability steps (`workflow_expansions`, `runs.expansion`): one run, one history, and one set of exactly-once rules. Idempotency keys stay unique because the expanded ids are. The publishing checks, readiness, the AI builder's policy rules and workflow tests read the expanded definition (readiness names the template step a need comes from), and a workflow around a product (a Payrolla trigger or step) may not use a template that moves money (milestone R7 of [rails and products](../spec/rails-and-products.md)); a workflow test mocks and expects the template's steps by their expanded ids (`pay__read_list`, `pay__pay_all[0].pay__pay`).

## Callbacks and responses

Two additions let a workflow talk back and forth with a system that has no connector.

A `callback` step waits for another system to call the run back. Its `config` is optional `timeout` (default `7d`) and `on_timeout` (`fail`, the default, or `continue`, which completes the step with `{timed_out: true}`). From the start of a run, every expression can read the step's address, `run.callbacks.<id>` (`<hooks>/<tenant>/callbacks/<run>/<token>/<step instance>`); an earlier `http` or connector step sends it to the other system. A `POST` or `PUT` to that address with the right token completes the step with `{body, query, received_at}`: the request's JSON (or form fields), its query parameters, and when it came. Inside a `foreach`, `run.callbacks.<id>` names the current iteration's instance. The token is an HMAC of the step instance under a key the run gets when it starts; the key is sealed in history as personal data is, never shown to expressions, and each step's token reveals nothing of the others'. A wrong token answers 401, an unknown run 404, a run that has ended 410, and a call before the step has begun is buffered for it as a signal is. The step is a signal wait (`callback`, correlated by run and instance), so a workflow test answers it with `signals`, and a timed-out callback fails with kind `timeout`. Starting a workflow with callback steps needs `TASKIEM_HOOKS_URL` (or the public URL), where the outside reaches Taskiem.

A `respond` step answers the webhook call that started the run, which otherwise gets `202` with the run id at once. Only a workflow whose `webhook` trigger has `respond: true` may have one, and such a workflow must have one. Its `config` is `status` (200 to 599, default 200), `headers` (only `Content-Type`, `Location`, `Cache-Control` and `X-` headers are sent) and `body` (an object or list is sent as JSON, a string as text; values may be expressions). It completes at once; the caller gets the first respond step completed, with the run's id in `X-Taskiem-Run`, and the run carries on after it. A run that ends without one answers `200` (`{run_id, status}`), one that fails first `500`, and one that takes more than 30 seconds the usual `202` with the run id, so the caller can follow it. Secrets may not appear in a respond step: the answer is recorded in history and sent outside.

## USSD menus

A `ussd` trigger requires `config`, a menu (`$defs/ussdMenu`): `service_code` (`*384*123#`), `screens` (1 to 50), optional `start` (default: the first screen), `max_chars` (60 to 182, default 182) and `notify` (`{sms, connection?, completed?, failed?}`). A screen has `id`, `type` (`menu`, `input`, `confirm`, `end`) and `text`. A `menu` screen requires `options` (1 to 9: `label`, `next`, optional `value` and `when`) and may set `input`. An `input` screen requires `input` and `next`, and may set `validate` (`type`, `pattern`, `min`, `max`, `min_length`, `max_length`, `when`) and `error`. A `confirm` screen may set `confirm_label`, `cancel_label` and `done`. `engine/wd.Validate` adds these rules (paths under `/trigger/config`):

- **U1. Size.** Each screen, measured at its worst case (error line, placeholders at their longest, options or confirm lines, `0. Back`), and each `done` text fit `max_chars`. Texts and labels are printable ASCII; SMS texts are at most 160 characters.
- **U2. Links.** Every `next` names a screen; every screen is reachable from the start; at least one `confirm` screen exists; ids are unique.
- **U3. Fields per type.** A screen carries only its type's fields (no `options` on an input screen, no `next` on a confirm screen, and so on).
- **U4. Validation.** Patterns compile (RE2, matched against the whole input); `min` ≤ `max` and only with `type` `number` or `integer`; `min_length` ≤ `max_length`.
- **U5. Conditions.** `when` (on options and in `validate`) is an expression over `trigger.body` only (the inputs collected so far, with the new value in place for `validate.when`). Other roots, `secrets` among them, are refused.
- **U6. Texts.** Texts are fixed, never expressions. `{{name}}` names an input some screen collects, and `{{reference}}` appears only in `done` and the `notify` texts.
- **U7. Inputs schema.** When the inputs schema is an object with `properties` (directly or through `#/types/...`), every collected name is a property of a compatible type, and every `required` property is collected by some screen.
- **U8. One code per environment.** At publish, a service code already served by another workflow in the environment is refused.

The run started by a confirmation has `trigger.body` (the inputs), `trigger.caller.phone_number` (sealed) and `trigger.ussd` (`reference`, `service_code`, `provider`, `network`). See [USSD](../ussd.md).

## Expressions

CEL with the standard library and cel-go's strings, math, lists and optional-types extensions, plus `sum(list)`: the total of a list of numbers (an int when every element is an int, a double otherwise, 0 for an empty list; integer overflow is an error). Code written with the SDK uses it as a CEL string (`"=sum(steps.pay.output.map(r, r.amount))"`).

## Durations

`<n><unit>` repeated, units `ms`, `s`, `m`, `h`, `d`; for example `90s`, `1h30m`, `7d`.
