# A proper code editor: Monaco in the Code and JSON tabs and in code steps

Status: **Draft** 29 October 2026, for review (revised 30 October after a review against the code: §2, §4.1, §5, §7) · Builds on: [workflow builder](../workflow-builder.md) (Code and JSON tabs), [SDK](../sdk.md) (code and canvas), [code steps](../code-steps.md), [architecture §10.2](architecture.md#102-round-trip) and its library table (Monaco, MIT, "WD and code step editing"), [licence policy 0007](../decisions/0007-licence-policy.md)

## 1. Summary

The web app's three places for code are plain text areas: the Code tab (the workflow as TypeScript), the JSON tab (the wd/v1 definition) and a code step's Source box. They work, and the round trip behind them is solid, but a developer gets no colouring, no line numbers, no completion of the SDK's builders or a connector's fields, and a compile error is a line of text under the box with nothing pointing at the line it names.

This plan puts Monaco, the editor the architecture already chose, in those three places: TypeScript with the SDK's own types loaded so `paystack.` completes and a wrong field is underlined before the server is asked; compile errors and the publishing checks shown as markers on the lines they belong to; JSON against the wd/v1 schema; JavaScript, TypeScript and Python in code steps with the step's `host` typed. It is loaded only when one of those places opens, so an owner who never sees Advanced downloads none of it, and on a phone the text areas stay.

Four milestones, E1 to E4, each a PR. Nothing in the API changes except one field on the compile error.

## 3. What stays as it is

- **The round trip.** Generate, compile, apply, the merge by parent digest and the "generated code builds to exactly its definition" rule are untouched. The editor is a better box around the same two endpoints.
- **Code is technical.** The tabs stay behind Advanced and `data-technical`; no owner screen gains a word from Appendix C of [no technical steps](no-technical-steps.md).
- **Phones.** Below 768 px, or without a fine pointer, the text areas stay: Monaco on a phone is worse than a text area, and the builder's phone list is the way owners work there.
- **No CDN.** Monaco is bundled and served from the app's origin like everything else; nothing is fetched from the web at run time, which the CSP would refuse anyway.

## 4. The editor

### 4.1 Loading

- `monaco-editor` (MIT) from npm. Recent releases bring runtime dependencies (`dompurify`, under MPL-2.0 or Apache-2.0, and `marked`, MIT). E1 pins the version and runs the licence gate over the whole tree it brings in, and any dependency outside the allowed tier is an exception under 0007, or a version without it.
- Imported from `monaco-editor/esm/vs/editor/editor.api` with only the languages we use (`typescript`, `javascript`, `json`, `python`) and the features we want, not the full `monaco-editor` entry, so the chunk is as small as Monaco gets. Its workers (`editor`, `ts`, `json`) are Vite `?worker` imports, same-origin files, which satisfies `default-src 'self'` with no CSP change; `MonacoEnvironment.getWorker` hands them out.
- One component, `web/src/code/CodeEditor.tsx`, loaded with `React.lazy` from each place that uses it, so the editor's chunk (a few MB, mostly the TypeScript worker) is fetched only when a Code, JSON or code-step editor is shown, and once per session. Until it arrives the text area is shown, not a spinner, so nothing waits on it.
- Chunking: the editor and each worker are their own chunks. Vite's `chunkSizeWarningLimit` is global (`web/vite.config.ts` has 1500 already), so it stays as it is. Instead, the build's size check names the Monaco chunks as the expected large ones, and the app's own chunks keep their budget.

### 4.2 Look

- Two themes, `taskiem-light` and `taskiem-dark`, defined from the CSS variables in `styles.css` (`--code-bg`, `--text`, `--brand` and the rest) read with `getComputedStyle` at mount and again when `data-theme` changes, so no hex colour enters a component and the editor follows the theme toggle and the system setting. Token colours are a small fixed set, chosen to pass contrast in both themes.
- The app's monospace stack and 12.5 px size, line height 1.6, tab size 2, as `textarea.mono` has; minimap off; word wrap on; line numbers on; the gutter shows markers; folding on.
- The editor fills the card and grows to its content up to the viewport, as the text area does with `rows`, so the page does not scroll inside a box inside a page.

### 4.3 Accessibility

- Monaco's own screen-reader mode and its keyboard model (Tab moves focus out by default; `Ctrl+M` toggles tab trapping, which the hint says). The editor carries the same accessible name the text area has ("Workflow code", "Definition", "Source"), so tests and assistive technology find it the same way.
- The pages stay in `accessibility.spec.ts`; Monaco's known axe findings (colour contrast on a few token classes, a `role` on its hidden input) are either fixed by the theme or listed in the test's exclusions with a reason, never by excluding the page.

### 4.4 A test hook

Playwright's `fill` does not drive Monaco. The component sets, on its root element, a `taskiemEditor` property with `getValue`, `setValue` and `markers`, used only by tests (`page.evaluate`). The smoke test and the new tests use it; the component's text-area fallback needs nothing.

## 5. E1: the Code tab

- The generated code opens in Monaco as TypeScript.
- **The SDK's types as extra libs.**
  - Every file of `sdk/src` that `index.ts` reaches, plus `connectors.gen.ts`, is added to the TypeScript worker at its own name in **one** directory, `file:///node_modules/@taskiem/sdk/src/` (`index.ts`, `wd.ts`, `builder.ts`, `contract.ts`, `expr.ts`, `codegen.ts`, `connectors.gen.ts`).
  - The files' own relative `./builder.js` imports then resolve as they do on disk. Under NodeNext resolution a `.js` import finds the `.ts` file beside it, and `connectors.gen.ts` imports `./builder.js` from the same directory.
  - Two package stubs map the names the generated code imports: `node_modules/@taskiem/sdk/package.json` with `types` pointing at `src/index.ts`, and `node_modules/@taskiem/connectors/package.json` with `types` pointing at `../sdk/src/connectors.gen.ts`.
  - The files are imported into the web build as text (`?raw`, through the `@sdk/*` path the web's tsconfig already has) and added when the editor first opens.
  - A unit test resolves the generated code of every workflow in `flows/` against those virtual files with the TypeScript compiler API and expects no unresolved import.
- **Compiler options** are `flows/tsconfig.json`'s, except its `paths`, which are relative to `flows/` and are replaced by the stubs above: strict, NodeNext, `noImplicitAny` off, so `(e) => e.amount` is not an error here either.
- **What the browser checks.** Completion covers every builder, every connector action and its fields, and every workflow option. A misspelt field is underlined **by the editor's own type check, in the browser, before anything is sent**. The server never type-checks: esbuild only strips types, so a wrong field name compiles there, and the browser is the only place it is caught.
- The SDK's types in the bundle are the same source `go generate ./sdk` writes, so they cannot go stale separately; the existing `TestGeneratedHelpersAreCurrent` already fails CI when `connectors.gen.ts` is.
- **Apply to workflow** is unchanged in what it does. Compile errors that esbuild reports come back with positions: `POST /v1/code/compile` returns `422 {"error": "...", "problems": [{"line", "column", "message"}]}`.
  - The positions are parsed from esbuild's messages in `bundleWithSource`, which already has `Location.Line` and `Column`.
  - Only messages located in the user's file count: the entry stub (`entry.ts`) and the SDK's files are filtered out by `Location.File`, and an error in them stays in `error` without a line.
  - These are syntax errors and unresolved imports. Type errors never reach the server (above).
  - A runtime error (the script threw while building the definition) has no position and stays one message.
  - They are shown as error markers on their lines and in the problems strip under the editor, each a link that moves the cursor.
- Check problems (`{path, message}`) are mapped to lines by step: a path under `/steps/<n>` names the step whose `id` is at that index in the compiled definition, and the generated code names each step once, in `.step("<id>"`, `.next("<id>"`, or its container's call, so the problem is marked on that line (a warning marker, since the definition compiled) and listed. A problem with no step (workflow options, the trigger) is listed without a line.
- **Reset** returns to the generated code; `Cmd/Ctrl+S` in the editor applies when the code changed (the page's existing `Cmd+S` handler, which skips text areas, learns the editor too). The text area fallback keeps the old behaviour exactly.
- A Git-managed workflow opens read-only, with the file's path in the hint, as today.
- **Accept:** the smoke test passes through the hook; a new `web/e2e/code-editor.spec.ts` types `paystack.` and sees the actions offered, types a wrong field name and sees the editor's own type marker on that line before applying, applies code with a syntax error and sees the server's marker on its line and the strip's message, applies a definition the checks reject and sees the warning on the step's line; the page passes axe in both themes; the editor chunk is not in the network log until the Code tab opens; at 390 px the text area is shown instead.

## 6. E2: the JSON tab

- The definition in Monaco as JSON, with `schemas/wd-v1.schema.json` registered with the JSON language service (`jsonDefaults.setDiagnosticsOptions`, the schema served as a bundled asset), so a wrong key, a missing required field or a step type that does not exist is underlined with the schema's words, and keys complete. The schema's `$id` is the match; the file is the one `sdk/src/wd.ts` is tested against, so the editor cannot drift from the definition.
- The existing client-side check (`jsonProblem`, "what keeps the text from being a definition the builder can draw") stays as the strip's message when the text parses but the builder refuses it; schema findings are markers.
- Format on open (two spaces, as `flowcode.Indent` writes) and **Format** in the strip.
- **Accept:** a step with `"type": "codee"` is marked with the schema's message; a definition with a removed required field is marked; applying a valid one redraws the canvas; the smoke test's JSON path, if any, passes through the hook.

## 7. E3: code steps

- The step's Source in Monaco: TypeScript or JavaScript with a small typing of the step's world loaded as an extra lib, `step-host.d.ts` in `web/src/code/`: `host.log`, `host.secret(name)`, `host.now()` and `host.fetch(url, {method?: "GET" | "HEAD", headers?: Record<string, string>, body?: string})` returning a promise of `{status, headers, body, json(), text()}`.
  - The default export's shape is the sandbox's: `(input: Record<string, unknown>, host: Host) => unknown | Promise<unknown>`, called as `fn(input, host)` and awaited (`engine/sandbox/sandbox.go`). So an async function and the `host` parameter are both valid, as well as the global `host`.
  - `host.` completes. `host.fetch(url, {method: "POST"})` is an error with the hint's words ("send writes from an http or connector step"), which is what the sandbox enforces: it sends only `GET` and `HEAD` ([code steps](../code-steps.md)). Python gets colouring and indentation only; no language service runs in the browser for it.
- The typing is checked against the sandbox: a test in `engine/sandbox` lists the host's members from the JavaScript host object, and `web/src/code/step-host.test.ts` reads the `.d.ts` and fails when they differ, so the editor never offers what the sandbox does not have.
- The step panel's layout is unchanged: the editor sits where the text area was, 12 rows tall and growing to 24; on phones the text area stays.
- **Accept:** `host.` completes in a code step; a `POST` is underlined; a Python step opens coloured; the builder's e2e passes; `StepPanel` passes axe.

## 8. E4: polish and the gate

- **Diff before applying.** In the Code tab, **Compare** shows Monaco's diff editor between the generated code and the edit, so a developer sees what Apply will do; in the JSON tab the same against the definition as it is.
- **Go to step.** A marker's line or a `.step("id"` call is a link that opens that step's window on the Build tab (`setOpen(id)`), and the Build tab's step window gains "Show in code", which switches to the Code tab and reveals the line.
- Docs: [workflow builder](../workflow-builder.md) (the Code and JSON tabs), [sdk](../sdk.md) (code and canvas: the editor's completion), [code steps](../code-steps.md) (the host typing), [embedding](../embedding.md) if the embedded builder shows code (it does not today, so no change expected), and this page's status.
- The licence check in CI sees `monaco-editor` (MIT) and nothing else new.

## 9. Security

| Concern | Control |
| --- | --- |
| Code from the web, fetched at run time | None: Monaco, its workers and the schema are bundled and same-origin; `default-src 'self'` is unchanged and would block anything else |
| The editor runs code | It does not: the TypeScript worker type-checks and completes; the only run is the server's, in the sandbox, as today |
| The SDK's source in the bundle | It is already public in `sdk/` and the SDK package; nothing tenant-specific is in it |
| Secrets in code | Unchanged: a code step reads `host.secret(name)`; the editor adds no path for a value to be typed where it was not before |
| A large paste | The compile endpoint's 1 MiB limit stays; the editor refuses above it with a message, as the text area did implicitly by the server's answer |

## 10. Testing

- **Units** (vitest, jsdom): the error-to-marker parser, the step-to-line mapper (over the generated code of every workflow in `flows/`, so every call shape the generator prints is covered), the theme reader, the `.d.ts` against the sandbox host. Monaco itself is not loaded under jsdom; the component is tested with its text-area fallback and a mocked loader.
- **End to end** (Playwright): the four accepts above, through the test hook; the editor chunk's absence from the network log before the tab opens; 390 px shows the text area.
- **The round trip** is untouched and keeps its tests (`go test ./engine/flowcode`, `pnpm test` over `flows/`).

## 12. Risks

| Risk | What we do |
| --- | --- |
| The TypeScript worker is big (about 4 MB before compression) | Lazy, once per session, cached by the asset's hash; developers on Advanced pay it, owners never do. Measured in E1's PR, with the number in the docs |
| Monaco's bundling with Vite goes wrong (worker paths, CSS) | The `?worker` import route is the one Vite documents; the editor's CSS is imported once, and `style-src 'unsafe-inline'` already allows what it injects. E1 proves it in the production build, not only `vite dev` |
| Type loading is slow on first open | The libs are added once, after the editor is visible, and completion appears when the worker is ready; the code is editable before that |
| Monaco's accessibility findings | Fixed in the theme where they are contrast; the rest listed per rule with a reason, and the page is never excluded |
| Monaco 1.0 removed APIs we use | Pin the version; the editor is one component, so an upgrade is one file |

## 13. Out of scope

A language service for Python in the browser; CEL expression editing in step windows (a different editor, the field-text one); editing the SDK or connector manifests; running code in the browser; collaborative editing (the merge by parent digest stays the way two people work).
