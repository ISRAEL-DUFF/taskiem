# Threat model

What Taskiem protects, from whom, where the trust boundaries are, and which control holds at each one. It is written for the external penetration test (spec 14.4, gate G2), whose scope is in [pen-test-scope.md](pen-test-scope.md), and for anyone changing a boundary. The internal self-review that tested this model is in [self-review.md](self-review.md).

Keep this document current. A change that adds an entry point, a role, a store of secrets or a new way to run tenant code updates the tables below in the same pull request.

## What we protect

| Asset | Why it matters | Where it lives |
| --- | --- | --- |
| Provider credentials (bank, wallet, payments, KYC API keys; OAuth refresh tokens; database passwords) | Each one can move money or read customer identity data | `secrets` and `connections`, envelope-encrypted (AES-256-GCM data keys under a tenant key, under the KMS root key) |
| Money-moving decisions | A forged approval, a replayed webhook, a duplicated transfer or a skipped four-eyes check moves money wrongly | Run history (`run_events`), approvals, policies, idempotency keys |
| Personal data (BVN, NIN, account numbers, names, phone numbers) | NDPA obligations; identity theft | Sealed fields in run inputs and outputs (`engine/pii`), approval subjects, reports |
| Workflow definitions and policies | Whoever controls them controls what the platform does with the credentials | `workflows`, `workflow_versions`, `policies`, Git repositories |
| Audit chain | The evidence regulators and partners rely on | `audit_log` (hash chain), signed anchors on disk and sent by email |
| Tenant isolation | One tenant's data or credentials reaching another is the worst outcome for a multi-tenant platform | Row-level security on every tenant table; the tenant in the session |
| Availability of the engine | Stalled payouts and missed salary runs | Postgres, worker queues |

## Who attacks

| Actor | Starting position | Wants |
| --- | --- | --- |
| Internet attacker | Can reach the public URL, `/hooks/*`, `/git-hooks/*` and `/channels/whatsapp` | An account, webhook forgery, SSRF into the cluster, denial of service |
| Holder of a phone | Can message the platform WhatsApp number, from their own number or one they took over (a stolen or SIM-swapped phone of a bound person) | Act as the number's owner: approve, start runs, read status; forge or replay approval buttons |
| Malicious or compromised tenant member | Holds a valid session, possibly a custom role, in one tenant | More rights in the tenant, another tenant's data, raw secrets, an approval they should not give, a publish that skips four-eyes |
| Malicious tenant code | A `code` step (JavaScript, TypeScript or Python), a tenant WASM connector, or flow code compiled at publish | Escape the sandbox, read other tenants' data or secrets, reach internal addresses, exhaust the host |
| Compromised provider or identity provider | Sends webhooks, API responses, SAML assertions or OIDC tokens | Forge events or logins, inject content that is shown to people or fed into expressions |
| Compromised Git repository or Git host | Can push to a connected repository and send push hooks | Deploy a workflow without the platform's approval flow |
| Insider with infrastructure access | Database, cluster or KMS access | Read secrets, rewrite history without detection |

Out of scope for the model: a compromised KMS root key together with the database (accepted: that is the root of trust), a compromised build pipeline (covered by release signing, spec 14.3, once releases are cut), and physical attacks.

## Trust boundaries and entry points

```
 browser ──HTTPS──▶ ingress ──▶ api (8080) ──┐
 partner pages ─CORS─▶ ingress ──▶ api ──────┤   (/v1/embed: end-user tokens)
 partner servers ─────▶ ingress ──▶ api ──────┤   (/v1/partner: partner keys; headless /v1/embed)
 providers ─HTTPS─▶ ingress ──▶ edge (8081) ─┤──▶ Postgres (RLS, taskiem_app)
 Git hosts ─HTTPS─▶ ingress ──▶ edge ────────┤
 Meta (WhatsApp) ──▶ ingress ──▶ edge ────────┤   /channels/whatsapp
 Meta ◀──egress guard── api, edge, scheduler  │   Graph API sends
 IdPs ◀─redirects─ browser                   │
                       orchestrator, scheduler ┤
 providers ◀─egress guard── worker ───────────┘──▶ OpenBao transit (root key)
                              └─ sandboxes: QuickJS, CPython, tenant WASM (wazero)
```

The api role also calls the model provider (Anthropic's API, or a self-hosted model) for AI building, with redacted prompts; what comes back is only ever a proposal (B10).

| # | Boundary | Entry points | Main controls | Code |
| --- | --- | --- | --- | --- |
| B1 | Internet → API | `/v1/*`: sign-in, passkeys, SSO start and callbacks, password reset (forgot and reset), signup (off by default), and every authenticated route | Session cookies (`HttpOnly`, `Secure`, `SameSite=Lax`); cookie sessions must send the `X-Taskiem-Request` header on every non-GET request, and there is no CORS (outside the embed API, B10); per-IP sign-in rate limit; Argon2id password hashes; API keys stored hashed; permissions checked per route (`need(...)`); step-up (passkey or TOTP) for approvals; administrators held to passkeys once a public URL is set | `api/server.go`, `api/auth.go`, `api/passkeys.go`, `engine/webauthn`, `engine/totp` |
| B2 | Identity provider → API | OIDC callback, SAML ACS, SCIM | OIDC: state, nonce and PKCE; issuer, audience, expiry and signature checked. SAML: signed assertion required (gosaml2), IdP-initiated responses refused, `InResponseTo` bound to a single-use RelayState, audience, recipient and validity window checked. SCIM: per-tenant bearer token; owners never deprovisioned; JIT users only in DNS-verified domains | `api/sso.go`, `engine/oidc`, `engine/saml`, `api/scim.go` |
| B3 | Provider → edge | `/hooks/{tenant}/{path}` and connector triggers | Signature verified before parsing (HMAC, Slack v0, query secret, basic, connector-specific), compared in constant time; body size limit; deduplication; handshakes answer only the documented challenge | `engine/ingest`, `engine/connector/webhook.go` |
| B4 | Git host → edge | `/git-hooks/*` | Per-repository webhook secret; a push only triggers a sync, which reads the repository with the tenant's token and goes through the same validation, policy and four-eyes rules as publishing in the UI | `api/git.go` |
| B5 | Worker → internet | HTTP steps, connectors, alert webhooks, Slack | Egress guard: per-tenant host allow-list, private, loopback, link-local and metadata ranges refused, the vetted IP pinned for the connection, redirects re-checked | `engine/egress` |
| B6 | Tenant code → host | `code` steps, tenant WASM connectors, flow code at compile time | WebAssembly only (wazero, no host filesystem or sockets); memory, time and output limits; fetch only through the egress guard; secrets only those the step declares; a fresh instance per run | `engine/sandbox`, `engine/wasmconn`, `engine/flowcode` |
| B7 | Tenant → tenant | Every table holding tenant data | Postgres row-level security, forced, on every tenant table; the app connects as `taskiem_app` and sets the tenant per transaction; services that run across tenants (scheduler, ingest) scope each query explicitly | `engine/db/migrations`, `api.Server.tx` |
| B8 | Application → secrets | Secret reads in the worker | Envelope encryption, ciphertext bound to tenant and name; decrypted only in worker memory for the call; never in logs, events or responses (log attributes redacted) | `engine/secrets` (every decryption recorded in `secret_reads`, migration 00033), `cmd/taskiem` (`redactAttr`) |
| B10 | WhatsApp → edge, and decision tokens | `/channels/whatsapp` (Meta's webhook for the platform number); approval buttons and step-up links carrying decision tokens; `/v1/me/whatsapp` (binding) and `/v1/whatsapp/handoff/{token}` (step-up) on the API | `X-Hub-Signature-256` under the app secret before parsing; message ids claimed once; a number speaks only for the person it is bound to (by an OTP to the number plus proof of the account), with their current roles in the organisation it works in; decision tokens HMAC-signed over tenant, run, step, level, approver, decision, expiry and nonce, single use, checked against the sender's bound number, decided through the web app's approval path; step-up only in the web app; per-number rate limits; masked messages | `api/whatsapp*.go`, `engine/whatsapp`, migrations 00035–00037 ([WhatsApp](../whatsapp.md#security-model)) |
| B9 | Application → audit | Every privileged action | Append-only hash chain; heads signed and written outside the database and emailed; offline verification of exports | `engine/audit` |
| B11 | Partner → sub-tenant; end user → embed API | `/v1/partner/*` (partner API keys); `/v1/embed/{app}/*` (end-user tokens, from the partner's pages through CORS or, headless, from its servers) | Sub-tenants are tenants under RLS; no session or key holds one in scope; the partner API enters one sub-tenant per transaction through `taskiem_partner_enter` (checks `parent_id`, audits in both chains, narrows the scope); partner API only for full-tenant API keys with `partner.*`; end-user tokens opaque, hashed, at most 1 h, bound to an app and optionally an origin, permissions within a fixed ceiling and the app's current allow-list, refused on every other route; CORS only on embed routes for the app's exact origins, without credentials; definitions checked against the app's connectors at save, publish and run start; partner sees redacted outcomes only | `api/partner.go`, `api/embed.go`, `api/embedapps.go`, `engine/embed`, migrations 00045–00047, [embedding](../embedding.md) |
| B12 | Application ↔ model provider | `/v1/ai/*`, `/v1/repairs/*`; outbound calls to the model API (Anthropic, or a self-hosted model) | The model only proposes: the builder and the repair pipeline (`engine/ai/...`) hold no vault, database, principal or connector handler, and their import graph is tested to exclude them (and the shadow sandbox); prompts redacted before they leave and carry names, never secrets, credentials or variable values; repair prompts carry the run as sealed, with placeholders; every call logged (insert-only) and every proposal audited; proposals validated like human work, repairs also in a shadow run with every write mocked; saved, published or resumed only by a person, through the normal publish path; per-tenant token budgets ([AI](../ai.md#safety-model), [decision 0016](../decisions/0016-repair-and-resume.md)) | `engine/ai`, `engine/shadow`, `api/ai.go`, `api/repair.go`, migrations 00040–00041, 00050–00052 |

## Threats and responses

STRIDE per boundary. **Status** is what the code does today. "Self-review" points to a finding in [self-review.md](self-review.md).

| Boundary | Threat | Response | Status |
| --- | --- | --- | --- |
| B1 | Credential stuffing or brute force on sign-in | Per-IP burst limit on sign-in; Argon2id; passkeys for administrators | In place. A per-account limit is a follow-up |
| B1 | Account takeover through credential recovery (password reset), and user enumeration through it | Same `202` and body for every email, work done after answering; links only for active people with a password who are not held to SSO everywhere (owners keep the break-glass); token in the URL fragment (out of logs and `Referer`), 256-bit secret stored as SHA-256, single use, 30 minutes, replaced by a newer link, locked after five wrong secrets; limits per address, per email and per link; JSON only; the reset ends every session, is audited in each tenant and emailed to the person, and signs nobody in, so the passkey rule and SSO enforcement still apply. Recovery is only as strong as the person's mailbox; administrators held to passkeys are not exposed, since a password does not sign them in once they have one. Changing a password needs the current one (or a passkey or authenticator to set a first one) and ends other sessions | In place (`api/password.go`, migration 00032) |
| B1 | CSRF on state-changing routes | Required `X-Taskiem-Request` header on cookie sessions; `SameSite=Lax`; no CORS outside `/v1/embed` (B11). Sign-in and SSO callbacks bound to the browser (self-review) | In place |
| B1 | Session theft, and what a stolen session can do | `HttpOnly` and `Secure` cookies; sessions revoked on sign-out and deprovisioning; adding or removing a second factor needs an existing factor; step-up codes rate-limited (self-review) | In place |
| B1 | Privilege escalation through custom roles or API keys | Nobody grants a permission they lack; API keys cannot exceed their creator | In place |
| B1 | Approving your own request; approving without a second factor | Policies forbid the requester; step-up per decision; four-eyes on publishing and policy changes | In place |
| B2 | Forged SAML assertion (signature wrapping), replay | Signature validation by gosaml2/goxmldsig; single-use request ids; window checks | In place |
| B2 | Account takeover by linking an IdP identity to an existing account | JIT only within DNS-verified domains; SSO enforcement with an owner break-glass | In place |
| B3 | Forged or replayed webhook starting a payout | Signature before parsing; deduplication on signed material (a hash of the body when there is no key); a delivery verified in one environment reaches only that environment's runs | In place (self-review S8, S19) |
| B3 | Flooding `/hooks` (one tenant's traffic starving others, or exhausting the database) | Body size limit (per tenant, at most 10 MiB); per-tenant soft rate and hard ceiling, limiters created only for tenants that exist and bounded in memory; above the soft rate runs are recorded but queued and admitted from the database at the tenant's rate, each tenant from its own bucket; backlog cap (429 `backlog_full`); optional run quotas; workers claim round-robin across tenants under a per-tenant in-flight cap; limits set only by operators (the application role cannot write `tenant_limits`), every change audited | In place (2026-10-07, [operations](../operations.md#plan-limits)). Limiters are per edge replica, so a tenant's effective ceiling scales with replicas; admission and worker caps are global |
| B4 | A push deploying around four-eyes | Git-led publishing still passes validation and the environment's publish policy | In place |
| B5 | SSRF to cloud metadata or the cluster network | Egress guard on every outbound connection, with the IP pinned against DNS rebinding | In place. Private databases (MySQL, Postgres, SFTP inside a customer network) need a reviewed design: carried gap A4 |
| B6 | Sandbox escape | WebAssembly isolation; no host functions beyond fetch, logs and declared secrets | In place |
| B6 | Resource exhaustion by tenant code | Memory, time and output limits per instance; queue concurrency | In place |
| B7 | Cross-tenant read through a missing tenant filter | Forced RLS, so a missing `WHERE tenant_id` returns nothing rather than another tenant's rows | In place |
| B8 | Secrets in logs, errors, run history or AI prompts | Redaction of log attributes; secret values never placed in events | In place |
| B8 | A secret used without a trace, or its trace removed | Every decryption for use recorded in `secret_reads` in the decrypting transaction (purpose, run, step, attempt; never the value); insert-only for the application role; hourly per-tenant digests appended to the audit chain, so a read removed, changed or added later fails the check ([compliance](../compliance.md#secret-use)) | In place (was carried gap A4). Someone with database write access can still remove reads of an hour not yet digested (at most about 75 minutes) |
| B8 | Ciphertext swapped between tenants or names | Associated data binds tenant and name | In place |
| B10 | Forged WhatsApp webhook (a message or a button press that never came from Meta) | Signature verified with the app secret before anything is parsed; wrong phone number id ignored | In place (2026-10-07) |
| B10 | Replayed delivery or button | Message ids claimed in the database before acting (at most once); a token's row is spent when used, with its Approve/Reject pair | In place |
| B10 | Forged, altered or expired decision token | HMAC-SHA256 under `TASKIEM_WHATSAPP_TOKEN_KEY` over every claim; claims besides the header stored per nonce in the tenant; expiry in the signed header; refusals audited | In place. The key is in the environment, not the KMS: a leaked key plus a stored token row still needs the approver's bound number |
| B10 | A button forwarded to, or tapped by, someone else | The sender's bound number must belong to the approver the token names; the vote is then checked by `VoteApproval` (role, delegation, makers, distinct approvers) | In place |
| B10 | Approving over WhatsApp without the second factor a policy requires | Step-up is never satisfied in chat: a 10-minute single-use hand-off link (token in the URL fragment) to a web page that needs a session as the same person and a passkey or TOTP for that decision | In place. A WhatsApp Flows PIN is milestone A2 |
| B10 | Taking over a number (SIM swap, stolen phone) | Binding needs the code sent to the number and proof of the account; a taken-over number gets only what its owner could do there, step-up approvals still need the owner's passkey or authenticator, every start needs an explicit confirmation, per-number rate limits; the owner unlinks the number in the web app | In place. WhatsApp's own two-step PIN is the person's responsibility |
| B10 | Binding someone else's number, or guessing codes | OTP to the number (6 digits, 10 minutes, five guesses, three an hour per person, a few per number); the number is unique to one account | In place |
| B10 | Personal data or secrets in WhatsApp messages (which Meta and the phone keep) | Subjects and inputs masked by category (account and card numbers last four), names to an initial, credential-like fields hidden, free text redacted; inputs typed in chat sealed while waiting | In place |
| B10 | One tenant's data reaching another through the shared number | Person-level tables reachable only through narrow functions; conversation state, tokens and notices under forced RLS and read with the conversation's (or token's) tenant only; every message names its organisation | In place |
| B9 | History rewritten by someone with database access | Hash chain plus anchors outside the database; anchors emailed | In place, provided anchors go to write-once storage (see [kubernetes.md](../kubernetes.md#storage)) |
| B11 | A partner (or its staff) reading a sub-tenant's data outside the partner API, or without a trace | Memberships never put sub-tenants in scope (`taskiem_auth_tenant_scope` refuses to); the partner API's only way in checks the parent and writes both audit chains in the same transaction as the access; partner views and webhooks carry run outcomes, never inputs, outputs or messages | In place (`TestSubTenantIsolation`, `TestPartnerEnter`). The partner's own counts of its sub-tenants' runs are not audited (counts only) |
| B11 | One partner reaching another partner's sub-tenants, or a sub-tenant reaching a sibling | `parent_id` checked against the single partner in scope; the parent is fixed at creation; nesting refused; an app, a token and a sub-tenant must all belong to the same partner | In place |
| B11 | Stolen, forged or replayed end-user token | 256-bit random, stored hashed, at most 1 h (a `CHECK`), bound to its app (the path) and optionally its origin; revocable per end user; dead once the sub-tenant is suspended, the app disabled or the partner disabled. A token in a page is readable by that page's scripts: a cross-site scripting flaw in the partner's product exposes it for its lifetime | In place (`TestEndUserTokens`, `TestSubTenantSuspension`). Partners should mint the shortest useful TTL and bind an origin |
| B11 | An end user escalating beyond what the partner allows: secrets, members, approvals, other routes, connectors the app does not allow | Separate route tree with exactly the builder's handlers; permissions within a fixed ceiling and the app's current list, re-checked per request; connectors and the `http`, `code` and `ai` step types checked at save, validate, publish and run start; four-eyes publishing still needs a person | In place (`TestHeadlessFlow`) |
| B11 | A hostile page driving the embed API with a user's token (CSRF), or reading answers cross-origin | Tokens travel in the `Authorization` header, never cookies, so a page cannot borrow them; CORS answers only the app's exact origins, only on embed routes, never with credentials; a request without `Origin` only for headless apps | In place (`TestEmbedCORS`) |
| B11 | Branding tokens carrying script or style injection into the embedded builder (C2) | Every token validated against a strict format (hex colours, a font-name charset, https URLs, `Npx`), unknown fields refused | In place; C2 must still render them as values, never as markup |
| B11 | Partner webhooks forged, replayed, or aimed at internal addresses | HMAC-SHA256 over timestamp and body with a per-app secret in the vault, shown once and rotatable; delivery through the egress guard | In place (`TestPartnerWebhooks`) |
| B11 | A partner flooding the platform through many sub-tenants | Sub-tenants' limits capped at the partner's; partner-wide caps on sub-tenant count and runs per day and month | In place. Rates and concurrency are per sub-tenant, not shared: a partner's total is its sub-tenants' sum. A suspended sub-tenant's triggers keep firing (follow-up) |
| B12 | Prompt injection: a goal, connector description or existing workflow tells the model to publish, approve, exfiltrate secrets or call a provider | The model has nothing to do any of that with: no route under `/v1/ai` publishes, approves or runs (`TestAIRoutes`), the builder cannot reach the vault, workers or connector handlers (`TestImportGraphExcludesPrivilegedCode`, `ManifestOnly`), and its only output is a proposal that is validated by the publishing checks and shown to a person, who saves it as a draft. Injected content can at worst produce a bad proposal | In place (2026-10-07) |
| B12 | A malicious or careless proposal: a payment without approval, a webhook with no authentication, an HTTP step to an attacker's host | Same validation as a human's edit (schema, CEL, secret placement, write classes, connectors); payments without a preceding approval flagged and fed back for correction; the reviewer sees warnings and dry-run results before saving; publishing keeps its own permission, four-eyes and egress rules | In place. The reviewer remains the control for intent (an HTTP step to a host the tenant allowed is valid) |
| B12 | Personal data or secrets sent to the model provider | Prompts built from names and summaries; secret values, credentials and variable values never selected (a test seeds each and checks every prompt); `pii.Redact` over every prompt before it leaves; logs store the redacted prompt | In place. Redaction is pattern-based (emails, Nigerian phones, BVN, NIN, cards): free-text personal data it does not recognise (a name in a goal) can reach the provider, under its data-processing terms (needs people, AI1) |
| B12 | Cost exhaustion: one tenant burns the deployment's model spend | Per-tenant monthly token budget checked before every call; five builds at once per tenant; at most four calls per build; builds time out after 15 minutes | In place |
| B12 | Model or provider outage, or a refusal, blocks work | AI building degrades to a clear error and manual building; runs never depend on the model | In place |
| B12 | Poisoned recorded data (a webhook payload, a provider response, an error message) instructs the repair model to write a malicious patch: send money elsewhere, drop an approval, call an attacker's host | The run's data is presented as data; the patch must keep the workflow's id, pass the publishing checks without a new policy finding (a payment without approval is refused), complete a shadow run with every write mocked and inputs matching their schemas, and pass the stored tests; only then is it shown, as a diff, to a person with `workflow.publish` and `run.resolve`, and published through the normal path (four-eyes, promotion gates). The repair system cannot publish, approve or resume (`TestRepairRoutes`, `TestRepairFourEyes`) | In place (2026-10-07). As with the builder, the reviewer remains the control for intent: a patch that changes a recipient to another valid value passes every check |
| B12 | A repair or resume repeats an effect: a completed payment sent again by the resumed run | Resume is a fork that replays the parent's recorded outcomes instead of executing them; a completed write whose input the patch changes is parked, never sent; runs with uncertain or compensated writes are not resumed; the fork keeps the parent's idempotency seed; one resume per proposal (dedup key) | In place (`TestForkResumesWithoutRepeatingWrites`, `TestForkParksAChangedWrite`, `TestRepairDataPatchPublishAndResume` counts provider executions) |
| B12 | Personal data from a failed run reaching the model or a stored test | The model sees the sealed history with placeholders, never opened values; the shadow run on real data runs in the API and reports step ids, statuses and messages scrubbed of every value the history held, then redacted again; regression tests are built from the redacted recording; reconcile results are masked | In place (`TestRepairDataPatchPublishAndResume` seeds a secret, an email and a BVN) |
| B12 | The AI resolving an uncertain write | Unknown outcomes are never accepted: the service runs only a read-class reconcile action and shows its answer; a person resolves the parked step with the existing, audited endpoint | In place (`TestRepairUnknownOutcome`) |
| B12 | Repair cost or load: a burst of failures | One job per run and reason; at most three model calls per repair; the tenant's budget checked before each; a per-tenant switch; jobs processed one at a time per tenant in the background | In place |
| All | Personal data exposed in history, approvals or reports | Declared PII fields sealed (inputs and outputs); unsealing needs a permission and is audited | Nested input paths (`transfers[].account_name`) are carried gap A4 |

## Assumptions

- TLS terminates at the ingress. `TASKIEM_TRUST_PROXY` is on only behind a proxy that overwrites `X-Forwarded-For`.
- The database role used by the pods is `taskiem_app`, not the schema owner. Only migrations run as the owner.
- OpenBao (or the cloud KMS) is separate from the database and its token is scoped to the transit key.
- The scheduler's anchor directory is write-once storage, or anchors are also emailed outside the platform.
- Cluster network policies or the egress guard, not tenant goodwill, stop workers reaching internal services.
