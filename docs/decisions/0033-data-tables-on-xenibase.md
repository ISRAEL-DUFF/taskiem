# 0033 — Data tables: a Xenibase project per organisation, reached through the ordinary connector

Date: 2026-10-17 · Status: Proposed

## Context

The joint document and the [integration plan](../xenibase-integration.md) (P3-T2, Q4, Q6, Q9) raise "data tables": records a small business keeps (customers, debtors, staff, stock) that its workflows read and write. Taskiem has no such feature. The SME templates assume a Google Sheet for every list, and a trader on a phone has no sheet. The [chat-first strategy](../strategy/chat-first-nigeria.md) makes data tables the piece that lets the agent answer "remind my customers who owe me" with no sheet and no database in sight.

Xenibase now publishes what the plan asked of it: the V4 data API writes rows with bound values, one operation per call, a required filter and a `max_affected` guard, non-2xx errors with stable codes, and an `Idempotency-Key` honoured for 24 hours (Xenibase decisions, "Taskiem integration asks"); a structured schema API (`POST /projects/{id}/schema/preview` then `/apply` with the preview's hash); project creation by an API token with the `write` scope under the organisation's quotas; backend services turned on and API keys minted by a token with the `admin` scope; and an error-code list with a deprecation policy. So the plan's P1-G1, P1-G2 and P1-G4 are answered without a parameterised SQL endpoint, and the "stopgap" the plan feared is not needed.

## Decision

1. **A data table is a Postgres table in a Xenibase project, plus Taskiem's record of it.** Taskiem keeps the table's id, name, title, columns (name, title, type from a small list, required, personal-data flag) and limits in its own database under forced row-level security (`data_tables`, `data_table_columns`). The rows live only in Xenibase. The table in Postgres is `public.<name>` with an `id bigint generated always as identity primary key`, `created_at` and `updated_at timestamptz`, and the declared columns; changes go through Xenibase's schema preview and apply, never SQL text written by Taskiem.
2. **One Xenibase project per organisation, provisioned by Taskiem, in a Xenibase organisation the platform owns.** The operator configures `TASKIEM_XENIBASE_URL`, `TASKIEM_XENIBASE_TOKEN` (an unrestricted token with `read`, `write` and `admin` scopes on that organisation) and `TASKIEM_XENIBASE_ORG`. The first table an organisation creates makes its project (shared tier, the configured region, named after the tenant id), waits for the create operation, turns backend services on, keeps the secret key from that one answer, and mints a project-restricted token (`read`, `write`) for the connection below. The platform token is never stored in a tenant's vault and never used by a workflow. A sub-tenant gets its own project like any tenant; its partner's plan limits apply. Q9 is answered: one project per organisation; the platform pays for it as part of the plan.
3. **The project is reachable as an ordinary `xenibase@1` connection named `data_tables`, in the `prod` environment, owned by Taskiem.** Its credentials (the restricted token, the project id, the secret key, the data API URL) sit in the tenant's vault like any connection's. The connection is marked `managed`: people see it on the Connections page as "Data tables", may test it, and may not edit or delete it (Taskiem rotates its token before expiry). Workflows use the connector's actions on it (`query_rows`, `insert_rows`, `upsert_rows`, `update_rows`, `delete_rows`) and its `row_changed` trigger, so a data table starts workflows the way any Xenibase table does, and nothing in the engine knows what a data table is. The AI builder's context lists the organisation's tables and columns next to its connections, so a goal names a table instead of a sheet.
4. **An organisation may bring its own Xenibase project instead.** Settings > Data tables accepts an existing `xenibase@1` connection of the organisation's own (its token restricted to the project, with the project's secret key). Tables are then created in that project and the `data_tables` connection is that one. Q4 is answered: Xenibase is the only backend, and the third-party test holds because everything Taskiem does with the project goes through Xenibase's published APIs with the customer's own credentials.
5. **Rows are read and written through the data API with the secret key, and every write carries an idempotency key.** Taskiem's own API (`/v1/tables/{id}/rows`, the table page, CSV import, chat) and the connector's write actions both send `Idempotency-Key`; the connector's is the engine's derived key, Taskiem's API's is the request's own. Updates and deletes name a key or a filter and a `max_affected`; the data API refuses the rest.
6. **Personal data.** Columns of type `phone` and `email`, and any column flagged personal, are masked wherever the connector's outputs are (the connector declares `pii` on rows), in chat, in logs and in the AI builder's context (which sees names and types, never rows). The table page shows rows to people with the `table.read` permission; `table.edit` creates and changes tables and rows. Both are added to the owner and admin roles.
7. **Limits.** A plan limit `max_data_tables` (default 20; 0 is no limit) and `max_data_table_columns` (50) are enforced by Taskiem; row counts and size are the Xenibase project's own quotas, surfaced as the data API's `plan_limit_reached` and `quota_exceeded` errors. A table's rows are the organisation's data: deleting the table drops the Postgres table (Xenibase takes a final backup of the project on its own schedule) after a typed confirmation; deleting the organisation deletes the project.

## Alternatives considered

- **Rows in Taskiem's own database.** Rejected: Taskiem's database is the execution store, kept small and partitioned by run; a tenant's growing record store does not belong under the same row-level-security and retention rules, and Xenibase already does backups, point-in-time recovery, quotas and a table UI.
- **A new `tables@1` connector or a new step type.** Rejected: the `xenibase@1` connector already has the reads, the trigger and (with this work) the writes; a second surface to the same project would need its own schemas, classes, tests and builder context. A managed connection reuses all of it, and a workflow written against a data table works unchanged against any Xenibase project.
- **A schema per organisation in one shared project.** Rejected: one project per organisation gives each its own roles, keys, quotas, backups and webhooks, and makes "bring your own project" the same code path.
- **Taskiem writing DDL.** Rejected: the schema API previews the SQL, names the risks and applies it with a hash; Taskiem never composes SQL text (the same rule the connector keeps for rows).
- **Rows readable by every member.** Rejected: rows are personal data by default; a permission pair keeps the table page behind an explicit grant, like secrets and policies.

## Consequences

- The platform needs a Xenibase organisation, a token and a region before any organisation can create a table; without them the feature answers 503 `tables_unavailable` and the Templates and chat surfaces leave it out.
- Xenibase tokens expire (a year at most); a scheduler job renews the `data_tables` connection's token two weeks before expiry and alerts the operator if the platform token cannot mint one.
- Deleting a column drops its data; the API and the page ask for the column's name typed, as Xenibase's own editor does.
- The row-changed trigger on a data table is registered remotely like any `xenibase@1` trigger (decision 0021), so an organisation on the platform's Xenibase gets webhooks within the project's plan rate.
