# 0016 — Self-repair, and resuming a failed run as a fork

Date: 2026-10-07 · Status: Accepted

## Context

Phase 3 milestone B2 (spec 12.2) repairs failed runs: classify the failure, propose a fix, prove it in a shadow sandbox against the run's real recorded data with every write mocked, and offer a person a one-click "publish and resume from the failed step" that still goes through the normal approval policy. Three things had to be decided: where the analysis runs and who acts, how the model can see enough of a run to patch it without seeing its personal data, and how a run pinned to one version continues on another without repeating anything it already did.

The engine pins a run to its version (`runs.version`); `decide()` replays the run's whole history against that version's definition. Changing the version under a running history would replay old events against a new graph (renamed or reordered steps, foreach items that now differ), which `decide()` was never designed to accept. Spec 4.10 already describes the repair path as **fork from step**: a new run that continues from a chosen step on a newer version, inheriting the parent's idempotency seed so it "never pays twice for a step the parent already completed"; `runs.parent_run_id` and `forked_from_seq` were reserved for it in Phase 1.

## Decision

1. **Triggering is a queue, filled by triggers, worked in the background.** An `AFTER UPDATE OF status` trigger on `runs` (to `failed` or `needs_reconciliation`) and an `AFTER INSERT` trigger on `connector_drift` (a first finding) insert one `repair_jobs` row per `(run, reason)`, in the transaction that caused it. That insert is all the failing transaction does; the analysis runs later in the API role (`Server.RunRepairs`, only where a model provider is configured), one claimed job at a time with `SKIP LOCKED`. A drift job waits for its run to settle. Jobs are skipped when the tenant turned repair off (`ai_repair_settings`, on by default), when the run already has an open proposal, or, for a job that needs the model, when the tenant's `ai_monthly_tokens` budget is spent. Runs are never delayed.

2. **Rules first, the model second.** `repair.Classify` reads the error kind, HTTP status, connector error class, `MaybeApplied`, drift findings for the run's connector actions and whether the failing step reads the trigger. It decides `unknown_outcome`, `credential` and `transient` outright, and `data` and `schema_drift` when the evidence is clear; otherwise it gives a best guess and the model classifies in the same call that proposes a patch. `transient`, `credential` and `unknown_outcome` never reach the model when the rules are sure, and never change the workflow.

3. **The model sees redacted data; the shadow sees real data; the two never meet.** The repair service (the API) opens the run's history under the tenant's scope and also reads it sealed. The model gets the sealed view with every envelope replaced by a placeholder and free text masked (`shadow.Recording.Redacted`), plus the definition, the failure and the connector schemas. The shadow run uses the opened recording, inside the service. What a shadow run reports back to the model is step ids, statuses and messages, with every personal value the history held (the opened taint set) replaced and `pii.Redact` applied, and then `ai.Redacted` again on the way out. `engine/ai/repair` cannot import `engine/shadow`, `engine/drift`, the runtime, the database or the vault (`imports_test.go`).

4. **A patch must earn its way to a person.** Up to three model attempts. Each patch must keep the workflow's id, change something, pass the publishing checks (`wdcheck`) without adding a policy finding, and then pass the shadow: the patched definition runs on the real orchestrator (`engine/wdtest`) with the run's recorded trigger, completed steps answered from their recorded outputs (as a resume would replay them), everything else mocked from output schemas (so every write is mocked), recorded approvals and signals, and must complete with connector inputs that match their actions' input schemas. A regression test for the failing case, built from the redacted recording, must pass on the patch (and is recorded as reproducing the failure when it fails on the old version); the model's own test, if any, must pass; every stored test of the workflow (`workflow_tests`) must still pass. Failures are fed back. A patch that never passes is **withheld**: stored for audit, never offered.

5. **Accepting is a person's request through the normal path.** `POST /v1/repairs/{id}/accept` needs `run.resolve` and, for a patch, `workflow.publish`. It creates the next version with `created_by = system:ai-repair` and `repair_id` naming the proposal (the AI co-author); the accepting person is recorded on the proposal and in the audit chain, and is the one who asks to publish. Publishing then runs exactly as a person's: with four-eyes on, a publish request in that person's name that someone else must approve (the system author is not a person, so the accepter cannot approve their own request); otherwise `publishTx` with its checks. Promotion gates apply: the run resumes only once the version is deployed in the run's environment, checked after the publish, after a publish decision and after a promotion (a rejected publish request dismisses the proposal). Accepting a transient or credential action needs `run.resolve` and resumes on the same version. Unknown outcomes cannot be accepted: the service runs the connector's reconcile action (only one whose class is `read`) and shows the answer; a person resolves the parked step with the existing resolve endpoint.

6. **Resume is a fork, not a migration.** `Store.Start` with `Fork{Parent}` creates a new run on the new version, with the parent's trigger and variables, `parent_run_id`, `forked_from_seq`, `resumed_step`, and the parent's idempotency seed (`runs.idempotency_seed`). It is refused unless the parent is `failed`, no write has an intent without an outcome, no failure may have been applied, and the parent ran no compensation. The parent's outcomes are copied, as recorded (sealed), into `run_replays`. The new run's own orchestrator schedules steps as usual; when it schedules a task the parent completed, `applyEffects` appends the parent's `StepCompleted` (marked `replayed_from`) instead of queueing the task, provided the resolved input's digest equals the parent's. A **read** with another input is executed normally; a **write** with another input is parked (`fork_mismatch`, `needs_reconciliation`) for a person, never sent and never replayed. Signals the parent received are delivered again; waits the parent finished fire at once; approvals are asked again (the version they approved changed). The worker uses the inherited seed for keys, so any effect the fork sends carries the key the parent would have used; a step the parent attempted and that failed definitively starts at the next attempt group, so a provider does not answer it from a cached failure. Each accepted proposal resumes at most once (`TriggerID = repair/<id>`, a dedup key).

## Alternatives considered

- **Migrating the run in place to the new version.** Simpler to show, but `decide()` would replay the old history against a different graph, and nothing guarantees the replay is consistent (renamed steps, changed foreach items, changed inputs to completed writes). Proving it safe in general amounts to the fork's input check anyway, while losing the old run's record as it was.
- **Copying the parent's history up to the failed step into the new run.** Rejected for the same reason: copied `StepScheduled` events carry the old version's inputs; the fork lets the new version decide and only substitutes outcomes whose inputs match.
- **Analysing inline in the failing transaction.** Rejected: a model call must never hold a run's lock or delay it.
- **Letting the model see opened data for better patches.** Rejected: redaction is the boundary (decision 0014); the shadow, which needs real values, runs on the service's side.

## Consequences

- A completed write is never sent twice by a resume: it is replayed, or parked if the patch changed it. Tests count provider executions for each case.
- Approvals in a resumed run are asked again; long waits already served are not.
- A run whose failure triggered compensation cannot be resumed; a person starts a new run.
- Regression tests accumulate per workflow (`workflow_tests`) as repairs are accepted, so later repairs cannot quietly break earlier fixes. Git-led workflows refuse the accept (their changes go through the repository), as manual edits do.
- A model-free deployment queues jobs that nobody works; they are tiny and skipped as soon as a provider is configured and the loop runs.
