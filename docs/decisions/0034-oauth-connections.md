# 0034 — OAuth connections: one click to link a provider, with the secrets kept server-side

Date: 2026-10-17 · Status: Proposed

## Context

A connection is made by pasting credentials the person first makes at the provider: for Xenibase, an API token restricted to a project with the right scopes and expiry ([Xenibase integration](../integrations/pgdock.md#connection)). That is six choices in another product before the first workflow runs, and the [chat-first strategy](../strategy/chat-first-nigeria.md) wants a trader on a phone to connect a service in one step. Xenibase now publishes an OAuth 2.0 authorization code flow for third-party apps (its `docs/oauth-apps.md`: PKCE required, confidential clients, a consent page where the user picks the organisation, scopes, projects and expiry, a single-use code, a token endpoint, RFC 7009 revocation, `401 invalid_token` once a token is gone), and names Taskiem as its first app. Nothing in it is private to Taskiem: the [third-party test](0018-pgdock-integration-principles.md) holds.

The manifest contract is frozen for Phase 1 ([contracts](../contracts/README.md)); the gmail and googlesheets connectors already hold tokens people paste, and the schema had an unused `auth.oauth2` block (authorize and token URLs, scopes) from the start.

## Decision

1. **A connector declares OAuth in its manifest, alongside its pasted fields.** `auth.oauth2` (the existing, unused key, extended rather than a new one) names the provider's authorize, token and optional revoke URLs, the scopes Taskiem asks for, `pkce: true`, and `fields_from_token`: which auth fields the token answer fills. The pasted fields stay: a person without a registered client, or with a self-hosted provider, pastes as before. The addition is contract rule 13; nothing existing changes.
2. **The provider's server is resolved at runtime.** Xenibase is installed per operator, so the manifest's URLs start with `${server}/` and are resolved from the connector's base URL (the platform's Xenibase, `TASKIEM_PGDOCK_URL`). A connection's own server is never used for OAuth: Taskiem is not registered there. A platform that names no server cannot link the connector, and says so.
3. **State and PKCE live on the server, for ten minutes, once.** `POST /v1/connections/oauth/start` records the request (tenant, person, connector, environment, name) with the state hashed and the PKCE verifier sealed under the tenant's key like a connection's credentials, and answers the consent URL. The callback is unauthenticated (the browser arrives from the provider), so the state alone names the request, through a `SECURITY DEFINER` function that marks it used in the same statement, as single sign-on does. An unknown, used or expired state is refused without saying which. The browser never sees the verifier or the client secret; the exchange is made by the API through the egress guard.
4. **One project per connection.** A Xenibase connection is one project, as the connector was built. `fields_from_token` takes `project_ids[0]`, and a grant that names no project (every project) or several is refused, its token given back to the provider, and the person asked to connect again and choose one. The token's expiry becomes the connection's `expires_at`; there is no refresh token, and when it expires the person connects again.
5. **Optional fields come afterwards.** The token reaches only the management API; Xenibase's data API needs the project's secret key and URL, which no OAuth grant gives. `PUT /v1/connections/{id}/credentials` merges fields into a connection's credentials, keeping the token, and the Connections page offers it right after linking.
6. **Revocation goes both ways.** `DELETE /v1/connections/{id}` (new; refused for a connection a deployed workflow names unless forced, and for one Taskiem keeps) also revokes an OAuth connection's token at the provider, best effort. In the other direction, a connector reports a provider's "token revoked or expired" answer by wrapping `connector.ErrCredentialsRejected` (Xenibase: `401 invalid_token`), and the worker, at the one place every connector call's error passes, marks an OAuth connection `expired`. Pasted credentials are left alone: the person replaces them. The remote reconciler's calls (webhook registration) do not pass that place; a revoked token shows there as an unhealthy subscription until the next run expires the connection.
7. **Client registration is in the environment, for now.** `TASKIEM_OAUTH_<CONNECTOR>_CLIENT_ID` and `_CLIENT_SECRET`, read once at start, per connector. Taskiem is one app at the platform's Xenibase, registered once by a platform admin there; the secret is a process secret like the platform's Xenibase token, not a tenant's. A registry of clients (per server, rotated through the operator console) can come when a second provider or a second server needs it; nothing in the API would change.

## Alternatives considered

- **A new `auth.oauth` key.** Rejected: the frozen schema already had `auth.oauth2` for this; a second key for the same thing would leave the first as a trap.
- **The browser does PKCE and the exchange (a public client).** Rejected: Xenibase registers Taskiem as a confidential client, the token must land in the vault without passing through the web app, and the state check belongs where the request was recorded.
- **Keeping the verifier in the clear, as the SSO request does.** Rejected: the vault's sealing is one call, and a request row then proves nothing to anyone who reads the table.
- **Storing the token as a named secret and pointing the connection at it.** Rejected: a connection's credentials are one sealed object with a recorded read per use; the token is a credential like any other.
- **Expiring the connection from the connector's `test_connection` only.** Rejected: the worker's error path is a single choke point with the connection in hand, so the first run after a revocation marks it, not the next manual test.
