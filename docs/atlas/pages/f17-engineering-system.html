What it is

Everything that stands between a change and a running server: the Makefile a contributor runs, the two workflows in .github/workflows, the tests they run, the licence gate, the generators whose output is committed, and the docs that tell people how to do all of it. There is one CI workflow, ci.yml, with eleven jobs, and one scheduled workflow for the AI evaluation against a real model. Nothing is filtered by path except one step inside the ai-eval job, so every pull request runs the whole Go and browser suites.

Risk

CONTRIBUTING says "Run make check before pushing; CI runs the same targets" (CONTRIBUTING). A contributor who follows it skips the api, runtime, e2e and every other database test, and CI also runs things no target does: the theme loop, OpenBao transit, migrations through the CLI, the browser suite, both image jobs, the VM rehearsal and the chart check. Add export TASKIEM_TEST_DATABASE_URL to the Makefile (or make test-db run ./...), and have CONTRIBUTING list what CI runs beyond make check and the golangci-lint version.

Images, signing and promotion

Every push to main and every v* tag publishes ghcr.io/<repo> as sha-<12>, as the version for a tag, and as staging for main (tags). Buildx attaches an SBOM and mode=max provenance, and cosign signs the digest with the workflow's OIDC identity. Servers check that identity before they pull:

VM servers follow a channel tag. A staging server moves on every merge. A production server moves when promote re-points production, which waits for a reviewer in the production environment. The vps job runs with TASKIEM_VPS_VERIFY: "0" and local images, so CI never exercises the signature check itself. The image build excludes .git through .dockerignore, so the checkout's token does not reach a build stage.

Risk
  • staging can go backwards. ci.yml has no concurrency group, so two merges a few minutes apart run two image jobs at once. Each moves staging when it finishes, and the older commit can finish last. taskiem-vps update only checks that the digest differs, so staging servers then "upgrade" to the older binary, after the newer one has already run its migrations. Fix: give image a concurrency: image-${{ github.ref }} group, and check that GITHUB_SHA is still the head of main before tagging.
  • The signed image is not the one the tests ran. docker, vps and deploy each build their own copy, and image builds again later from base images named by tag (node:22-alpine, golang:1.26, distroless/static-debian12:nonroot). If a base tag moves in between, the image that is pushed and signed has never been run. Fix: build once, push by digest, run docker and vps against that digest, then tag and sign it, and pin the base images by digest.
  • Actions are pinned by tag, not by commit. The jobs that hold packages: write and id-token: write run docker/* and sigstore/cosign-installer by tag, and release-build runs anchore/sbom-action@v0, a floating major tag. If any of those tags is moved to malicious code, that code can mint the OIDC identity that every server trusts. Fix: pin every third-party action to a commit SHA and let Dependabot update them.
  • Any v* tag is a release. A tag on a commit that never went through review is still built, tested and signed with an identity the SIGNER pattern accepts. Only the environment approval stands between it and production, and that approval is configured outside the repository. Fix: a tag ruleset, plus a check in image that the tagged commit is an ancestor of main.

release-build signs a bare binary and an SBOM of the source tree (Syft over ., so it includes the web app's dev dependencies) and keeps them as a 90-day workflow artifact. It runs on main but not on tags, so a tagged version has a signed image but no signed binary.

Risk
  • The 192 lines of alert unit tests that the phase 4 status page lists as shipped are never run by CI. A rule change that breaks paging still passes. Fix: install promtool in the go job from the Prometheus release, checking its checksum.
  • The engine harness gives every provider call 200 ms unless a test sets more (harness). For a write, that time counts from when the intent was recorded, so it includes database time on a loaded runner. Commit 269ddb7 fixed one test that tripped it ("four Paystack calls at once against the harness's 200ms default, which a loaded runner can miss") by raising that test's limit. Many other test files use the default. Fix: raise the default to a few seconds, and set short timeouts only in the tests that are about timeouts.
  • No job runs the race detector (-race), though the engine's correctness depends on concurrent workers, leases and fencing.

Two recent fixes were tests that built a "wrong key" by replacing the first character with x. A random key that already began with x stayed right, about one run in 32. A search of the Go and Playwright tests finds no other copy of that pattern. Tests that use "000000" as a wrong authenticator code (whatsapp_test.go, dispatch_test.go) are the same kind of test, but they fail only when one of three valid codes is 000000, about three runs in a million. The WhatsApp browser spec already avoids this.

Determinism and crash recovery

The engine's promise is that a run replays exactly and an effect happens once. Two suites in suites_test.go test it, through fault hooks the worker exposes for tests only:

TestCrashRecoverySuite starts 120 payment-shaped runs (an idempotent transfer, a reconcilable bank transfer to a provider that ignores keys, and a fan-out of three transfers). Four workers with 400 ms leases run them. The hooks crash a worker after an intent or after a call (4% each) or stall it past its lease (1%), the test kills a worker every 300 ms, and the fake provider fails 8% of calls. When every run has settled, the test asserts that every run completed, that each of the five effects per run happened exactly once, that each step completed once, and that decide.Verify replays the history byte for byte. TASKIEM_CHAOS_RUNS=10000 is the G1 gate's size. Two more suites check that a code step's writes are never sent and that unsafe writes never repeat. TestDatabaseCrashSuite crashes Postgres itself, but only when TASKIEM_CHAOS_PG_CRASH names a command that does it. The worker crashes are random, but the invariants hold whatever the interleaving. The only timing in the test is its deadline, the number of runs × 100 ms + 60 s.

Spec and code differ

The build plan's determinism suite replays "any recorded run history", and its crash suite kills "workers, orchestrators, and the database primary" (build plan). TestDeterminismSuite is described as "replays every history the runtime tests produce", but it replays the 20 runs of one workflow that it starts itself. Verify is called from seven test files, not from the harness, so most runs the tests make are never replayed. The database-primary crash is opt-in and is not in CI. The build plan also calls for "live sandbox checks nightly" of connectors, and no workflow does that. Fix: call Verify on every run in the harness's cleanup.

Contracts and generated files

The contracts are checked from both sides:

  • OpenAPI. TestOpenAPICoversRoutes walks the chi router and fails on a route that is missing from api/openapi/openapi.yaml, or on one the document has but the router does not. The few routes left out are listed with a reason. TestOpenAPIMatchesSource compares each operation's permission, plan feature and authentication with the router's source. Every request the API tests send and every answer they get passes through ValidateResponse, unless the test marks the body invalidBody.
  • wd/v1. taskiem validate runs the schema and wdcheck with the binary's connectors. Every committed .flow.ts must compile to its .wd.json (flowcode_test.go), and every .wd.json must turn into SDK code and build back to the same definition (roundtrip.test.ts).
  • Connector conformance. conntest.Run replays recorded fixtures against a connector, built-in or WebAssembly, with no network. It also reports uncovered actions, idempotency keys that never reached the provider, and outputs that drift from the schema. Nine first-party connectors have a conformance suite (Mailchimp, Brevo, Resend, Meta, Payrolla, and the four Zoho and QuickBooks connectors). The others use their own fixture tests.

The licence gate and the clean-room policy

tools/licencecheck lists every non-standard module that the repository's packages and their tests import (go list -deps -test ./...). It classifies each module's root LICENSE, LICENCE or COPYING file with google/licensecheck, and fails on a module with no licence, a licence below 75% match, or one not in the allow-list. It does the same for npm packages from pnpm licenses list, accepting a package if any of its OR alternatives is allowed (okAny). The allow-list and the per-package exceptions (the OFL fonts, MPL axe-core and lightningcss, each with a reason) are in policy.json. At this commit, 78 Go modules pass. The checker has no tests of its own.

The clean-room policy forbids reading competitors' source, copying their artefacts, and having an AI assistant imitate them. It requires a decision-log entry for any design that looks like an existing product, and a signed acknowledgement and IP assignment before a contributor's first commit. The licence gate is its only part that a machine enforces. The acknowledgement table has no rows (G0), which needs-people L1 tracks as open. Most of the history is commits by an AI assistant, which the policy's rule 7 covers.

Risk
  • The gate can be loosened in the same pull request. The policy says a new allowed licence needs "a decision-log entry and founder approval". Nothing requires it: CODEOWNERS covers only the database definer files and itself, not tools/licencecheck/ or the workflows. A pull request can add a dependency and its exception together, or change what the licences job runs, and only the usual reviewer sees it. Fix: add /tools/licencecheck/ and /.github/workflows/ to CODEOWNERS, and require code-owner review on main.
  • Code copied into the repository is never checked. The checker skips the main module (main.go), so vendored third-party code inside it is invisible to the gate. That includes CPython in engine/sandbox/pywasm, under the PSF licence. Decision 0007 allows Python-2.0 for "TypeScript's dependency tree only" (0007), but the allow-list applies to Go too. The QuickJS fork in third_party/qjs is checked, because it is a separate module. Fix: have the checker scan every LICENSE file under the tree against a list of known vendored directories, and give allow-list entries an ecosystem.

Linting

.golangci.yml is golangci-lint v2's standard set, plus bodyclose, errorlint, gosec, misspell (UK spelling), nilerr, rowserrcheck, sqlclosecheck and unconvert, with gofmt and goimports. gosec is off in tests and the spike. It sets no build tags, so files behind //go:build e2e (democmd.go and its test) are never linted, though go test's vet pass still compiles and vets them. third_party/qjs is a module of its own, so ./... neither lints nor tests it. Its Taskiem edits are tested only through the sandbox tests.

eslint.config.js applies @eslint/js recommended and typescript-eslint's strict to every JS and TS file outside dist, node_modules, .claude and site: the web app, the SDK, the flows, the public host's scripts and this atlas. Type imports must be written as import type. ShellCheck runs only on install.sh and taskiem-vps.

The docs site, the API reference and this atlas

tools/docsite builds three things into one static site: the product website from the designer's pages, the docs from docs/, and the API reference from the OpenAPI document (decision 0025). It first checks every relative link and anchor in docs/, README.md and CONTRIBUTING.md. At this commit, 218 files resolve. Each doc must be either in the navigation or on the internal list (TestEveryDocClassified), and the web app's help links must be public pages. CI builds the site but publishes it nowhere, which needs-people P4-D1 tracks.

The atlas is built by make atlas and checked by node docs/atlas/atlas.mjs check. Neither runs in CI, so a renamed function breaks an atlas link silently until someone runs the check, and the committed site/index.html can fall behind its pages. Adding node docs/atlas/atlas.mjs check to the typescript job would catch both.

CONTRIBUTING and agent instructions

CONTRIBUTING.md is right on the docs workflow and the OpenAPI rules. Every command it names exists, as do the connector CLI commands in the connector guides. Where it is wrong or out of date:

  • "CI runs the same targets" (above). It does not mention make e2e, Playwright, go generate ./sdk or ./engine/slo, the golangci-lint version, or the atlas.
  • The layout table still describes Phase 0 and 1: "serve --role (Phase 1)", "the Phase 0 spike", "Web app (Phase 1)".
  • Two of its four "rules that CI enforces" are not enforced (contracts, above).

The repository has no CLAUDE.md or AGENTS.md at the root, so a coding agent gets no instructions for the Go side. The web app has one: web/CLAUDE.md includes web/AGENTS.md. Everything it points to exists: docs/brand/screens.md, Appendix C of no-technical-steps.md, naira(), fmtTime(), dateLabel(), brandFile(), e2e/accessibility.spec.ts and src/lib/plainwords.test.ts. docs/agents.md is about field agents, not coding agents. The CI runner downloads OpenBao with curl and no checksum (ci.yml). The VM installer, by contrast, verifies cosign's checksum.
