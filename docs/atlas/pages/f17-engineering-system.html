What it is

Everything that stands between a change and a running server: the Makefile a contributor runs, the two workflows in .github/workflows, the tests they run, the licence gate, the generators whose output is committed, and the docs that tell people how to do all of it. There is one CI workflow, ci.yml, with seventeen jobs, and one scheduled workflow for the AI evaluation against a real model. Nothing is filtered by path except one step inside the ai-eval job, so every pull request runs the whole Go and browser suites.

The CI jobs

ci.yml runs on every pull request and on pushes to main and to v* tags. Its default token is contents: read. It has no pull_request_target trigger and no secrets on pull-request jobs. Every third-party action is pinned to a commit with its version in a comment, and dependabot.yml moves the pins, the Dockerfile's base-image digests, both Go modules and the pnpm workspace weekly.

Images, signing and promotion

Every push to main and every v* tag builds the image once, from base images pinned by digest in the Dockerfile, and pushes it to ghcr.io/<repo> by digest with an SBOM and mode=max provenance. The docker and vps jobs pull that digest and run it. image then signs the same digest with the workflow's OIDC identity and only then tags it sha-<12>, the version for a tag, and staging for main (tags), checking that each tag names the signed digest. Servers check that identity before they pull:

VM servers follow a channel tag. A staging server moves on every merge. A production server moves when promote re-points production, which waits for a reviewer in the production environment. The vps job runs with TASKIEM_VPS_VERIFY: "0" and local images, so CI never exercises the signature check itself. The image build excludes .git through .dockerignore, so the checkout's token does not reach a build stage.

Resolved
  • staging could go backwards. ci.yml has no concurrency group, so two merges a few minutes apart run two image jobs at once. Each moves staging when it finishes, and the older commit can finish last. taskiem-vps update only checks that the digest differs, so staging servers then "upgrade" to the older binary, after the newer one has already run its migrations. image now has a concurrency group per ref that never cancels a running job, and tags staging only if its commit is still the head of main (ci.yml). GitHub keeps one waiting run per group, so a third merge in quick succession replaces the waiting one, whose image is then not tagged.
  • The signed image was not the one the tests ran. docker, vps and deploy each built their own copy, and image built again later from base images named by tag, so if a base tag moved in between, the image pushed and signed had never been run. It is now built once (image-build), run by digest, signed and tagged, and the base images are pinned by digest (Dockerfile).
  • Actions are pinned by tag, not by commit. The jobs that hold packages: write and id-token: write run docker/* and sigstore/cosign-installer by tag, and release-build ran anchore/sbom-action@v0, a floating major tag, so a moved tag could have minted the OIDC identity that every server trusts. Every third-party action is now pinned to a commit SHA (sbom-action), and Dependabot updates them.
  • Any v* tag was a release. A tag on a commit that never went through review was still built, tested and signed. image-build and release-build now fail on a tag whose commit is not an ancestor of origin/main (ci.yml), before anything is pushed or signed.
Risk

Who may push a v* tag, and the approval in the production environment, are set outside the repository. A tag ruleset would keep tags to the people who release. Untagged digests that image-build pushed for runs that later failed stay in GHCR, unsigned, until someone prunes them.

release-build signs a bare binary and an SBOM of the source tree (Syft over ., so it includes the web app's dev dependencies) and keeps them as a 90-day workflow artifact, for every merge to main and, named and versioned by the tag, every release.

Determinism and crash recovery

The engine's promise is that a run replays exactly and an effect happens once. Two suites in suites_test.go test it, through fault hooks the worker exposes for tests only:

TestCrashRecoverySuite starts 120 payment-shaped runs (an idempotent transfer, a reconcilable bank transfer to a provider that ignores keys, and a fan-out of three transfers). Four workers with 400 ms leases run them. The hooks crash a worker after an intent or after a call (4% each) or stall it past its lease (1%), the test kills a worker every 300 ms, and the fake provider fails 8% of calls. When every run has settled, the test asserts that every run completed, that each of the five effects per run happened exactly once, that each step completed once, and that decide.Verify replays the history byte for byte. TASKIEM_CHAOS_RUNS=10000 is the G1 gate's size. Two more suites check that a code step's writes are never sent and that unsafe writes never repeat. TestDatabaseCrashSuite crashes Postgres itself, but only when TASKIEM_CHAOS_PG_CRASH names a command that does it. The worker crashes are random, but the invariants hold whatever the interleaving. The only timing in the test is its deadline, the number of runs × 100 ms + 60 s.

Spec and code differ

The build plan's determinism suite replays "any recorded run history", and its crash suite kills "workers, orchestrators, and the database primary" (build plan). TestDeterminismSuite is described as "replays every history the runtime tests produce", but it replays the 20 runs of one workflow that it starts itself. Verify is called from seven test files, not from the harness, so most runs the tests make are never replayed. The database-primary crash runs in CI's chaos job, which does not yet pass (above). The build plan also calls for "live sandbox checks nightly" of connectors, and no workflow does that. Fix: call Verify on every run in the harness's cleanup.

Contracts and generated files

  • OpenAPI. TestOpenAPICoversRoutes walks the chi router and fails on a route that is missing from api/openapi/openapi.yaml, or on one the document has but the router does not. The licence gate and the clean-room policy

tools/licencecheck lists every non-standard module that the repository's packages and their tests import (go list -deps -test ./...). It classifies each module's root LICENSE, LICENCE or COPYING file with google/licensecheck, and fails on a module with no licence, a licence below 75% match, or one not in the allow-list. It does the same for npm packages from pnpm licenses list, accepting a package if any of its OR alternatives is allowed (checkAny). And it walks the repository for licence files (vendored): each must sit in a directory the policy lists as vendored, with the licences no file shows (CPython's), and each listed directory's licences must pass. The allow-list, whose entries can be limited to an ecosystem (go, npm, vendored), the exceptions, each naming its ecosystem and a reason, and the vendored directories are in policy.json. At this commit, 78 Go modules and 3 vendored directories pass, and the checker has tests.

The clean-room policy forbids reading competitors' source, copying their artefacts, and having an AI assistant imitate them. It requires a decision-log entry for any design that looks like an existing product, and a signed acknowledgement and IP assignment before a contributor's first commit. The licence gate is its only part that a machine enforces. The acknowledgement table has no rows (G0), which needs-people L1 tracks as open. Most of the history is commits by an AI assistant, which the policy's rule 7 covers.

Resolved
  • The gate could be loosened unseen. CODEOWNERS covered only the database definer files and itself. It now covers tools/licencecheck/, the workflows and dependabot.yml (CODEOWNERS).
  • Code copied into the repository was never checked, since the checker skips the main module, and Python-2.0, which decision 0007 allows for "TypeScript's dependency tree only" (0007), was allowed for Go too. Vendored directories are now checked and Python-2.0 is allowed only for npm.
Risk
  • The vendored CPython has an unapproved exception. engine/sandbox/pywasm is embedded in the binary and CPython is under the PSF licence stack, which 0007 does not allow outside npm. Its exception keeps the gate passing as before and says it is not yet approved (policy.json): it needs a decision-log entry or founder approval, or the module removed.
  • Code-owner review counts only if branch protection on main requires it, which the repository cannot show.

Linting

.golangci.yml is golangci-lint v2's standard set, plus bodyclose, errorlint, gosec, misspell (UK spelling), nilerr, rowserrcheck, sqlclosecheck and unconvert, with gofmt and goimports. gosec is off in tests and the spike. It builds with the e2e tag (.golangci.yml), so democmd.go and its test are linted too. third_party/qjs is a module of its own, so ./... skips it; the go job lints it from its directory with its own configuration, golangci-lint's standard set, since the repository's UK spelling and gosec rules would ask for changes to code kept identical to upstream, and runs its (upstream-stripped) tests. Its Taskiem edits are still tested mainly through the sandbox tests.

eslint.config.js applies @eslint/js recommended and typescript-eslint's strict to every JS and TS file outside dist, node_modules, .claude and site: the web app, the SDK, the flows, the public host's scripts and this atlas. Type imports must be written as import type. ShellCheck runs on install.sh, taskiem-vps and the browser tests' web/e2e/*.sh.

The docs site, the API reference and this atlas

tools/docsite builds three things into one static site: the product website from the designer's pages, the docs from docs/, and the API reference from the OpenAPI document (decision 0025). It first checks every relative link and anchor in docs/, README.md and CONTRIBUTING.md. At this commit, 218 files resolve. Each doc must be either in the navigation or on the internal list (TestEveryDocClassified), and the web app's help links must be public pages. CI builds the site but publishes it nowhere, which needs-people P4-D1 tracks.

The atlas is built by make atlas and checked by node docs/atlas/atlas.mjs check, which the atlas job runs, so a renamed function fails CI instead of breaking a link silently. On a pull request the job also fails when the atlas's pages, partials or build change without a rebuilt site/index.html.

Risk

The committed site/index.html cannot be compared with a rebuild byte for byte: a build records the commit and date it was made at, line counts of the whole tree and excerpts of the code it quotes, so any later commit changes it. A change to quoted code leaves the committed site behind until someone runs make atlas.
