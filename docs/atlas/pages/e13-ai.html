What the AI does here

Taskiem uses a language model in four places: to draft a workflow from a sentence (the builder), to diagnose a failed run and propose a fix (repair), to answer one question inside a running workflow (an ai step), and to route chat messages and moderate public pages. The rule from spec 12 runs through all of them: the AI proposes and people dispose. It can draft, diagnose and answer, but publishing, approving, starting a run and reading a secret stay with people, and every proposal goes through the same checks as a person's work.

The model layer

engine/ai is one small interface in front of every model (decision 0014). A request is system blocks (each can mark the end of a cached prefix), messages, an optional JSON Schema for structured output, a token ceiling and an effort level. Nothing else crosses it:

ProviderWhat it does
anthropic (default when ANTHROPIC_API_KEY is set)Claude through the official Go SDK, claude-opus-5-5 by default. Cached system blocks, effort through output_config, structured output, streaming above 16,000 max tokens, server-side refusal fallbacks unless TASKIEM_AI_FALLBACKS=off, and stop_reason: refusal checked before any content is read (Params).
selfhostedAny OpenAI-compatible /chat/completions server (vLLM, llama.cpp, Ollama, a gateway), with response_format: json_schema. Retries a 429 or 5xx three times, honouring Retry-After up to 30 seconds (post).
fakeA scripted provider that records what it was sent, for tests and the offline evaluation.

The deployment picks one with TASKIEM_AI_* (ConfigFromEnv). Without a provider, AI building is off and the canvas is the only way to build. Transient says which failures are worth trying again: a rate limit, a 5xx, a timeout or a broken connection, never a 400 or 401.

The layer turns text into text and holds nothing else. Redacted wraps a provider so every system block and message passes through pii.Redact (emails, Nigerian phone numbers, BVNs, NINs, card numbers) before it leaves. The builder, repair, chat routing and moderation each wrap their provider themselves, so no caller can forget. AI steps do not use it: they have their own, stronger masking, described below.

Spec and code differ

Spec 12.3 says "tenants with strict residency can require" a self-hosted model (spec 12.3). The provider is chosen per deployment, not per tenant: one process has one provider, and every tenant on it uses it. A tenant that needs residency needs its own deployment.

The builder: from a sentence to a draft

A person with workflow.edit types a goal of up to 4,000 characters on the web (POST /v1/ai/build) or in WhatsApp or Telegram. The API records an ai_builds row, reads the tenant's context, and runs the build in the background with no principal at all (startAIBuild). Builder.Build then does this:

  1. Context. aiContext reads names and shapes only: connections by name and connector, data tables by column names and types (never rows), variables by name (never values), roles by how many people hold them (never who), active policies by a summary, and the latest definition of up to 100 workflows, of which the builder keeps only the structure. Keyword scoring picks up to six connectors whose schemas go into the prompt, and up to two templates from the library as starting points (contextDoc). Connectors are passed as manifests with their handlers removed, so nothing in the pipeline can call a provider.
  2. Draft. The model answers an envelope under structured output: a summary, assumptions, the workflow as a JSON string, up to three test cases, or instead a template id and its parameters. The full wd/v1 schema is in the cached system prompt, because the schema itself is recursive and cannot be a strict output schema.
  3. Validate. The draft goes through the same publishing checks as a person's (injected from the API, s.check), then the builder's policy rule: a money-moving connector or capability step with no approval before it is a finding (PolicyFindingsWith).
  4. Correct. Problems and findings go back to the model, up to three times. The budget is checked before each call.
  5. Dry run. The final draft runs on the real orchestrator with every connector mocked from its output schema, plus the model's own cases.
  6. Review. The proposal holds the definition, the problems that remain, warnings, test results, the new data tables it wants, and what it needs before it can run.

Every model call is written to ai_interactions before its answer is acted on, and a recording failure stops the build. The table is insert-only for the application. Saving is a separate request by a person with workflow.edit: it creates a draft version authored by that person, with the build as co-author in the audit log (saveAIBuildTx). Publishing that draft is the normal publish, with four-eyes counting the saver as the author.

Risk

Saving a build that changed an existing workflow can silently undo edits made in the meantime. The build reads the workflow's latest version when it starts. A build can take up to 15 minutes, and the proposal can be saved any time later. Saving then writes the model's whole definition as the next version, with no check that the base is still the latest (saveAIBuildTx). The canvas's own save sends a parent_digest and merges three ways when someone else saved first (createVersion). Fix: keep the base version's digest on ai_builds and merge on save, as createVersion does, or refuse with a conflict.

Spec and code differ
  • Spec 12.1 starts from "the canvas, CLI, or WhatsApp" (spec 12.1). The taskiem command has no build command. Telegram, which the spec does not name, has one.
  • Decision 0049 says "the builder lists the startable workflows" for subflow steps (decision 0049). The builder has a Startable field and puts it in the prompt, but aiContext never fills it, so the model is never told which workflows a subflow step may start.

Self-repair: rules, then the model, then the shadow

When a run fails or parks a step, or the drift monitor sees a provider's response change shape, a database trigger queues one repair_jobs row per run and reason, in the transaction that recorded the failure. The failing run waits for nothing. The API works the queue in the background every five seconds (RepairOnce), skipping tenants that turned repair off and runs that already have an open proposal (decision 0016).

A patch that never passes is withheld: stored for audit, never offered. Accepting is a person's request (run.resolve, plus workflow.publish for a patch). The patch becomes a new version created by system:ai-repair, published through the normal path. With four-eyes on, that means a publish request someone else must approve. The run then resumes as a fork once the version runs in its environment, replaying completed steps and parking any write whose input changed (acceptPatch). An unknown outcome cannot be accepted: the service runs the connector's read-only reconcile action and shows the answer, and a person resolves the step.

Risk
  • Accepting a repair can roll back newer versions. A patch is the failed run's version plus a fix. Accepting it inserts it as the next version and publishes it, with no check that the workflow has not moved on since (acceptPatch). If version 5 failed and someone has since published 6 and 7, accepting the repair publishes 5 plus the fix as 8 and quietly drops their changes. The diff shown is against 5, so the reviewer cannot see it. The same happens when two failed runs of one workflow each get a proposal and both are accepted. Fix: refuse, or rebase with wdmerge against the latest version, when the proposal's version is no longer the newest, and mark open proposals superseded when a newer version is published.
  • One bad deploy fans out into one analysis per failed run. Jobs are unique per run, and the "open proposal" check is per run too, so 500 runs failing for one reason means 500 model analyses of up to three calls each. They all draw on the one monthly budget that AI building and AI steps share, and once it is spent, AI steps in other workflows fail with limit. Fix: one analysis per workflow version and failure signature, with later runs attached to that proposal.
  • One tenant's queue holds up every other tenant's. RepairOnce drains each tenant's queue completely before moving to the next, one job at a time with up to 15 minutes each, so a tenant with hundreds of jobs delays repairs for everyone after it. Fix: take one job per tenant in each round.
  • Data from outside can steer a patch. The model reads the failed run's trigger, which for a webhook comes from outside. The prompt says to treat it as data, and a patch must pass the checks, but the policy check only compares counts of findings, and a patch is one person's click from being published when four-eyes is off. The reviewer's reading of the diff is the real gate.

AI steps and personal data

An ai step asks the model one question during a run (decision 0050): sort a message, pull fields out of free text, summarise, or draft a reply. It runs on its own ai worker queue, and the worker is the only place a model is called with a run's data (aiEvent). Before anything leaves, the worker:

  1. checks that the deployment has a model and the business has not turned AI steps off (governance_settings.ai_steps);
  2. checks the monthly budget, unless the plan bills overage;
  3. masks the prompt and the input with a Masker: every value the run holds sealed, wherever it appears, and what the detectors recognise, each replaced by a placeholder such as [[name_1]]. The same value always gets the same placeholder, so the model can tell two mentions of one person from two people;
  4. leaves as they are only the top-level input fields the step lists in personal_data. Publishing a version with such a step writes ai.personal_data.allow to the audit log (auditAIPersonalData).

The answer must match the step's output_schema, which is sent with every object closed. A mismatch is sent back once, and a second fails the step with invalid_output. A refusal or a cut-off answer fails it straight away. A rate limit or provider error is retried under the step's retry policy. The placeholders in the answer are put back, and the output is sealed because it now holds personal values. Each call is an ai_interactions row against the run and step, counted against the budget (recordAIStep). Saving a version with an ai step checks the model, the plan and the switch first (aiStepProblems).

Risk
  • Personal data used as a map key reaches the model unmasked. The masker replaces values, never keys (maskKnown), and the input is then serialised whole into the question (aistep.go). Verified with an ai step whose input is {"balances": "={trigger.body.email: 5000}"}, with the email marked x-pii: the model receives the email in the clear. The interaction log masks it afterwards, so the record does not show what was really sent. Fix: mask keys as well (or refuse input whose keys hold a known value), and write the log from the exact bytes sent.
  • Short values and common number formats pass. A known value under 5 characters (MinRedact) is masked only when it is a whole field, not inside text, so a sealed first name such as "Ada" goes to the model inside a prompt like "Summarise the balances for Ada" (verified). In free text, the phone pattern accepts only unbroken Nigerian numbers, so +234 803 123 4567, +234-803-123-4567, (0803) 123 4567 and every non-Nigerian number pass, in the builder's redaction too (detect.go). Fix: normalise separators before matching, and accept international formats.
  • The plan is checked only when saving. The worker checks the switch and the budget, but not the plan's ai feature, so after a downgrade a published workflow's ai steps go on calling the model. Decision 0050 says the plan "gates AI steps as it gates building", and building checks it on every request.
  • A call that cannot be recorded is still used, and not counted. If the ai_interactions insert fails, the worker logs the error and completes the step with the answer (aistep.go). The budget is summed from that table, so those tokens are free and the call has no audit record. The builder stops in the same case.
  • The budget can be overshot. It is read once before the call, with nothing reserved, so concurrent steps all pass the check. The prompt and input have no size limit: one step can send as much as the model's context holds after the budget is spent.
  • The limit failure says "the step runs again once the budget allows", but it is final (next: fail) and nothing reschedules it (aistep.go).
  • A callable workflow may contain an ai step. Used as a template step, it is expanded only when the run starts, so the save checks and the ai.personal_data.allow record look at the workflow that uses it and see no ai step.
Spec and code differ

Spec 12.3: "hitting the cap degrades to manual building, never to blocking runs" (spec 12.3), and decision 0014: "Hitting it refuses AI building only." Since decision 0050, a run whose ai step meets a spent budget fails. The decision chose this, but neither the spec nor the budget section of docs/ai.md was updated, and that section still promises runs are never affected.

Chat routing and moderation

In WhatsApp and Telegram, a message in a language other than English that the word lists do not recognise can be routed by the model (waModelIntent). It may answer only one of a fixed set of intents with a short argument (Allowed). Yes, no and cancel are not among them, so the model can name a workflow to run but the person still confirms it, matched by the word lists. A build started in chat is the same build as on the web (waStartBuild).

Storefront moderation asks the model to judge public page text against a written policy after a word list and a price check (ask). Its "allowed" lets text go public, which makes it the one place where a model's answer, not a person's, decides what is shown. The text it judges is written by the business it judges.

Risk

Chat builds and repair skip the plan check. The web's /v1/ai routes require the plan's ai feature (FeatureAI: "AI building and repair"). waStartBuild checks the permission, the model, the budget and the rate limits but not the plan. Neither the repair loop nor chat routing checks it. A tenant on a plan without AI can build with AI from WhatsApp or Telegram, and gets model repairs, up to its monthly token budget (2,000,000 by default). Fix: call Billing.Require(…, FeatureAI) in waStartBuild, processRepairJob, waModelIntent and aiEvent.

Budgets

Each tenant has a monthly budget, ai_monthly_tokens (2,000,000 by default, 0 for none), summed from ai_interactions for the UTC month. Every token counts, cache reads included. A plan with AI overage lifts it (aiBudget).

Two uses sit outside that boundary by design. An ai step's answer is data the workflow acts on: if an author wires it into a payment, the model's answer feeds the payment, with only the builder's warning about payments without approval, and the builder's rule 21 telling it never to use an ai step for money. And moderation decides what goes public, above. Neither package is covered by the import test: the step's call is made in engine/runtime, and moderation lives in engine/moderation.

The evaluation suites

tools/aieval runs two suites through the same Builder and Repairer the API runs, with the platform's publishing checks and the compiled-in connectors, every connector mocked:

  • Builder (evals/builder): 308 requests in 17 files, each with the connectors, step types, trigger and properties a good answer must have. Properties are small rules over the definition, such as approval_before_payment, idempotency and no_inline_secrets (rules.go). A model judge is optional. TestNoEvalRequestInPrompts fails if any request, or any eight of its words, appears in a prompt or a template.
  • Repair (evals/repair): 22 recorded failures with the class a person expects, whether the rules should decide alone, and a case a patch must make pass.

Every pull request that touches engine/ai, evals, templates or tools/aieval runs both suites with the offline heuristic provider against the committed baselines at zero tolerance (ci.yml). The real model runs nightly when ANTHROPIC_API_KEY is a repository secret, and does nothing without it (ai-eval.yml). The heuristic is not a model: it catches regressions in retrieval, templates, validation, the dry run and the grader, not in what a model does.

Risk
  • The CI filter misses code the suites depend on. A change to api/ai.go (the context), api/repair.go (the shadow check and redaction), engine/shadow, engine/pii, engine/wdcheck or a connector manifest changes what the suites measure without running them.
  • No suite covers ai steps, masking or prompt injection. Nothing measures what personal data reaches a model, or whether injected text in a goal, trigger or page changes what is proposed.
  • The real-model gate has never been enforced: there is no repository key (needs-people AI1), and no real-baseline.json to compare with.
Spec and code differ

Spec 12.4 asks for "at least 200 real-world automation requests (seeded from dogfooding)" (spec 12.4), and says a model or prompt change ships only if it does not regress. The 308 requests are synthetic, written by engineering and marked as pending review by people. The only gate a change must pass is the offline heuristic, which does not run the model being changed. docs/ai.md still counts 282 builder requests.
