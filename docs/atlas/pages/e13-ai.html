What the AI does here

Taskiem uses a language model in four places: to draft a workflow from a sentence (the builder), to diagnose a failed run and propose a fix (repair), to answer one question inside a running workflow (an ai step), and to route chat messages and moderate public pages. The rule from spec 12 runs through all of them: the AI proposes and people dispose. It can draft, diagnose and answer, but publishing, approving, starting a run and reading a secret stay with people, and every proposal goes through the same checks as a person's work.

The model layer

engine/ai is one small interface in front of every model (decision 0014). A request is system blocks (each can mark the end of a cached prefix), messages, an optional JSON Schema for structured output, a token ceiling and an effort level. Nothing else crosses it:

The deployment picks one with TASKIEM_AI_* (ConfigFromEnv). Without a provider, AI building is off and the canvas is the only way to build. Transient says which failures are worth trying again: a rate limit, a 5xx, a timeout or a broken connection, never a 400 or 401.

The layer turns text into text and holds nothing else. Redacted wraps a provider so every system block and message passes through pii.Redact (emails, phone numbers, BVNs, NINs, card numbers) before it leaves. The builder, repair, chat routing and moderation each wrap their provider themselves, so no caller can forget. AI steps do not use it: they have their own, stronger masking, described below.

Spec and code differ

Spec 12.3 says "tenants with strict residency can require" a self-hosted model (spec 12.3). The provider is chosen per deployment, not per tenant: one process has one provider, and every tenant on it uses it. A tenant that needs residency needs its own deployment.

The builder: from a sentence to a draft

A person with workflow.edit types a goal of up to 4,000 characters on the web (POST /v1/ai/build) or in WhatsApp or Telegram. The API records an ai_builds row, reads the tenant's context, and runs the build in the background with no principal at all (startAIBuild). Builder.Build then does this:

  1. Context. aiContext reads names and shapes only: connections by name and connector, data tables by column names and types (never rows), variables by name (never values), roles by how many people hold them (never who), active policies by a summary, the latest definition of up to 100 workflows, of which the builder keeps only the structure, and the published workflows a subflow step may start (those with a manual or subflow trigger, by name and inputs, leaving out the workflow being changed). Keyword scoring picks up to six connectors whose schemas go into the prompt, and up to two templates from the library as starting points (contextDoc). Connectors are passed as manifests with their handlers removed, so nothing in the pipeline can call a provider.
  2. Draft. The model answers an envelope under structured output: a summary, assumptions, the workflow as a JSON string, up to three test cases, or instead a template id and its parameters. The full wd/v1 schema is in the cached system prompt, because the schema itself is recursive and cannot be a strict output schema.
  3. Validate. The draft goes through the same publishing checks as a person's (injected from the API, s.check), then the builder's policy rule: a money-moving connector or capability step with no approval before it is a finding (PolicyFindingsWith).
  4. Correct. Problems and findings go back to the model, up to three times. The budget is checked before each call.
  5. Dry run. The final draft runs on the real orchestrator with every connector mocked from its output schema, plus the model's own cases.
  6. Review. The proposal holds the definition, the problems that remain, warnings, test results, the new data tables it wants, and what it needs before it can run.

Every model call is written to ai_interactions before its answer is acted on, and a recording failure stops the build. The table is insert-only for the application. Saving is a separate request by a person with workflow.edit: it creates a draft version authored by that person, with the build as co-author in the audit log (saveAIBuildTx). Publishing that draft is the normal publish, with four-eyes counting the saver as the author.

A build that changes a workflow records the digest of the version it started from (ai_builds.base_digest). If someone saved another version before the proposal is saved, the proposal is merged onto the latest three ways, the base version as the common ancestor, as a canvas save naming its parent_digest is (createVersion). Conflicts come back as 409 with the latest version and digest, and the web panel offers the editor's merge dialog; the save is sent again with resolutions (saveAIBuildTx).

Resolved

Saving a build used to write the model's whole definition as the next version with no check that its base was still the latest, so edits saved while the build ran, or before it was saved, were silently undone. The builder's context also had a place for startable workflows that was never filled, so the model was not told which workflows a subflow step could start. Both were found while writing this page.

Risk

Saving from WhatsApp or Telegram sends no resolutions, and a merge conflict there is not one of the errors the chat answers in words: it falls through as an error (waBuildSave), so the person gets no reply that says to finish the save on the web.

Spec and code differ

Spec 12.1 starts from "the canvas, CLI, or WhatsApp" (spec 12.1). The taskiem command has no build command. Telegram, which the spec does not name, has one.

Self-repair: rules, then the model, then the shadow

When a run fails or parks a step, or the drift monitor sees a provider's response change shape, a database trigger queues one repair_jobs row per run and reason, in the transaction that recorded the failure. The failing run waits for nothing. The API works the queue in the background every five seconds, in rounds of one job per tenant, so one tenant's burst of failures does not hold up another's repairs (RepairOnce). A job is skipped when the plan lacks the ai feature, when the tenant turned repair off, or when the run already has an open proposal (decision 0016).

A burst of failures is analysed once. When the model would be needed, a run that failed on the same version at the same step, for the same reason and with the same class from the rules, is covered by the analysis already standing for it; the job is skipped with a detail naming that proposal. The check holds an advisory lock on the failure, so two workers cannot both start the analysis (sameFailure). Analyses that failed, were interrupted, ran out of budget or were superseded do not count.

Resolved

Accepting a repair used to publish the failed run's version plus the fix as the next version, dropping any version published since. Every failed run got its own analysis, so one bad deploy could spend the month's budget hundreds of times; the queue drained one tenant completely before the next; repair ran on plans without AI; and the policy check compared only the number of findings, so a patch that moved an approval from one payment to another passed. All were found while writing this page.

Risk
  • Data from outside can steer a patch. The model reads the failed run's trigger, which for a webhook comes from outside. The prompt says to treat it as data, and a patch must pass the checks, including the policy check step by step, but the checks cover only what the rules know about, and a patch is one person's click from being published when four-eyes is off. The reviewer's reading of the diff is the real gate.
  • Covered runs are not resumed. Only the run whose proposal is accepted resumes as a fork. The other runs its analysis covered were skipped with a note in their job's detail, have no proposal of their own, and stay failed after the fix is published; a person has to rerun or resolve each of them.
  • When the patch is merged onto newer versions, only the proposal's own tests run again on the result, not the shadow run against the recorded history or the workflow's stored tests, and without four-eyes the person accepting saw the diff against the run's version, not the merged one.

AI steps and personal data

An ai step asks the model one question during a run (decision 0050): sort a message, pull fields out of free text, summarise, or draft a reply. It runs on its own ai worker queue, and the worker is the only place a model is called with a run's data (aiEvent). Before anything leaves, the worker:

  1. checks that the deployment has a model, that the business has not turned AI steps off (governance_settings.ai_steps), and that its plan includes the ai feature, through the AISteps.Plan hook the serve command sets from the billing service (AISteps.Plan). A business moved off AI gets a final disabled failure with no model call;
  2. masks the prompt and the input with a Masker: every value the run holds sealed, wherever it appears, in object keys as well as values, and what the detectors recognise, each replaced by a placeholder such as [[name_1]]. The same value always gets the same placeholder, so the model can tell two mentions of one person from two people. Known values of five characters or more are found anywhere in text; those of three or four (a first name such as "Ada", a PIN) only as whole words; one or two characters only when they are the whole value (MinMaskWord). In free text, phone numbers are recognised however they are grouped, by spaces, dashes, dots or a bracketed prefix, and in international form with 8 to 15 digits (detect.go); the builder's redaction uses the same patterns;
  3. leaves as they are only the top-level input fields the step lists in personal_data. Publishing a version with such a step writes ai.personal_data.allow to the audit log, looking inside the callable templates the version pins too (auditAIPersonalData);
  4. refuses a question (the prompt and input together) over 256 KB, the size a step's output may be, with input_too_large;
  5. reserves the tokens the step may use (its question and the longest answer, for both rounds) in ai_reservations, under an advisory lock per tenant, and checks the month's use plus the reservations of steps still calling against the budget, unless the plan bills overage (reserveAI). The reservation is removed when the step is done and lapses if its worker dies.

The answer must match the step's output_schema, which is sent with every object closed. A mismatch is sent back once, and a second fails the step with invalid_output. A refusal or a cut-off answer fails it straight away. A rate limit or provider error is retried under the step's retry policy. The placeholders in the answer, in keys and values, are put back, and the output is sealed because it now holds personal values. Each call is an ai_interactions row against the run and step, counted against the budget (recordAIStep). The row is built from the same masked question that was sent, so it shows what the model saw; only the fields let through are redacted in it. If the row cannot be written, the answer is not used and the attempt fails as retryable. Saving a version with an ai step checks the model, the plan and the switch first, on the definition with its template steps expanded, so an ai step inside a callable template is checked too (aiStepProblems).

Resolved

Several gaps here were found while writing this page. The masker replaced values but never keys, so an input built as {name: balance} sent the name to the model, and the interaction log, redacted afterwards, hid it. Known values under five characters were not masked inside text, and only unbroken Nigerian phone numbers were recognised. The worker did not check the plan, so ai steps went on after a downgrade. A call that could not be recorded was still used, unaudited and uncounted. The budget was read once with nothing reserved, so steps starting together all passed, and the question had no size limit. The limit failure said the step would run again, though it was final. And ai steps inside callable templates escaped the save check and the personal-data audit.

Risk

A call whose record cannot be written is still a call the provider bills. The retry asks the model again, the reservation is released, and the first call's tokens are never counted against the budget, so a database that keeps refusing the insert lets a step spend tokens on every retry (aistep.go).

Spec and code differ

Spec 12.3: "hitting the cap degrades to manual building, never to blocking runs" (spec 12.3), and decision 0014: "Hitting it refuses AI building only." Since decision 0050, a run whose ai step meets a spent budget fails. The decision chose this, but neither the spec nor the budget section of docs/ai.md was updated, and that section still promises runs are never affected.

Chat routing and moderation

In WhatsApp and Telegram, a message in a language other than English that the word lists do not recognise can be routed by the model (waModelIntent). It may answer only one of a fixed set of intents with a short argument (Allowed). Yes, no and cancel are not among them, so the model can name a workflow to run but the person still confirms it, matched by the word lists. Routing needs the plan's ai feature; without it, messages are routed by the word lists alone. A build started in chat is the same build as on the web, and it checks the plan too, answering that the plan lacks AI (waStartBuild).

Storefront moderation asks the model to judge public page text against a written policy after a word list and a price check (ask). Its "allowed" lets text go public, which makes it the one place where a model's answer, not a person's, decides what is shown. The text it judges is written by the business it judges.

Resolved

Chat builds, chat routing, repair and ai steps used to skip the plan's ai feature (FeatureAI), which only the /v1/ai routes and saving checked, so a tenant on a plan without AI could build from WhatsApp or Telegram and get model repairs. Found while writing this page.

Budgets

Each tenant has a monthly budget, ai_monthly_tokens (2,000,000 by default, 0 for no limit), summed from ai_interactions for the UTC month. Every token counts, cache reads included. A plan with AI overage lifts it (aiBudget).

Two uses sit outside that boundary by design. An ai step's answer is data the workflow acts on: if an author wires it into a payment, the model's answer feeds the payment, with only the builder's warning about payments without approval, and the builder's rule 21 telling it never to use an ai step for money. And moderation decides what goes public, above. Neither package is covered by the import test: the step's call is made in engine/runtime, and moderation lives in engine/moderation.

The evaluation suites

tools/aieval runs two suites through the same Builder and Repairer the API runs, with the platform's publishing checks and the compiled-in connectors, every connector mocked:

  • Builder (evals/builder): 308 requests in 17 files, each with the connectors, step types, trigger and properties a good answer must have. Properties are small rules over the definition, such as approval_before_payment, idempotency and no_inline_secrets (rules.go). A model judge is optional. TestNoEvalRequestInPrompts fails if any request, or any eight of its words, appears in a prompt or a template.
  • Repair (evals/repair): 22 recorded failures with the class a person expects, whether the rules should decide alone, and a case a patch must make pass.

Every pull request that touches engine/ai, evals, templates, tools/aieval, api/ai.go, api/repair.go, engine/shadow, engine/pii, engine/wd, engine/wdcheck, engine/expansion or a connector's manifest.yaml runs both suites with the offline heuristic provider against the committed baselines at zero tolerance (ci.yml), and a test keeps that filter covering them (TestCIRunsTheSuitesForTheAILayer). The real model runs nightly when ANTHROPIC_API_KEY is a repository secret, and does nothing without it (ai-eval.yml). The heuristic is not a model: it catches regressions in retrieval, templates, validation, the dry run and the grader, not in what a model does.

Risk
  • No suite covers ai steps, masking or prompt injection. Nothing measures what personal data reaches a model, or whether injected text in a goal, trigger or page changes what is proposed.
  • The real-model gate has never been enforced: there is no repository key (needs-people AI1), and no real-baseline.json to compare with.
Resolved

The CI filter used to cover only engine/ai, evals, templates and tools/aieval, so a change to the context, repair, the checks, masking, shadow runs or a manifest moved what the suites measure without running them. Found while writing this page.

Spec and code differ

Spec 12.4 asks for "at least 200 real-world automation requests (seeded from dogfooding)" (spec 12.4), and says a model or prompt change ships only if it does not regress. The 308 requests are synthetic, written by engineering and marked as pending review by people. The only gate a change must pass is the offline heuristic, which does not run the model being changed. docs/ai.md still counts 282 builder requests.
