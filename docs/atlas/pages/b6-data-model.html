All state is in one PostgreSQL database: definitions, runs, the queue, secrets, the audit log and every product module's records. Ids are UUIDv7, so they sort by creation time, and money is integer kobo with a currency code. Every tenant-owned table carries tenant_id. The counts above are read from the migrations by the build.

Two rules are enforced by the database itself rather than by convention. A trigger refuses any change to a published definition (00003), so only layout and lifecycle fields can change and a new definition means a new version. And run_events and audit_log grant the application only SELECT and INSERT (00004).

Three roles, three ways in

Migrations create the roles as NOLOGIN NOBYPASSRLS (00001, 00176). In production the engine logs in as a user that is a member of taskiem_app only. Every pooled connection then runs SET ROLE taskiem_app (afterConnect), so RLS applies even when a development setup logs in as a superuser. Migrations run separately, as the schema owner.

Tenant scope

Every tenant table's policy compares tenant_id with the transaction's scope:

The scope is a transaction-local setting holding an array of tenant ids, read through taskiem_tenant_scope(). When it is unset, the array is empty and every policy matches nothing, so forgetting to set it fails closed. All Go code enters the database through db.InTenantTx, which sets the scope as the first statement of the transaction and refuses an empty list:

InTenantTxRetry is the same, plus retrying through a failover. It retries a transaction whose COMMIT outcome is unknown only when the caller says the transaction is idempotent, as fenced worker writes are.

Partners and sub-tenants

A partner, a SaaS company embedding Taskiem, never gets its sub-tenants in its own scope. To act inside one, the API calls taskiem_partner_enter. It checks the sub-tenant's parent is the caller, writes the access to both tenants' audit chains, and narrows the scope to that one sub-tenant for the rest of the transaction (decision 0015).

The cross-tenant functions

Some work has to see every tenant: claiming tasks, firing timers, finding a user by email before anyone knows their tenant, routing an inbound WhatsApp message to its business. That work goes through SECURITY DEFINER functions owned by taskiem_dispatch. The dispatch role has policies of its own on the routing tables only, with column-level grants, so even its functions cannot read payloads:

The rule each function follows: claim with SKIP LOCKED, return only routing columns, and let the caller open a normal tenant-scoped transaction to read anything else. Every definer function in the migrations pins search_path, which closes the classic hijack of an unqualified name.

There are of them, not the spec's original four. Grouped by name, the largest families are public pages (about 34), authentication (27), the operator console (25), WhatsApp and Telegram (32), the connector catalogue (14) and partners (11). Each is a doorway past row-level security. Spec 5.3 now describes them as built (spec 5.3).

Risk, partly resolved (findings 3)

What fences these functions now:

  • TestDefinersAllowList pins every definer function taskiem_app may execute to definers.tsv, each with an owner and a reason, and fails when one lacks search_path or is executable by PUBLIC. A new function cannot reach the API without a line there.
  • TestDispatchColumnsAllowList turns the dispatch role's readable columns into an allow-list (dispatch_columns.txt).
  • CODEOWNERS asks the named owner to review any change to those lists.
  • TestEveryTenantTableIsProtected checks every table has RLS enabled and forced, and the public host's test pins what taskiem_public may execute.

Still open: 82 reasons in definers.tsv only repeat their migration's heading; there is no lint against SQL built from strings; and the functions have not been reviewed family by family against the "routing columns only" rule. GitHub never asks a pull request's author to review it, so on the owner's own changes there is no second reviewer.

What the isolation protects against, and what it does not

Row-level security here protects against query mistakes: a missing WHERE tenant_id = …, a join to the wrong table, a list endpoint that forgot a filter. Those return nothing from other tenants, and TestTenantIsolation checks it.

It does not protect against code that sets the wrong scope, or against SQL injection. app.tenant_scope is an ordinary setting that the application role is allowed to change, so a statement running as taskiem_app can name any tenant. The real boundary is therefore InTenantTx and the authentication code that decides which tenant ids to pass it. Those deserve the same review as the definer functions. The scope itself is set with a bound parameter (set_config('app.tenant_scope', $1, true)). Any SQL built from strings elsewhere would be a way around the whole scheme, so string-built SQL deserves a lint rule.

Migrations

Migrations are plain SQL files embedded in the binary and applied by goose with taskiem migrate, as the schema owner (db.migrate). Each file has a Down section, but the CLI only migrates up. Roll back by restoring, or by writing a new migration. CI applies every migration to a fresh database on each push, and the database tests in engine/db/db_test.go check the properties above: append-only tables, immutable versions, distinct sequence numbers under concurrent appends, disjoint claims, fencing, and timers firing once.

Because a SQL function is replaced by a later migration with the same name, the current definition of anything (taskiem_claim_tasks has five) is the one in the highest-numbered migration. Search from the end.

The read replica

With TASKIEM_DATABASE_READ_URL set, run lists and dashboards read from a replica (decision 0024). The replica pool sets the same role and scope, so RLS applies there too. It is never used for anything that decides, leases or writes. When its lag goes past the limit, or it cannot be reached, reads fall back to the primary.
