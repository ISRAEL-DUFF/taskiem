This page is a judgement on the rest of the atlas, written for the people who decide what Taskiem's engineers do next. Every claim below was checked against the code at the commit in the header. Where a sentence is an opinion rather than a fact read from the code, it says so. The detail lives on the pages it links to; this page only collects it and ranks it.

In short: the core is in good shape. The exactly-once machinery, the tenant fences in the database and the public host's isolation are careful and tested. The open work is mostly in three places: things only people can unblock (120 open items, most of them provider answers, accounts and legal), throughput that has never been measured on real hardware, and a long tail of features where the spec promised more than the code does.

Scaling the Postgres queue

Postgres is the queue by design, not by default. A task is inserted in the same transaction as the event that schedules it, so there is no event without its task and no task without its event. No external queue can join that transaction (decision 0002, amendment of 2026-10-28). Workers claim with FOR UPDATE SKIP LOCKED, hold a 60-second lease (worker.go), and write with a fencing epoch. One claimer per queue per process wakes on NOTIFY, ignores other queues' notifications, and polls every second as a fallback (listen.go). The claim is the most complex statement in the engine:

It walks the distinct tenants that have unleased tasks in the queue, one index probe per tenant (a loose index scan over tasks_claimable_tenant). For each, it looks up the tenant's worker pool, counts that tenant's leased tasks against its cap, and takes tasks in turn so no tenant can starve another.

The two results differ by an order of magnitude, and neither is a capacity figure. The spike measures the queue alone, on a quiet host. The cluster ramp measures the whole engine on a machine where other jobs used most of the CPU. performance.md says so itself. The number that matters, on target hardware with a synchronous standby, has never been taken (I1, I2, P4-R5).

What would break first

Ranked by how soon each would bite. The first comes from the measurements. The rest are judgements read from the code.

  1. Commits serialised by NOTIFY. Every inserted task fires pg_notify from a row trigger (00004). Postgres serialises the commits of transactions that have notified, so they cannot share a WAL flush. This is the measured cause of the collapse above 40 runs/s. A faster disk will raise the point where it happens. It will not remove it.
  2. The claim's tenant walk. The ready scan visits every tenant with an unleased task in the queue, including tenants whose only task is waiting for a retry's available_at. Each tenant it visits costs a pool lookup and a count. The claim already took 2 to 3 ms per call with 4 tenants. With thousands of active tenants it will grow roughly in proportion, on every claim.
  3. The run row. Worker, orchestrator and ingest transactions for the same run all lock it with FOR UPDATE. Transaction-id waits were 6 to 25% at the knee. This is expected, but it makes every commit longer.
  4. Retention, one run at a time. The purge no longer has a fixed ceiling: it loops over batches while they come back full, up to a second a tick (purgeRetention), and schedulers split it. It still archives and deletes one run at a time, so its rate is bounded by the archive's latency; taskiem_retention_purge_oldest_overdue_seconds says when that is not enough. Monthly partitions are dropped only when they are completely empty, so a run kept longer than the others started that month keeps the partition. Its rows cannot move to another month without rewriting history, so this is documented rather than changed (operations.md).
  5. Long histories. decide folds a run's full history. An in-memory cache of 2,048 runs per process (decidecache.go) avoids refolding, but a cache miss on a foreach over the default maximum of 10,000 items is still a full read.
  6. Run lists for big tenants. GET /v1/runs without a workflow filter sorts by started_at, and there is no (tenant_id, started_at) index. The only nearby index includes workflow_id (00004).

The next steps, in order

  1. Measure on production-like hardware with a synchronous standby: the cluster ramp, the three failure scenarios, and the pgbench test of the ingest transaction that performance.md left half-built.
  2. Send fewer notifications: notify only when a queue goes from empty to non-empty, or batch wake-ups through one notifier, and poll faster while busy. This needs a short decision. It changes no guarantee, because polling already covers lost notifications.
  3. Done: the purge loops while batches come back full, claims with SKIP LOCKED and a lease so that schedulers split the work, and reports its backlog (resolved below).
  4. Restrict the claim's tenant walk to tenants with tasks that are available now, and add the run-list index (both are migrations built CONCURRENTLY).
  5. After that: a larger primary, dedicated worker pools, and moving big tenants to their own deployments, all of which exist today. Only past that point would dispatch need redesigning (an outbox and a relay), and the 0002 amendment rightly says that would be a decision of its own.

Judgement: the design will carry a launch with tens of design partners on one well-sized primary, once the notify item is dealt with. It has not yet shown it can carry the spec's 500 steps/s with real workloads. Until I1 is done, no one should quote a capacity figure to a customer.

Resolved

The retention purge used to have a fixed ceiling and a single point of failure, found while writing this page. Tick called PurgeExpired with 500 runs every 10 minutes and did not loop when the batch was full, so at most 72,000 runs a day left the database. The claim took no lock, so a second scheduler archived the same runs again. The batch returned on its first error, and the claim was ordered by retain_until, so one run that could not be read or archived came first every time and stopped all purging. No metric showed any of this.

Now purgeRetention claims batches of 25 while they come back full, for up to a second a tick, and carries on next tick until none are left. taskiem_claim_purgeable_runs takes its runs with SKIP LOCKED and leases them for 10 minutes (runs.purge_after), since archiving happens outside the claim's transaction. A run that fails is skipped, counted and logged, and taskiem_purge_run_failed records the error and backs it off from a minute up to a day. The backlog, the oldest run's wait and the failing runs are exported, and TaskiemRetentionPurgeBehind opens a ticket after 6 hours (runbook). Tests: retention_test.go.
