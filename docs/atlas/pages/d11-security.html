What is protected, and against whom

A tenant trusts Taskiem with three kinds of thing: credentials (API keys, OAuth tokens, database passwords), the personal data that passes through its runs (BVNs, account numbers, names), and the ability to call out to the world. The design keeps each of those safe from the other tenants, from someone who gets a copy of the database, and from the tenant's own workflows reaching places they should not. The threat model lists 19 boundaries, B1 to B19, and says what holds at each; a change that adds an entry point, a role, a secret store or a way to run tenant code updates it in the same pull request.

Keys

Nothing secret is stored in the clear. Every value is encrypted under its own key, and keys are wrapped by keys above them:

Tenant key (KEK), versionedEach data key, bound to the tenanttenant_keys, wrapped by the root key

Every read of a secret is recorded with why it was read, a secret_reads row in the same transaction as the decryption: which run, step and attempt, or which person (WithUse). Each hour's reads are hashed into the tenant's audit log, so deleting a read afterwards shows.

Rotating makes a new tenant-key version, and a background job re-wraps the data keys under it, 500 at a time; values themselves are never re-encrypted. Old versions are destroyed a day after nothing uses them.

Spec and code differ

The spec puts the root key "in an HSM or KMS" (spec 14.1). The choices are OpenBao, or a key in the process's environment, which is the default (TASKIEM_KMS=local). A cloud KMS is supported only for a tenant's own key. A production install should set TASKIEM_KMS=openbao.

Bringing your own key

A tenant can add its own key, so that revoking it in its own KMS makes its data unreadable to Taskiem (EnableBYOK). Taskiem first proves it can wrap and unwrap with the key, then wraps a new tenant-key version twice, by the root key and then by the tenant's, so the tenant's KMS only ever sees ciphertext. Every minute a job asks the tenant's KMS to unwrap a test value. After two failures in a row the key is marked unavailable: the API answers 503 key_unavailable, and steps that need a secret are parked before anything is sent, then resume by themselves when the key comes back.

Risk

Revocation is not instant. Unwrapped tenant keys are cached in memory for 5 minutes by default (up to an hour) in every process, so a revoked key keeps working that long. Versions made before BYOK was turned on stay readable without the tenant's key until the re-wrap finishes, and a database backup taken before then stays readable without it until the backup expires. The BYOK guide says so.

Personal data

A field marked as personal, in the workflow's inputs or in a connector's manifest, is sealed before an event is written. Each person, a subject, gets their own key, and the subject's id is a keyed hash of the value, so the same BVN always has the same subject and the same key (SealTx). sealPayload seals declared fields, then any copy of a known value it finds elsewhere in the payload, then values it recognises by shape: emails, Nigerian phone numbers, BVNs and NINs, card numbers, and account numbers beside a bank code. If a connector's personal fields cannot be known, the event is not written at all.

Erasing a person destroys their key (Erase). Every sealed copy, in events, archives and backups, then reads as [erased]. A trigger in the database makes this one-way, and the application cannot delete the key rows.

Risk: worth fixing
  • A value built from personal data is stored in the clear. A step whose output is 'ref-' + bvn or 'Dear ' + name writes ref-22298765432 and Dear Adaeze Okafor to the run's history unsealed, while a plain copy of the BVN is sealed. Checked by running it and reading the stored event. Sealing finds copies only by exact match, so erasure cannot reach these. Sealing any string that contains a known value would close most of it.
  • An erased person cannot be processed again. Their subject's key is gone, so a new run with the same BVN fails with "subject erased". That may be intended, but nothing documents it, and a customer who leaves and later returns would need a way back.
  • Erasure needs no second proof. It is irreversible, yet needs only pii.erase, while changing an encryption key needs a passkey or code.
  • The spec says erasure "is never applied under a running workflow" (spec 9.4). Nothing checks for runs in flight; a waiting run sees [erased] when it resumes.
  • Log lines are masked for emails, phones, BVNs, NINs and cards, but not names or account numbers, and not secret values. Keeping secrets out of logs depends on code not logging them.

Outbound traffic

Every call out of Taskiem made for a tenant goes through egress.Guard: connector calls, HTTP steps, code steps' fetch, alerts, partner webhooks, and calls to a tenant's KMS. A connector may reach only its manifest's hosts, and an HTTP step only its environment's allow-list. The guard resolves the name once, refuses if any address is private, loopback, link-local, a cloud metadata address, or one of the IPv6 forms that hide an IPv4 address, and then dials the address it checked, not the name, so a second DNS answer cannot redirect it. Redirects are followed at most five times, each checked the same way, and proxies from the environment are ignored.

Where a network requires an explicit proxy, Taskiem connects through it by IP address with CONNECT, never by name, so the proxy cannot resolve the name differently (decision 0028). Each connection is logged with the tenant, purpose, host, address and port.

Spec and code differ

The spec's egress "logs every request" (spec 14.2). It logs every connection, so several requests over one kept-alive connection log once. Some platform calls do not go through the guard, by design: the OpenBao client, billing, Git, and a self-hosted model. A few IPv6 forms are not on the list (::ffff:0:0/96 and two new documentation ranges); reaching anything through them needs a translation path a normal Linux host does not have.

The HTTP surface

httpsec.Set gives every API and edge response nosniff, no-referrer, X-Frame-Options: DENY and a content security policy that allows nothing but the app's own origin and refuses framing. Embedded frames get a policy naming the partner's allowed origins, and public pages a stricter one with no inline script or style. HSTS is a year, sent when the public URL is HTTPS.

Rate limits are token buckets in each API process: sign-in, password reset and re-authentication at a burst of 10 and then one every 6 seconds, per IP and per email; passkey challenges and SSO starts at a burst of 30; and ingest per tenant by plan (Triggers and channels).

Spec and code differ

The spec has "Rate limits per IP, user, API key, and tenant" (spec 14.3). Limits exist on the endpoints above, but there is no general limit per API key or per tenant on the rest of /v1, and every limit is per process, so several API replicas allow several times the rate. The app's policy also allows inline styles.

Secrets in outputs

A step's output, logs and error are scrubbed of every secret the step could read before they are written (scrubSecrets). The Sandbox page covers what it catches and what it does not.

Self-review

Security is reviewed in rounds, recorded in self-review.md. Four reviewers each take one area: sign-in and sessions; tenancy and authorisation; untrusted input, egress and sandboxes; secrets, personal data and audit. Findings are numbered by round (S1 to S35, then K1 to K8 for BYOK, then R1 to R10), each with a severity, a status and, when fixed, the regression test that proves it. What a round leaves open is carried to the next. Two are open now: R7, undeploying without a second person, and R9. The repository has no secret scanner such as gitleaks; the linter's security rules and signed, SBOM-listed images in CI are what exist.
