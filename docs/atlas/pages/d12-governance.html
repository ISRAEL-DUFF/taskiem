What governance means here

A lender or a payroll company has to show a regulator, and itself, that money moved only when the right people agreed, that nobody approved their own work, and that the record of it cannot be quietly changed. Taskiem builds that into the engine rather than leaving it to each workflow: approvals follow policies, separation of duties is checked in the database transaction that records a decision, and every privileged action goes into a hash chain that is signed outside the database.

Approval policies

An approval step names a policy, a versioned object a tenant keeps apart from its workflows (engine/policy). A policy is a list of rules; the first whose condition matches the approval's subject decides how many levels of approval it needs, from which roles, and whether each approver must step up:

Amount thresholds are just conditions, such as =subject.amount_kobo >= 50000000. Each run keeps the policy versions that were active when it started (policySnapshots), so editing a policy never changes an approval already waiting. A subject that matches no rule fails the step rather than letting it through.

An approval can time out. On timeout it is rejected, fails, or escalates once to another role with a fresh deadline (approvalProgress). There is no default timeout: without one, an approval waits as long as the run may.

Separation of duties

VoteApproval checks a vote in one transaction, with the run locked, in this order:

  1. The voter holds the level's role, or acts under a delegation from someone who still holds it. An owner holds every role. Delegations last at most 90 days, and owner and admin cannot be delegated.
  2. The voter is not a maker: not whoever started the run, wrote the version or published it, each traced through an API key to the person behind it, and not acting for one. A policy can allow a business with one person to approve its own work; such a decision is recorded as self-approved.
  3. One vote per person per level, and nobody who approved an earlier level approves a later one.
  4. The step-up the rule asks for, last.

The final approval continues the run in the same transaction. API keys never vote. The same rule, that whoever asks does not decide, holds elsewhere:

WhereRule
Publishing, when four-eyes is on for the environmentA person other than the requester and the version's author (governance.go)
Promoting into a gated environmentNot the version's author, nor whoever deployed it to the source
A new approval policy version, when four-eyes covers policiesNot its author, and not an API key
Connecting Git to a governed environmentA second person
Catalogue reviewA reviewer outside the publisher's tenant
School cash and discount requestsNever the person who asked, with no single-person exception

The vote's audit entry is written in the vote's own transaction (Vote.Audit): a vote that cannot be recorded in the chain is not counted. Nobody who approved one level of a step approves another, including after an escalation reopens the step. The built-in withdrawal policy forbids the person who asked from approving while another owner can.

Resolved

Three gaps were found while writing this page and are fixed:

  • The audit entry used to follow the vote in a second transaction, and one WhatsApp path dropped its error.
  • After an escalation, the distinct-approver check did not run.
  • The withdrawal policy allowed self-approval.
Risk

Separation compares accounts, so one person with two accounts in a tenant can make with one and approve with the other. Operator writes need one person (with a passkey). A tenant whose withdrawal policy was written before this change keeps the old one until its withdrawal settings are next saved.

Spec and code differ

Spec 9.1 says rotating secrets "can each require approval" like publishing and policies (spec 9.1); there is no four-eyes setting for secrets. A policy's channels list is parsed and then ignored.

The audit log

Every privileged action appends an entry to its tenant's chain: who, as what kind of actor, did what to what, with details that never hold raw personal data. Each entry's hash is the SHA-256 of the previous hash and the entry in a canonical form, so changing, inserting or removing any entry breaks every hash after it. The application cannot write to the table directly. It calls a function that checks the caller's tenant, locks the chain's head and links the new entry:

A chain that only the database checks proves little against someone who controls the database. So once a day, for each tenant whose chain moved, the scheduler recomputes the chain from the last anchor, signs the head with Ed25519, and writes it to a directory outside the database before recording it inside (anchor.go). A tenant can also have each anchor emailed to them. taskiem audit verify checks an export offline against those anchors with the public key, and names the first entry that differs, if any.

Risk
  • Anchoring is off unless TASKIEM_ANCHOR_KEY and TASKIEM_ANCHOR_DIR are both set, with only a warning in the log. Without it the chain is checked only by the database it lives in.
  • Between anchors, up to about a day, someone with write access to the database can rewrite recent entries and recompute their hashes. That is inherent in daily anchoring; anchoring more often narrows it.
  • Offline verification checks signatures only when given --key, and the documented recipe takes that key from the same API it is verifying. It does not check that the anchors belong to the export's tenant.
  • The chain proves that entries were not changed, not who acted: the actor is whatever the application passes.
Spec and code differ

The spec stores anchors "in write-once object storage" (spec 9.2). They go to a local directory, which is write-once only if it is mounted that way. Export to a SIEM is not built.

Retention and erasure

A run is kept for its workflow's retention, else the tenant's default, else 90 days, counted from when it ends and capped by the plan. Every 10 minutes, and until none are left, the scheduler archives the runs past their date and then deletes them, writing run.purge to the chain (PurgeExpired). The audit log is never deleted. Erasing a person is covered on the Security page.

Each decision is also written, with the vote, to approval_history, which is never purged. It records who decided, for whom, the level, step-up, channel, policy and amount, but not the approval's subject, which can hold personal data and goes with the run. The approvals report reads it. A workflow's settings.retention must be at least a day.

Resolved

The purge used to take the approval evidence with the run, so the report forgot who approved what after 90 days. And a retention of minutes was accepted.

Risk

Without an archive configured, nothing is purged and personal data stays in the database for good (still erasable).

Spec and code differ

The spec keeps the audit log for a "minimum 7 years, configurable" (spec 9.4). There is no setting: it is kept for ever.

Suspended tenants

A partner can suspend its own sub-tenant, which also revokes its sessions (partner.go). Suspension stops new work everywhere:

  • sign-in, sessions and API keys stop resolving;
  • webhooks get 423, so providers deliver again later;
  • starting a run is refused;
  • schedules are not fired, and the ones missed are skipped on resume.

Runs already under way carry on to their end, including their payments, as the governance guide says: stopping one halfway would be worse.

A Taskiem operator can suspend or resume any tenant from the operator console, with a reason and a passkey for that tenant, recorded in both audit chains (opsTenantAction).

Resolved

Suspending a tenant other than a partner's sub-tenant used to mean an SQL update by hand, with no audit.

Compliance reports

GET /v1/reports/{kind} gives anyone with audit.read six reports, as JSON or CSV, over the last three months by default (reports.go):

  • approvals, by amount band;
  • effects: writes that needed a person or a provider check, parked or settled by reconciliation;
  • pii: reveals and erasures;
  • changes: every workflow version, who wrote and published it, its commit, and what changed;
  • chain: the audit chain verified, and each anchor checked against it;
  • secret-use: who read which secret, and why.

Viewing a report is itself audited, and CSV cells that a spreadsheet would run as formulas are written as text. Nothing maps these to SOC 2, ISO 27001 or the NDPA yet; the compliance guide lists that as work for people.
