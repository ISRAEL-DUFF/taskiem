What a connector is

A connector is how a workflow talks to a provider: Paystack, a bank, WhatsApp, Zoho, a database. It has two parts. The manifest is YAML that says what the connector can do: its actions, each action's class and idempotency key, the hosts it may reach, how a connection authenticates, and the webhooks it receives. The handlers are the code that does it. The engine reads only the manifest to decide how to retry, what to reconcile and where traffic may go. The handlers never decide that.

The manifest

Parse checks a manifest in two layers and returns every problem, not just the first. The JSON Schema (connector-v1.schema.json) checks shape, and requires a class on every action, an idempotency key on every idempotent write and a reconcile action on every reconcilable one. Then check applies the rules that span fields: a reconcile action must be a read, a compensating action must be a write, a read cannot compensate, and every personal-data path must exist in the action's input or output schema.

This is Paystack's transfer. The class decides retries, the idempotency block says how the engine's key fits Paystack's reference field, and reconcile names the read that can find out after a crash whether a transfer happened:

The key itself is a SHA-256 of the tenant, the seed, the step and the attempt group, cut to the length the manifest asks for. Spec.Validate refuses an encoding that would leave less than 128 bits, or a prefix and length that do not fit the provider's limits. The Exactly-once effects page covers what the engine does with the class and the key.

Where traffic may go

HostsFor gives the hosts a call may reach: egress_hosts, or the base URL's host, plus each mode's host. A host can come from the connection, as ${connection.api_domain} does for Zoho's data centres. Such a host is checked against connection_hosts, and a connector that lists none allows any (ConnectionHostAllowed). Whatever the list says, the egress guard still refuses private, loopback and metadata addresses.

Handlers and the registry

A handler is one method:

The Request carries the input with the key already in its field, the connection's credentials decrypted for this call only, an HTTP client and a TCP dialer that both go through the egress guard, and a way to refresh an OAuth token under a lock. A handler reports failure with one of the sentinels in effects: retryable, fatal, unknown outcome, not sent, or indeterminate. Most use DoJSON, which maps a failed DNS lookup or refused connection to not sent, 429 and 503 to retryable, any other 5xx to unknown outcome, and other 4xx to fatal.

Each built-in package embeds its manifest, parses it with MustParse and returns a Connector with one handler per action. builtin.Register registers the list at start-up:

Check fails start-up if a manifest action has no handler or a handler has no action. For each call, Registry.For adds the tenant's own and installed connectors to the built-ins. Because of the prefixes, a tenant's connector can never stand in for a built-in.

Spec and code differ
  • Rate limits. The spec says they "are enforced by a token bucket per connection, shared across all workers via Postgres" (spec 6.2). Manifests declare rate_limit, Paystack's at 50 a second, but the engine does not read the field, and nothing enforces it. A provider's 429 is the only brake, handled as retryable with Retry-After.
  • Version pinning. The spec says each run "executes every step on" the connector versions recorded in RunStarted (spec 6.4). The versions are recorded (Pins), but nothing reads them back. The worker looks up id@major at call time and gets the newest version. A run that is waiting while a new minor version is uploaded or deployed carries on with the new one.
  • Out of process. The spec says third-party connectors "run out of process as WASM modules". They run in the worker's process, in wazero, with a fresh instance per call.

WebAssembly connectors

A tenant, or a catalogue publisher, writes a connector in any language that compiles to WebAssembly. With Go and connectorsdk it is a manifest, Handle("action", fn) per action, and GOOS=wasip1. The ABI is taskiem-connector/v1 (contract). The module exports taskiem_execute_v1 and may import four host functions and nothing else outside WASI:

Execute passes the action, input, credentials and key as JSON. Each call gets a fresh instance with 128 MB of memory, 20 HTTP calls, 4 MB per response and 1 MB of output (defaults). HTTP goes through the worker's guarded client, so the manifest's hosts and the address checks apply exactly as for Go. The host also records whether anything was sent. A module that says "not sent" after the host sent a request is overruled to unknown outcome, so a buggy module cannot make the engine retry a write unsafely:

A tenant uploads to POST /v1/tenant-connectors (tenantconnectors.go). The upload is parsed, the id must start x_, every trigger must verify its deliveries, and the module must compile with only the allowed imports. It is stored with its digest and audited. Workers see it within 10 seconds (Source.Connectors).

Risk

A tenant's upload gets none of the checks a catalogue package gets: no strict lint, no conformance run, no semantic-version check, and none of the memory checks in Inspect. A tenant can therefore label a write as a read, which the engine will retry freely, or allow a wildcard host such as *.com, which only the catalogue refuses. Address checks still stop calls to private networks, and the harm stays within the tenant's own data and credentials. It is worth a lint pass on upload, with findings as warnings, so tenants see the problem before a payment goes out twice.

Conformance suites

A connector's tests are recorded exchanges with the provider. conntest reads testdata/fixtures (a request and its response) and testdata/conformance (an action, an input and the output or error expected). Run serves the exchanges from a local server, in order, and refuses any other host. As well as pass or fail, it reports three things a reviewer needs: actions no case calls, idempotent writes whose key never reached the provider, and reads that sent something other than GET or HEAD. Ten built-ins have conformance suites. Paystack and others test with fixtures and capability cases instead.

The public catalogue

A publisher ships a package: the manifest, the module, a licence, a source URL, its conformance suite, and an attestation that it is original work. The package is signed with the publisher's Ed25519 key over its format, id, version and digest (connpkg). On submission, Checker.Run checks, within three minutes:

  1. The signature.
  2. A strict lint (Lint): HTTPS only, no IPs, private names or wildcards, a read must not be named like a write, and personal fields must be declared.
  3. The module loads and stays within its memory.
  4. The licence is on the allow-list, and the attestation is given.
  5. Every host resolves to public addresses only.
  6. The version follows semantic versioning against the versions already published.
  7. Every case passes, every action is covered, and every write's key reaches the provider.

A package that passes waits for a reviewer, who must not belong to the publisher, must tick every item on the checklist, and must leave a note (taskiem_catalogue_review). Installing it asks the tenant to consent to its hosts and writes, and an upgrade asks again when those grow (Compare). A revoked version stops resolving within 10 seconds, and every tenant that installed it is told.

Drift

After every successful call the worker compares the output with the action's output schema (drift.Check). A wrong type, an enum value not listed or a missing required field is recorded in connector_drift, counted in a metric, raised as an alert, and offered to AI repair as a cause. The step still completes, because the output is what the provider said. The check is shallow on purpose: it ignores oneOf, formats, ranges and extra fields, and stops at 20 findings.

Two connectors, end to end

Paystack, a payment rail

The manifest takes a secret key, accepts sk_live_ and sk_test_ as the two modes, refuses a public key, and tests a new connection by checking the balance. Its webhooks are verified with HMAC-SHA512 over the body, and are polled every five minutes too, so a missed delivery is caught. The handler for transfer sends the engine's key as the reference. Zoho Books, a SaaS product

Zoho Books connects with OAuth through Taskiem's own Zoho app. The connection records the customer's data centre, and only Zoho's own data-centre hosts are accepted for it. Books has no idempotency key. Its writes are classed idempotent_write and made safe by looking first: creating a contact searches by email, phone and name, and returns the match if there is one.

Risk

Look-then-create is safe only if a contact created a moment ago can already be found. If Zoho's search lags behind a create that succeeded but timed out, the retry can create a second contact. A match on display name alone can also pick up an unrelated contact with the same name. Neither was reproduced. Zoho's conformance test deliberately skips the "key reached the provider" check, since there is no key to send.
