What it is

The web app in web/ is everything a person sees of Taskiem in a browser: the console a business works in (workflows and their builder, activity and the run inspector, approvals, money, storefront, schools, settings), the operator console at /ops, and a second bundle that partners put on their own pages to give their customers a builder. It is one React app, about 60,000 lines of TypeScript, with no server of its own. The Go binary serves the built files, and every piece of data comes from the same REST API that the CLI and the SDK use.

The entry point picks one of two apps by path, before React mounts anything. The operator console has its own session cookie and its own client (opsApi), and it never mounts the tenant console's providers:

Inside the console, routing is react-router-dom 7 with a BrowserRouter. Shell decides what a person may see before any route is matched. While /v1/me is loading it shows a skeleton. Signed out, every path but signup and password recovery goes to /login?next=…. Someone with only invitations, an administrator who must still enrol a passkey, and a school gate account each get one screen whatever the address. A field agent lands on the agent app, and while they work in a business the pages render inside that business's session. Everyone else gets SignedIn: the sidebar, filtered by permission, and about 70 routes in one <Routes>. A workflow's own page switches the shell to builder mode, which shrinks the menu to a rail of icons.

Pages are imported eagerly; only the operator console is a lazy chunk. The page container is keyed by the path and a refresh counter, so pull-to-refresh in the installed app redraws the page and every page fetches its data again.

Framework and build

React 19, TypeScript 6 in strict mode with noUncheckedIndexedAccess, Vite 8, and React Flow (@xyflow/react 12) for the canvases (package.json). There is no state library, no CSS framework and no component kit. Styles are one stylesheet of CSS variables, styles.css, and the rules for using them are in Building screens in Taskiem's look. Types for workflow definitions come from the SDK through a path alias, @sdk/wd, so the console and the SDK share one wd/v1 type.

pnpm --filter @taskiem/web build type-checks, then makes two builds. The console goes to dist/. The embed bundle is a library build of src/embed/index.tsx into one classic script with its styles inlined:

taskiem serve serves dist/ from TASKIEM_WEB_DIR through SPA: a path that is not a file gets index.html with no-cache, so client routes survive a reload; hashed assets are cached for a year; /v1/ and /hooks/ never fall through to the app. Every response carries the console's Content-Security-Policy, which allows scripts only from the console's own origin and no inline script (httpsec.CSP). In development, Vite proxies /v1 and /hooks to :8080 so the session cookie stays same-origin.

State

State lives in components. Three small pieces are shared:

  • AuthProvider holds the result of /v1/me: roles, permissions, the Advanced switch, and flags such as gate_only. can(perm) reads the permission list. Inside a field agent's session, AgentPermissions replaces can with what the agent may do in that business.
  • useLoad fetches on mount and when its dependencies change, ignores an answer that arrives after unmount, and, with poll, fetches again every 2 seconds. Every page loads its data with it. useAction runs a button's work with a busy flag, an error and a toast.
  • The agent's business session is module state in api.ts, kept in sessionStorage for the tab and read with useSyncExternalStore.

Nothing secret is kept in browser storage. localStorage holds the theme, the brand, whether More is open in the menu, and which consent screens a field agent has seen. sessionStorage holds the agent session's id and kind, the page to return to after an OAuth connection, and a gate's recent checks. Tokens that arrive in links (password reset, signup, invitation, operator enrolment, a WhatsApp step-up hand-off) are read from the URL fragment, which the browser does not send, and all but the hand-off are then removed from the address bar.

Talking to the API

Every call goes through one function. It sends the session cookie (credentials: "same-origin"), always adds X-Taskiem-Request: 1, adds the agent header when the agent is working in a business, and turns an answer that is not 2xx into an ApiError carrying the status, the message, the validator's problems and the whole body:

A request the browser could not send at all becomes status 0 with a plain offline message. A 401 outside /v1/auth/ fires taskiem:unauthorised; the auth provider sets the person to signed out and the shell sends them to the login page. Pages show errors with ErrorBox, and the validator's problems with ProblemLine, which links each to the step that needs fixing. Creating and sending invoices use postOnce, which sends an Idempotency-Key so a retry makes nothing twice.

The session is an HttpOnly cookie, SameSite=Lax (setSessionCookie). A browser's sign-in gets the cookie and no token in the body, which decision 0026 settled. The CSRF defence is the header: the API refuses any request authenticated by the cookie that is not a GET or HEAD and lacks it. A cross-site form cannot set a header, and a cross-site fetch with one needs a preflight the API does not grant. Sign-in itself takes only application/json (jsonOnly), which a cross-site form cannot send either.

Hiding what a person may not do is only for the screen. can() filters the menu and turns off buttons, but each route checks the same permission on the server, for example s.need(PermWorkflowEdit) on saving a version and s.need(PermWorkflowPublish) on publishing (server.go).

The builder and how it edits wd/v1

The builder (Editor) loads the workflow, the version in ?v= (else the latest), the connector catalogue and the capabilities, and keeps the definition being edited in component state with a dirty flag. Its tabs are Build, Runs and Settings, and with Advanced on, Code (the workflow as SDK TypeScript, compiled by the API) and JSON.

The canvas model is lib/flow.ts: pure functions over the definition, unit-tested without a browser. A step inside a container is addressed by the list it is in:

flowGraph turns the definition into cards and arrows at every depth, with a place for the first step of an empty path and for what follows a container. Positions saved in the layout win, and the rest are placed in columns by the longest path from the trigger. Every edit the canvas makes is one function that returns new steps:

EditWhat it does to the definition
insertStepAdds a step after one, before one, or between two, rewriting needs so the chain stays joined, and places it next to its neighbour in the list
removeAnywhereRemoves a step and what it holds; the steps that needed it now need what it needed
connectInAdds "target needs source" only within one list, and refuses a loop
renameAnywhereRenames a step and the needs in its list. Expressions that name it are not rewritten; the validator reports them
forSavingBefore saving, drops a choice's empty "otherwise", since wd/v1 lists hold at least one step

New step ids come from the picker's base word, unique across every depth (idFrom). Undo and redo keep the last 50 definitions with their layouts.

Every save is a new immutable version. The builder sends the digest of the version it started from, and when someone saved since, the API merges the two edits three ways; units both changed come back as a 409 with the conflicts, and the merge dialog asks which side to keep:

On the server, createVersion locks the workflow, refuses one Git manages, merges with wdmerge and stores the result; it answers with the validator's problems but saves the draft whatever they are. Publishing validates. Moving cards does not make a version: the layout is PUT on the current version 600 ms after a drag, and only while there are no unsaved edits, as spec 3.5 asks (spec 3.5). Publishing saves first, then publishes; a version that is not ready comes back as a list of needs, each with its fix, and with four-eyes on it waits for a second person.

Risk
  • The JSON tab applies any valid JSON object as the definition on every keystroke (Editor.tsx). Delete the steps key, or paste a definition with a typo in it, and the next render calls placed(undefined) and throws. The app has no error boundary, so the whole console goes blank and the unsaved edits are lost. The API accepts any JSON as a draft (canonical only compacts it), so a draft saved through the API with no steps blanks the builder for everyone who opens that workflow.
  • A step's "Edit this step as JSON" replaces the step whole (StepPanel.tsx). Typing in its id renames the step on the first keystroke, with no check that the id is free and without rewriting the needs that point at it; the window closes because the step it shows no longer exists, and the steps after it lose their arrows. The validator stops it being published, but the draft is broken.
  • Nothing asks before leaving the builder with unsaved changes: not closing the tab, not the back link or the menu, and not a 401, which signs the person out and drops the edits. The storefront pages do ask (beforeunload); the builder does not.

The run inspector

RunPage reads a run's whole history once from GET /v1/runs/{id}, then, while the run is not finished, streams the events recorded after the last one it has, by server-sent events, and fetches the run again when the stream ends:

timeline folds the events into one row per step instance (pay_all[2].pay_employee): status, attempts, input, output, logs, error, and what a waiting step waits for. The page shows those rows as cards or on the run canvas, with each step's plain-words error, the secrets and connections it decrypted (for audit.read), the form answers that started it, and the run's forks and subflows. Sealed personal data is shown as 🔒 by redact; the values are not in the browser unless revealed. Cancel (with or without reversing what the run did) and resolving a parked step are posts to the run, behind run.cancel and run.resolve.

Ticking "Reveal personal data" (pii.reveal) refetches with ?reveal=true. The stream is sealed, so a revealed live run is polled instead, every 2 seconds:

Risk

Each revealed fetch writes a pii.reveal entry to the audit chain (getRun). A revealed run that is waiting, for an approval or a form, does not end, so a tab left open writes 1,800 entries an hour until it is closed. That fills the chain and makes the pii report, which is meant to show who looked at personal data, unreadable. Reveal once, or stream revealed events, and audit the reveal once per page.

Forms and the builder

A step's settings are drawn from what its connector declares. SchemaForm turns an action's input JSON Schema into fields: text, numbers, booleans, enums and nested objects, each of which can also take an =… expression or a value picked from an earlier step. A schema without properties falls back to a JSON box. What a step can pick from is worked out at every depth, the steps before it in its own list and in each list it sits inside (earlierAnywhere), with samples once the draft has been tested. "Test workflow" posts the draft to /v1/workflows/{id}/try, which runs it with sample data and sends nothing; outputs can be kept for the next test.

A step opens in StepWindow, full screen: what came in, its settings (StepPanel), and what came out. Form triggers and form steps get FormEditor: fields with their personal-data categories, pages, and a live preview drawn by FormView, the same component members fill forms in with at /forms/:id and /forms/requests. Public forms are not this app; the public host serves them.

Nowhere does the app put markup from data into the page: there is no dangerouslySetInnerHTML, innerHTML or markdown renderer anywhere in web/src, so run outputs, connector schemas and form answers are always text. Links taken from data (a Git pull request, a provider's confirmation link, a notification) go through React 19, which blocks javascript: URLs.

The embed bundle

/embed/v1/taskiem.js defines three custom elements (embed/index.tsx). <taskiem-builder> and <taskiem-runs> run on the partner's page. <taskiem-frame> is the root of the frame page, for partners who prefer an iframe. Each renders into its own shadow root with the console's stylesheet scoped to :host, so neither page's styles reach the other. The partner's colours, font, radius and logo become CSS variables only after parseBranding has checked each against a pattern, so branding cannot inject CSS.

The bundle has its own client, EmbedClient. It calls only /v1/embed/{app}/… on the origin the script came from, sends the end user's token as a bearer header with credentials: "omit", so the console's cookie never goes with it, and streams runs with fetch, because EventSource cannot send a header. It warns the host page a minute before the token expires; only the partner's server can mint the next one, which the page hands over with setToken.

In iframe mode the token travels by postMessage, never in the URL. The frame announces itself to the parent, and accepts a token only from its parent window, only from one of the app's origins, and once it has one, only from that origin. It posts back only to that origin, never to "*":

The server holds the other half. embedFrame serves the frame page with frame-ancestors set to the app's origins, excluding Taskiem's own, and a policy that keeps scripts and API calls on its own origin (FrameCSP). Every other page sends frame-ancestors 'none'. embedCORS answers CORS only for the app's exact origins, without credentials. embedAuth requires a token whose audience is the app in the path, from an allowed origin and the token's bound origin if it has one; a request without an Origin is accepted only for a headless app. From the frame page, which runs on Taskiem's origin, the origin that counts is the partner page named in X-Taskiem-Embed-Parent (embedOrigin). Definitions an end user saves or validates go through embedGuardBody, which refuses connectors, step types and templates the app does not allow (embed.Uses); publishing and starting a run check the stored version again.

The embedded builder is not the console's builder. It draws top-level steps only, with lib/graph.ts, the model the console used before flow.ts, has a palette of step types instead of the picker, and edits nested steps as JSON in their parent's panel. The run view and the run canvas are shared with the console.

Risk
  • The save guard reads the body into a map and checks the key "definition" (embed.go), but the handler decodes it with encoding/json, which matches field names without regard to case (decodeBody). An end user who sends "Definition" skips the check, and a draft with http, code or ai steps or connectors the app does not allow is stored in the sub-tenant. Publishing and running through the embed API check the stored version again, so the end user cannot run it there; but the draft is in the partner's customer's workspace, where its own members can publish it. Decode the guard's view with the handler's own struct, or refuse keys that match only without case.
  • In the embedded builder, renaming a step checks only top-level ids (EmbedApp.tsx), so a step can take the id of one nested in a container. Its save sends parent_digest but has no merge dialog: a 409 shows as an error and the end user cannot keep their edit except by redoing it on a reload.
Spec and code differ

Decision 0015 and the partner guide say every definition an end user saves is checked against the app. The case-variant key above is saved unchecked.

Where the documents have moved on

Spec and code differ
  • The web app's README says the canvas shows top-level steps and that there is no live run view. The console's canvas shows steps at every depth, and the inspector streams a running run. Its list of limits describes the embedded builder.
  • Spec 15.1's live view lights steps "on the canvas as a run executes" (spec 15.1). The run canvas draws only top-level steps (RunCanvas); a container's card takes the state of what it holds, and the steps inside are seen only on the timeline.
  • Spec 15.1's search finds runs "by correlation key, status, date, or a redacted field value" (spec 15.1). Activity filters by status, workflow, environment and the end of a date range on the server; the start of the range and its search box work on the runs already loaded, 50 at a time, and the search matches workflow, run id and who started it. There is no search by correlation key or field value.
