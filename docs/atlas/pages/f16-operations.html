One binary, several shapes

Taskiem ships as one Go binary in a distroless image that runs as uid 65532 (Dockerfile). taskiem serve --role R picks what a process does, from roles: api, edge, orchestrator, scheduler, worker, public, mail, or all. Each role is a list of tasks run side by side by runTasks. If one task fails, the process stops and its supervisor restarts it. Every role also serves /metrics, /healthz and /readyz on the metrics port, 9090.

Resolved

The chart used to read one Secret whose TASKIEM_DATABASE_URL, the schema owner's, served both the migrate Job and every pod, so anyone who read a pod's environment had a login that could RESET ROLE past row-level security and the append-only audit tables. The owner's URL now lives in a second Secret, migrations.existingSecret, that only the migrate Job reads. The Job passes the pods' URL to taskiem migrate as TASKIEM_APP_DATABASE_URL, and EnsureAppLogin creates that login as a member of taskiem_app, as the VM kit does for its <db>_app, refusing the owner, a superuser or a login that owns tables (database logins). A test reads the rendered manifests and fails if any pod can reach the owner's Secret (TestPodsNeverGetTheOwnersLogin). Found while writing this page.

The dev Compose file used to publish Postgres (password postgres) and metrics on every interface, which Docker's published ports open past a host firewall such as ufw, and set no stop_grace_period, so Docker killed the process after 10 seconds while workers drained for 30. Both are now on 127.0.0.1, with a 45-second grace period (TestDevComposeStaysLocal).

For api, edge and all, the chart's service.type used to apply to the metrics port too, so LoadBalancer made /metrics public, and /debug/pprof with it when TASKIEM_PPROF was on, which pprof.go says must never be exposed. Those roles' metrics are now on a separate Service that is always ClusterIP, which the ServiceMonitor finds by its port name as before (TestMetricsStayInsideTheCluster).

Spec and code differ

Spec 2.3 says schedulers are leader-elected with a session-level advisory lock (spec 2.3). Nothing in the code takes such a lock. Each scheduler job relies on its own row claims, and every scheduler runs the canary.

Resolved

The chart's values and the stalled-scheduler runbook used to say a second scheduler was safe. With the default storage it was not: the scheduler mounts a ReadWriteOnce claim under a Recreate strategy, which a second replica on another node cannot attach, and one on the same node would share a local archive directory that archiver warns against. The scheduler's database work is safe to run twice, so the values, the runbook and kubernetes.md now say a second scheduler needs the S3 archive and no volume, which leaves it without audit anchoring, and the chart refuses anything else (taskiem.schedulerReplicas, TestChartRefusesASecondSchedulerOnLocalStorage).

Resolved

A boolean that did not parse used to become false with no error, including on and yes, the forms the docs use. TASKIEM_SECURE_COOKIES=yes sent cookies without Secure, and TASKIEM_REQUIRE_ADMIN_PASSKEYS=on turned admin passkeys off. An unparsable TASKIEM_DATABASE_POOL silently became 20, and a malformed TASKIEM_ANCHOR_KEY was only logged. envBool now accepts true/false, 1/0, yes/no and on/off in any case, and loadConfig refuses any other value, a bad number or a bad anchor key at start, naming the variable (TestConfigBooleans). Found while writing this page.

Probes and graceful shutdown

On SIGTERM, drainOnShutdown sets draining at once, so /readyz answers 503 on every port while /healthz stays 200. The process keeps serving for TASKIEM_SHUTDOWN_DELAY while load balancers take it out, then ends the run context. HTTP servers then have 20 seconds to finish open requests (httpTask). Workers stop claiming and let steps run on for TASKIEM_WORKER_DRAIN. Workers and schedulers then release the leases they still hold, so another pod picks the work up at once instead of after the 60-second lease. The chart refuses a grace period shorter than delay plus drain plus 10 seconds (taskiem.gracePeriod). The VM kit's container stops after 45 seconds.

Readiness on api, edge, all, public and mail pings the database with a 2-second timeout. The chart probes readiness only for api, edge and all. The other roles get liveness only, on the metrics port's /healthz, which answers 200 as long as the HTTP server runs. A wedged worker loop is not detected there. A task that fails stops the whole process.

Risk
  • Dedicated worker pools hard-code a 60-second grace period and do not get TASKIEM_SHUTDOWN_DELAY or TASKIEM_WORKER_DRAIN. They ignore shutdown.*: raising workerDrainSeconds changes the shared workers only.
Resolved

The public host's and the mail role's /readyz used to check only draining, so the VM kit and the chart judged them healthy while every storefront and form answered with an error. Both now use the same readiness handler as the API, which pings their own pool with a 2-second timeout (TestPublicReadinessPingsTheDatabase).

Migrations at deploy time

taskiem migrate applies the embedded goose migrations as the schema owner (db.Migrate). They only go forward, and each runs in its own transaction. The chart runs them as a pre-install and pre-upgrade hook, while the old pods keep serving. The VM kit runs them as a Compose service that the app waits on. The rule that makes this safe is that a release must work with the schema of the release after it (spec 15.4, "backward-compatible for one release"). In the Up sections of the 163 migrations there is no DROP COLUMN, rename or type change, and the one privilege change (00201) re-grants the columns the old code wrote. A VM rollback runs the old image's migrate against a newer schema. Goose finds nothing to apply, and the old release starts.

Resolved

Nothing used to bound how long a migration waited for a lock, so an ALTER TABLE queued behind a long transaction blocked every query on that table while the old pods were live, and with no session locker two migrate runs at once raced. migrate now sets lock_timeout on every migration connection (10 seconds, TASKIEM_MIGRATE_LOCK_TIMEOUT, the chart's migrations.lockTimeout), so such a migration fails and the Job retries, and takes goose's Postgres session lock, so concurrent runs take turns (TestConcurrentMigrationsTakeTurns, TestMigrationsGiveUpOnALock).

Risk

Shipped migrations are not edited, so their indexes stay built without CONCURRENTLY, and 00252's on audit_log blocked audited writes while it ran. The lock timeout does not bound a build once it has its lock. New indexes on large tables are to be built CONCURRENTLY, in a migration of their own marked -- +goose NO TRANSACTION; nothing checks this yet.

SLOs, alerts and dashboards

The objectives are one Go list, slo.SLOs. go generate ./engine/slo turns it into the Prometheus recording rules, the burn-rate alerts, promtool unit tests and the Grafana dashboard. These are committed under deploy/prometheus and deploy/grafana, and copied into the chart (decision 0023). Tests check that the generated files are current, that every alert has a runbook section in docs/reliability.md, and that every metric a rule or panel reads is one engine/telemetry exports. A further test runs promtool when it is installed. All of them pass at this commit.

Next to the burn rates are six symptom alerts: the canary failing or stopped, the scheduler stalled, a connector or sandbox queue over 10 minutes old, leases expiring, and a target that cannot be scraped (slo.Alerts). Every metric the rules read exists, with the labels they use.

Risk

The 30-day SLI and the error budget left go blank after any quiet hour. Both come from avg_over_time of the hourly ratio. If an SLO has no events in an hour, its counters exist but neither rose, and the ratio is 0/0, which is NaN. One NaN makes avg_over_time NaN for the next 30 days. The dashboard's "SLI, last 30 days" and "Error budget left" panels then show nothing. Scheduler timeliness has no events whenever no timer or schedule falls due. On a small install, the other SLOs have none at night unless the canary runs. The burn-rate alerts are unaffected, because NaN > x is false. Fix: record the 30-day ratio as sum(increase(errors[30d])) / sum(increase(total[30d])), or drop NaN hours with (ratio == ratio).

Metrics and traces

engine/telemetry registers counters and histograms on the default registry: HTTP requests by chi route pattern, ingest deliveries by kind and status, steps by queue and connector, dispatch delay, run start, scheduler lateness, the scheduler's last tick, leases recovered and released, the canary, limit hits, signups, key-check failures and refused tenant code. No metric has a tenant label. Which tenant hit a limit is recorded in tenant_limit_hits instead. Two collectors query the database at scrape time: QueueCollector (queue depth and oldest ready task, and runs held back by tenant or workflow limits) and PoolCollector (the same by worker pool). Every role registers both, so each pod's scrape runs those queries, with no timeout. database.go adds failover retries and replica lag.

Tracing is OpenTelemetry over OTLP/HTTP and stays a no-op until OTEL_EXPORTER_OTLP_ENDPOINT is set (Setup). HTTP requests, ingest and worker steps start spans, with tenant_id, run_id and step_id as attributes. Logs are JSON on stderr, with every string and error passed through pii.Redact.

Spec and code differ

Spec 15.2 lists orchestrator latency and connector error rates by provider. There is no orchestrator latency histogram. Connector outcomes exist only as taskiem_steps_total{target}, with no rule or alert on them. Spec 15.3's "time to detect a provider outage: under 5 minutes" has no SLO or alert behind it.

The canary and the status page

The canary is a black-box probe (Prober.Probe). Once a minute, it signs a webhook to a canary workflow in an internal tenant through the public hooks URL. It then follows the run through the public API, using a key that can only read runs, and checks that the code step returned n * 2 + 1. taskiem canary setup creates the workflow, the webhook key and a 365-day API key, all through the public API. The scheduler runs it when TASKIEM_CANARY_HOOK_URL is set, and records each result for the status page. taskiem canary run runs it from outside the cluster.

The api role serves /status, /status.json and an Atom feed. These show components, operator-declared incidents and maintenance, and the canary's last 24 hours. status.Build marks runs degraded, or webhooks when the probe's webhook was not accepted, once the last three probes have failed and the newest is fresh. A declared incident takes precedence. Declarations go through the CLI, the operator console or an admin API with hashed tokens, into tables that refuse updates and deletes. Each pod rebuilds the page at most every 15 seconds, and a CDN may serve it for 30 seconds and keep serving the last copy when Taskiem is down.

Worker pools and dedicated tenants

A worker serves one pool (TASKIEM_WORKER_POOL, default shared) on the queues it lists. The claim function picks only tenants whose pool, from taskiem_tenant_worker_pool, is the worker's own. That function checks the tenant's own routing, then its partner's, then its plan's, then falls back to shared:

taskiem pools assign POOL --tenant ID (or --plan) refuses a pool that no live worker has reported from in five minutes (checkLive). The chart's workerPools entries each become a Deployment, a metrics Service, and optionally an HPA, a PDB and a NetworkPolicy. An entry may not list the container queue. Within a pool, each tenant's tasks are still capped at its worker_concurrency, or its container_concurrency for container steps.

Risk

A tenant routed to a dedicated pool loses its container steps, and any queue the pool does not run. The pool filter above applies to every queue, container included. The only container workers are the chart's containerSteps Deployment, which serves shared, and workerPools refuses the queue. So once a tenant is routed to acme, its container tasks are never claimed. A scratch database at this commit shows it: taskiem_claim_tasks('container', …, 'shared') took the unrouted tenant's task and left the routed tenant's ready. checkLive counts a pool live if it serves any queue, so a pool running only connector strands sandbox and ai too. No alert notices: TaskiemQueueBacklog and the dispatch SLO both match only connector|sandbox. The tenants most likely to be routed are on the enterprise plan, which has 3,000 container minutes. Fix: let the claim skip the pool filter for container until pools can run it. Make checkLive check each queue the tenant's workflows use. Extend the backlog alert to every queue, labelled by pool, using taskiem_pool_oldest_ready_seconds.

Spec and code differ

cloud.md says the container queue "is served by the container worker pool alone", meaning for routed tenants too. The claim function does not do this.

Billing, plans and where limits are enforced

With TASKIEM_BILLING=on, every role but public and mail loads deploy/plans.yaml at start and syncs it to plans. Plans removed from the file are retired, never deleted. A tenant's limits are layered: the platform defaults, then its plan's limits, then the operator's overrides, which win. A sub-tenant is held to its partner's. The scheduler's billing job runs every minute. It enrols unsubscribed tenants in a 14-day growth trial and moves subscriptions through renewal, dunning (days 0, 3 and 5), a 7-day grace and degradation, charging saved cards after commit and never twice for an invoice. It also reconciles pending payments, and snapshots usage hourly. A degraded or cancelled subscription refuses new runs while running ones go on.

Resolved

The Business plan declares max_subtenants: 50, but creating a sub-tenant used to check only partners.max_subtenants, which defaults to 0, meaning no cap, so a Business partner could create any number. 00255 falls back to the partner's plan's cap when the operator set none (TestSubtenantCapFallsBackToThePlan). Risk

The active but unlisted Business plan costs ₦250,000 a month, more than Enterprise at ₦180,000, which has more features. That is a pricing question for the founder.

Spec and code differ

Spec 16.2 says excess runs "queue, they are never rejected". The code rejects them in four cases: past max_queued_runs (429 backlog_full), beyond optional run quotas, above the ingest ceiling, and while billing is degraded. Throughput is "a token bucket per tenant in the task dispatcher" in steps per second. The code has a token bucket for run admission, and a cap on concurrent tasks per queue. The per-tier "environments" limit in spec 16.1 is not a limit at all.

Backups and restore

The database is the provider's. Both the VM kit and the cloud guide assume a managed Postgres with point-in-time recovery, and cloud.md sets out a monthly restore drill that also checks audit anchors and that a secret still decrypts. On the VM, taskiem-vps backup runs nightly at 02:30 Lagos time. It stops OpenBao for a moment, copies its Raft storage, and backs that copy up with restic, together with the archive and anchor volume and the kit's env files. It leaves out the unseal key, which is only on the offline recovery sheet. It keeps 14 daily, 8 weekly and 12 monthly snapshots. restore rebuilds a new server from the newest snapshot and the unseal key. check runs every 5 minutes. It alerts by email or webhook when a backup is over 36 hours old, when the recovery sheet is still on the server, and on health, OpenBao seal, token renewal, disk and certificate problems. On Kubernetes, the scheduler's PVC (archives and anchors) is kept when the release is deleted, and OpenBao is the operator's own.

Accepted

On the VM, OpenBao's static unseal key sits in openbao-unseal.env on the same disk as the storage it unseals (decision 0032's amendment). A copy of the disk opens every tenant's secrets. Backups leave the key out, so the off-site copy is safe.

Runbooks

The alert runbooks are in reliability.md, one section per alert, which a test enforces. Three procedures are in docs/runbooks/: deploying staging on one VM, Taskiem's own iswallet client, and a scan for unsafe writes before a release. Each command and variable in them was checked against the code:

  • staging.md. The installer's questions, the env file paths, TASKIEM_SMS_TERMII_*, TASKIEM_PUBLIC_ADDRESSES, ANTHROPIC_API_KEY, TASKIEM_AI_RETENTION, _STEP_MODELS and _MODERATION_MODEL, taskiem operators add EMAIL --name, the 15-minute update timer, and the warning that re-running setup resets TASKIEM_ALLOW_SIGNUP all match. So do the staging Postgres file's user and database (taskiem_owner, taskiem_staging).
  • iswallet-platform.md. The four TASKIEM_ISWALLET_* variables, TASKIEM_ISWALLET_PAYOUT_FEE_KOBO, taskiem iswallet subscribe|status|unsubscribe -mode, and the 404 before a secret is set all match.
  • write-safety-scan.md. Its queries use real columns (workflow_versions.state, definition, tenant_id).
  • reliability.md. The canary's setup output, taskiem canary probe, taskiem runs tail, the metric names in every query, and the shutdown sequence all match. So do the two tests it names, TestShutdownFlipsReadinessFirst and TestWorkerDrainsThenReleasesLeases.
Risk
  • The lease-expiry runbook says to "lower TASKIEM_WORKER_QUEUES concurrency". That variable names queues, not slots. Worker concurrency is fixed in the worker (16, or 4 for sandbox and container), and no setting changes it. The advice cannot be followed. Fix: add TASKIEM_WORKER_CONCURRENCY, or change the advice to fewer queues per pod.
