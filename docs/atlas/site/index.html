    Engineering atlas

    How Taskiem is built, checked against its code.

    Taskiem is a workflow engine that businesses trust with money movement: durable runs, exactly-once payments, approvals and an audit trail, with connectors for African payment and identity providers. This atlas explains it one feature and one component at a time. It is written for the engineers who maintain it.

    The system on one page#

    Everything runs from one Go binary. Each box below is a role it can run as, and PostgreSQL in the middle holds the state, the work queue and the audit log. Select a box to read about it.

    Four ideas the rest depends on#

    The history is the run#

    A run is an append-only list of events in run_events. A pure function, decide(), reads that list and returns the next events. It reads no clock and no randomness, so replaying a history always produces the same decisions.

    Follow one run

    Postgres is the queue#

    Tasks, timers and waits are rows. Workers claim them with FOR UPDATE SKIP LOCKED and hold a lease with an epoch number. Every write a worker makes is checked against that epoch, so a stalled worker can never overwrite the result of the worker that replaced it.

    Durable execution

    Intent before effect#

    Before any call that moves money, the worker commits an EffectIntent carrying a key derived from the run. After a crash, the engine knows a call may have gone out, and the connector's action class decides whether to retry, reconcile or stop for a person.

    Exactly-once effects

    The database enforces tenancy#

    Every transaction sets app.tenant_scope, and row-level security checks it on every tenant table. Work that crosses tenants, such as claiming tasks, goes through a few SECURITY DEFINER functions that return only routing columns.

    What Taskiem is#

    Taskiem runs workflows for businesses whose workflows move money. A workflow is a versioned JSON document in the wd/v1 format. It can be drawn on the canvas, written as TypeScript, drafted by the AI builder or built from WhatsApp, and all of these produce the same document. A run of that workflow is an append-only log of events in PostgreSQL. Workers carry out the steps: calling Paystack or Moniepoint, running sandboxed code, asking a model. Every call that moves money carries an idempotency key derived from the run, so a crash or a retry never pays twice.

    The spec names four kinds of customer (spec 1.1):

    SegmentExampleWhat they need from it
    Regulated fintechs and microfinance banksLenders, payroll providers, walletsMoney flows with audit trails and approvals
    SaaS companiesPayroll, HR and accounting toolsAutomation embedded in their own product for their customers
    Small and informal businessesRetailers, cooperatives, agentsSimple automations run from WhatsApp
    Internal operations teamsPortfolio companies of the holding companyBack-office glue without writing services

    The engine is the core, but the repository has grown well past it. It now holds chat channels (WhatsApp, Telegram, USSD, inbound email), a money layer (a money log of every movement on a business's rails, matching payments to invoices, receiving money, reports), a Schools product, and public storefronts and hosted forms. The README puts the project in Phase 2 (hardening). The docs/phase-*-status.md files record later product work as built or in review, and gated on go-live.

    One binary, seven roles#

    taskiem serve --role ROLE (or TASKIEM_ROLE) chooses what a process does. all, the default, runs every engine role in one process, which is how a small install runs. A larger one runs each role on its own and scales each separately. Every role shares one engine built by newEngine: the database pool, the store, the secrets vault, the connector registry and the WebAssembly connector runtime. The exceptions are public and mail. They load a smaller configuration and connect with their own database login, so a fault in the public pages cannot reach engine data.

    RoleWhat runs in it
    apiThe REST API for the web app, CLI, SDKs and partners, plus the web app's static files and the embedded builder's bundle. Also a set of background loops: Git sync, the WhatsApp and USSD sessions, storefronts and their orders, hosted forms, invoices, the inbound email drain, the self-repair queue (when a model is configured) and the outbound SMS and email sender. Lists and dashboards read from a replica when TASKIEM_DATABASE_READ_URL points to one.
    edgeIngest. /hooks for webhooks, connector events and run callbacks, /git-hooks for pushes, and /channels/… for the platform's WhatsApp number, Telegram bot, Slack interactions and USSD aggregators. In all mode the api listener serves /hooks as well.
    orchestratorSweeps runs that were left with events nobody decided on, every 100 ms. It is the scheduler type with SweepOnly set, because most decisions run inline in the transaction that appends the event.
    schedulerFires timers, recovers expired leases, sweeps, admits queued runs, purges runs past retention and creates event partitions. It also runs the cron triggers and about fifteen other periodic jobs: alerts, hourly secret-read digests, partner webhooks, billing, domain and embed-site checks, tenant key health, data-table token renewal, the Paystack event poller, storefront reopening, the money-log and schools mirrors, money summaries, the canary and audit anchoring.
    workerOne worker loop per queue named in TASKIEM_WORKER_QUEUES (by default connector,sandbox,ai). The container queue brings up the container runner and its egress proxy. A worker can serve a dedicated pool for chosen tenants or plans.
    publicThe public host for storefronts and hosted forms. It connects as taskiem_public and never builds the engine.
    mailThe SMTP server for email triggers. It accepts mail only for known addresses and leaves it sealed in an inbox for the api role to read.

    Spec and code differ

    The spec lists five roles (spec 2.1). The code adds public and mail, which the spec only mentions as a proposal. The spec also says schedulers are leader-elected with a session advisory lock (spec 2.3). The code has no leader election. Instead, the scheduler is written to be safe when several run at once: every claim uses SKIP LOCKED and every timer firing is guarded by fired_at. Running several schedulers costs some duplicated work and nothing worse.

    Starting and stopping#

    runTasks runs every loop a role needs as a goroutine. If any loop returns an error, the whole process stops so its supervisor (systemd or Kubernetes) restarts it clean. On SIGTERM, drainOnShutdown fails readiness at once, keeps serving for a delay so load balancers stop sending traffic, and only then stops the loops. Workers let calls already in flight finish (TASKIEM_WORKER_DRAIN, 30 seconds by default) and hand their leases back, so their tasks can be claimed again at once. Every role serves /metrics, /healthz and /readyz on the metrics listener, so roles without an HTTP API can still be probed.

    The architecture map#

    Requests come in at the top. The front roles verify and record them. Nothing important happens in memory: an accepted webhook is already a committed run with its first decision made when the caller gets 202. The core roles pick up work from PostgreSQL, and only workers call out. Every outbound connection, whether a connector call, an HTTP step, a fetch from the sandbox or a database connection, dials through the egress guard.

    Where the spec and the code disagree#

    These are the differences found so far. Each is explained where it matters.

    1. Seven roles, not five, and no scheduler leader election (above).
    2. decide() returns events, not commands. Life of a run
    3. A worker writes StepStarted only for steps that write. Read steps go straight from scheduled to completed. Life of a run
    4. The attempt group, and with it the idempotency key, moves on automatically when a reconcile finds that a payment never happened. The contract says so and the spec's own section 4.4 is out of date. Life of a run
    5. The spec's example workflow uses smileid@2. There is no such connector. Identity checks go through youverify, prembly and dojah.
    6. Several tools named in the stack table are not used (above).
    7. There are 287 SECURITY DEFINER functions that bypass row-level security, not the spec's four. Data model

    9. The waiting run status is never set. Run statuses
    10. Publish approval is one tenant-wide switch, not per environment. Workflow definitions
    11. An operator's "retry" on a parked payment reuses the old idempotency key, where the contract says it should get a new one. Exactly-once effects

    The code also goes past the spec in places. Workers claim tasks fairly across tenants, with a concurrency cap per tenant and dedicated worker pools. Runs over a tenant's limits are queued and admitted later instead of being refused. The Durable execution page covers both.

    The life of a run

    One webhook followed from the edge, through three transactions and a payment, to the end of the run: what is written where, and what happens when something fails along the way.

    The fastest way to understand Taskiem is to follow one run from start to end. This page follows the spec's own example, a workflow that pays out an approved loan. It starts with a webhook, checks the borrower's BVN, waits for a credit officer's approval, sends the money with a Paystack transfer, and ends. Each stage names the function that does the work and the rows it writes, so you can open the code beside it.

    The workflow#

    This is the definition as the spec gives it (spec 3.1). Three things matter for this walkthrough. verify_bvn only reads. approve waits for a person. pay moves money, and its effect.idempotency_seed ties the payment's key to the loan rather than to the run, so even a second run for the same loan cannot pay it twice.

    Spec and code differ

    No smileid connector exists. In this repository a BVN check would use youverify@1's verify_bvn, which is also a read action. Nothing below depends on which one is used.

    The pay step calls Paystack's transfer action. Its manifest declares the action class and how the idempotency key is encoded to fit Paystack's reference format. It also names verify_transfer as the action that can ask Paystack, after a crash, whether a transfer happened.

    Follow the run#

    Select a stage to light up its part of the sequence. T1, T2 and T3 are database transactions. Everything a stage writes commits together or not at all.

    1. The delivery reaches the edge#

      The provider posts to /hooks/{tenant}/loans/approved. receive checks the tenant exists and is active, and applies the tenant's two ingest rates. Above the hard ceiling the caller gets 429 with Retry-After. Above the soft rate the delivery is accepted but the run will be queued. The body is capped by the tenant's plan.

      webhook then finds the trigger registered at that path, checks the method and CORS, and verifies the signature: HMAC, basic or JWT (verifyCall). It validates the body against the workflow's inputs schema (422 if it does not match). It computes a dedup key, by default a hash of the body, or the trigger's own expression. The whole request runs under a 5-second budget.

    2. T1: the run starts and is decided#

      Store.Start opens one tenant-scoped transaction, and startIn does everything else inside it. It checks the tenant is active. It inserts into trigger_receipts: if this (trigger, dedup key) was seen before, it returns the original run with duplicate: true and writes nothing more. It then checks billing, quotas and the tenant's hold (tenantHold), inserts the runs row, pins the connector versions and approval policies the run will use, seals personal data, and appends RunStarted.

      If the run is admitted, start arms the run's timeout timer and calls decideInline in the same transaction. That makes the first decision, StepScheduled for verify_bvn, and inserts its tasks row. Only then does the transaction commit and the caller get 202 with the run id.

      RunStartedStepScheduledtrigger_receiptsrunstaskstimerstenant_usage

    3. The worker wakes and claims the task#

      A trigger on tasks calls pg_notify('taskiem_tasks', queue), which wakes idle workers on that queue at once; polling every second is the fallback. Worker.Run has one claimer feeding a fixed set of executors, and it only claims as many tasks as it has free executors.

      The claim calls taskiem_claim_tasks, a SECURITY DEFINER function that can see every tenant's tasks but returns only routing columns. It takes ready tasks with FOR UPDATE SKIP LOCKED, sets a 60-second lease, and increments lease_epoch. That epoch is the fencing token for everything the worker writes about this task. A heartbeat extends the lease while the step runs.

    4. T2: intent is recorded before anything is sent#

      prepare reads the run's history inside the tenant scope. It finds the step's StepScheduled, notices if the step already has an outcome or was cancelled, and resolves the connector action and its class. verify_bvn is a read, so the worker goes straight to the call, with no intent and no StepStarted.

      For pay, a write, the worker derives the idempotency key from the tenant, the seed (here the loan id), the step and the attempt group. It looks at what earlier attempts left behind, then recordIntent checks the fence, locks the run, makes sure the step was not cancelled meanwhile, and appends StepStarted and EffectIntent with the key and a digest of the input. This commits before the call.

      StepStartedEffectIntent

    5. The call to Paystack#

      send resolves secrets and the connection's credentials. It puts the encoded key in the reference field and calls the action through an HTTP client that dials only through the egress guard. For a write, the call must start before the intent's time plus the call timeout, 30 seconds by default (decision 0009). If that deadline has passed, nothing is sent and the attempt fails as not sent, which is always safe to retry.

      The output is compared with the manifest's schema, and any difference is recorded as connector drift. Errors are classified as retryable, fatal, not sent or unknown outcome. The class of the action decides what each of those means.

    6. T3: the outcome is recorded and the next step decided#

      finish releases the task under the fence. If another worker holds the lease now, it records nothing. It scrubs any secret echoed in the output, records a settled payout in the money log, seals personal data, and appends StepCompleted (or StepFailed).

      In the same transaction it calls decideInline. After verify_bvn that writes ApprovalRequested and an approvals row. After pay it writes RunCompleted. finish retries across a database failover: repeating a finish that did commit is fenced out, so it can never record twice.

      StepCompletedApprovalRequestedapprovals

    7. Waiting costs nothing#

      While the approval is open, nothing runs. There is only a row in approvals and, if the step has a timeout, a row in timers. When the credit officer approves, from the web app or WhatsApp, DecideApproval locks the run, checks the approval is still open, appends ApprovalDecided, and decides inline. That writes StepCompleted for approve and StepScheduled for pay. Signals and timers wake runs the same way: one transaction appends the event and makes the next decision.

      ApprovalDecidedStepCompletedStepScheduled

    8. The scheduler is the safety net#

      Every 250 ms Scheduler.Tick fires due timers (the approval's timeout among them), makes expired leases claimable again, and sweeps runs that have events nobody decided on, which happens after a crash between append and decide. It also admits runs that were queued behind tenant limits, purges runs past retention every ten minutes, and creates run_events partitions every hour.

    9. The run ends#

      When decide finds nothing left to do, it writes RunCompleted. applyEffects calls endRun, which sets the status and the retention date, releases the run's concurrency slot, and admits the next run that was waiting for that slot.

      RunCompleted

    Spec and code differ

    The spec says StepStarted is written when "a worker claims the step's task" (spec 4.1). In the code a worker writes it only in recordIntent, so only for steps that write. That is why verify_bvn has no StepStarted above. decide also writes StepStarted for control steps (branch, parallel, foreach) to record which path or how many items it took. A run inspector that treats StepStarted as "a worker picked it up" will be wrong for reads.

    How a decision is made#

    decide is a pure function of the definition and the history. Its package comment states the rule that everything else depends on:

    Retry backoff needs jitter but cannot use randomness, so backoff derives it from a hash of the run id and the step. Replaying a history gives the same delays.

    decideInline is where the pure function meets the database. It locks the run row, folds the history (from an in-process cache of up to 2,048 runs, so a busy run is not re-read from the start every time), asks for the next events, and appends each one with applyEffects turning it into rows: a task, a timer, a signal wait, an approval, a child run. Some effects cause new events. For example, a signal that arrived early and was buffered is delivered as soon as the run starts waiting for it. So the loop runs again, up to 16 rounds, until nothing new happens.

    Spec and code differ

    The spec describes decide as returning commands (ScheduleStep, StartTimer and so on) that are then turned into events (spec 4.2). The code skips that layer. decide returns the events themselves (NewEvent), and applyEffects derives the rows from each event's type. One less translation step means one less place where a replay could come out different.

    Each decision also counts the steps it scheduled. A run that goes past its plan's max_steps_per_run, for example a runaway foreach, is failed in the same transaction, so no step over the cap ever reaches a worker (countSteps).

    How work is claimed fairly#

    Claiming is the one place where a worker has to see every tenant's tasks. It is done by a function owned by the taskiem_dispatch role, so the worker's own login never needs to bypass row-level security. The function does more than the spec asks. It walks the distinct tenants that have ready tasks (a loose index scan, so it stays fast with many tenants). It keeps only tenants routed to this worker's pool. It caps each tenant at its concurrency limit, counting leases it already holds. It then takes tasks round-robin across tenants, so one tenant's backlog cannot starve the others.

    The worker then does all of its real reading inside an ordinary transaction scoped to that one tenant, through db.InTenantTx, which sets app.tenant_scope for row-level security to check.

    Intent, fencing and the call deadline#

    Three mechanisms together make the payment safe, and recordIntent is where they meet. The fence is the first statement. The run lock stops a cancellation from slipping in between the check and the write. The intent records the key and a digest of what is about to be sent.

    The fence itself is a single function call that only succeeds while this worker still owns the task at this epoch. Every write a worker makes about a task goes through it.

    One document, many editors#

    A workflow is one JSON document in the wd/v1 format. The canvas, TypeScript workflow code, the AI builder, the WhatsApp builder, the template gallery and Git sync are all editors of that document. None of them keeps a format of its own. The runtime reads only this document, so whatever produced a workflow, it runs the same way.

    The contract is docs/contracts/wd-v1.md plus the JSON Schema schemas/wd-v1.schema.json. The Go model is in engine/wd/model.go:

    Run-level settings are short: timeout, concurrency_key, max_concurrency and retention. Canvas positions are not part of the definition. They live in a separate layout column that can change without making a new version, so moving boxes around never needs a publish approval.

    Every step can have needs (steps it waits for), when (a condition), retry, timeout, on_error (steps to run if it fails), effect (the idempotency seed) and compensate (the action that undoes it).

    Spec and code differ

    The spec lists 15 step types and marks form as proposed (spec 3.2). The code has form built and adds container, capability and template. Capability and template steps change what "the definition" means at run time: the version that is published is not the exact graph that runs. The run pins its expansion (runs.expansion), and the run inspector has to show the expanded steps.

    Expressions#

    A string that starts with = is a CEL expression. CEL has no side effects, cannot loop forever, and has a bounded cost, so it can run inside decide without breaking determinism. Each evaluation is capped at a cost of 1,000,000, and compiled programs are cached per process in a bounded cache.

    The rules that publishing enforces (checkExpressions):

    • Every expression compiles.
    • steps.<id> may only name steps that are certain to have finished first (rule 5). You cannot read a step in a parallel branch you are not waiting for.
    • item and index exist only inside a foreach.
    • An expression that reads secrets reads nothing else (rule 10, decision 0010). Secrets are resolved by the worker at execution time, so their values never enter history. Mixing them with data would force them into the decision.

    Versions, environments and publishing#

    Every save makes a new immutable version. A database trigger refuses changes to definition or digest once a version exists (00003). The digest is a SHA-256 of the canonical JSON (canonical). Runs pin the version they started on, so editing a workflow never changes a run in flight.

    Versions move through draft, published, deprecated and archived. Each environment (dev, staging, prod, or the tenant's own) runs its own version, recorded in deployments. Publishing deploys to every environment not gated on another. A gated environment only takes a version by promotion from the environment it names. Promotion copies the version and never edits it (00024).

    When a tenant turns on four-eyes publishing, a person asks to publish and a different person approves. API keys cannot ask. Every path that publishes checks the setting: the web app, chat, Git sync, AI repair, partner packages and receive-money (publish).

    Spec and code differ

    The spec makes publish approval "configurable per environment" (spec 3.4). In the code it is one tenant-wide switch, governance_settings.four_eyes_publish. A tenant cannot require approval for prod while letting dev publish freely. Gating prod behind promotion from staging gets close, but promotion itself is not four-eyes.

    Code, canvas and Git#

    Workflow code#

    A *.flow.ts file describes the same document with a builder. Arrow functions over the expression context compile to CEL, so authors get TypeScript's checking without the engine running TypeScript at run time:

    taskiem build compiles code to definitions and taskiem codegen goes the other way. Both run inside the Go binary: the SDK is embedded, bundled by esbuild and executed in the QuickJS sandbox, so neither the CLI nor the API needs Node (engine/flowcode). The repository's example and dogfood workflows are kept as both files, and CI validates the definitions.

    Concurrent edits#

    Each save names the version it was based on. If someone else saved in between, wdmerge merges the two three ways against that base. The unit is a top-level field or a top-level step with everything nested in it. Two edits to different steps merge cleanly. Two different edits to the same step are a conflict for a person, never a guess.

    Git#

    Each environment can be connected to one repository on GitHub, GitLab or Bitbucket (engine/gitprovider), in one of two modes (docs/git.md):

    • Platform-led: Taskiem is the source of truth. Publishing a version also opens a pull request with the definition and its generated .flow.ts, so the repository keeps a reviewed history. Publishing does not wait for the merge.
    • Git-led: the repository is the source of truth. A push to the connected branch, received on the edge's /git-hooks, saves and publishes the changed definitions to that environment and loads approval policies kept in the repository. Those workflows are read-only in Taskiem.

    Making an environment Git-led hands its deploys to whoever can push to the branch. So when a tenant's governance is strict (four-eyes publishing or policies, or a gated environment), setting up or changing a Git-led connection needs one person to ask and another to approve, and an API key cannot do it. After that, pushes deploy without a second approval in Taskiem. Review happens in the repository. Git credentials are tenant secrets in a reserved environment that workflows cannot read (api/git.go).

    Testing workflows#

    A workflow test (*.test.json, the wd-test/v1 contract) gives a trigger, mocked step outcomes, signals, approval decisions and form answers, and asserts the path the run took and its outputs. Tests run the real decide over an in-memory history on a virtual clock, so a test of a 72-hour signal timeout takes milliseconds and never calls a provider (engine/wdtest). taskiem test runs them offline, and the AI repair pipeline uses the same machinery for its shadow runs.

    Templates#

    The template library holds 78 ready workflows for small businesses ("every Friday, text my customers who owe me"). Each is a wd/v1 definition with typed parameters, embedded in the binary (templates). Parameter substitution is injection-safe: inside an expression a value becomes a quoted CEL literal, and no value may start with =, so a parameter is always data, never code. Personal data such as an owner's phone number is never a parameter. Templates read it from tenant variables, so no definition carries it.

    A run in Taskiem must survive any process dying at any moment without losing work or repeating a payment. This page explains the machinery that makes that true. The life of a run follows one run through it. This page takes each part in turn and covers the cases that one run does not reach.

    The run is its event log#

    Every run has an ordered, append-only list of events in run_events. Nothing else describes what a run has done. The runs row holds a status, counters and leases for quick lookups, but the history is the source of truth. The application role can only SELECT and INSERT on run_events. UPDATE and DELETE are never granted, so even a bug cannot rewrite history.

    Events are appended through taskiem_append_event. It increments runs.last_seq and inserts the event at that number in one statement. The UPDATE takes the run's row lock, so two transactions can never give out the same sequence number, and there are never gaps.

    run_events is partitioned by month on the run's start time, not the event's time, so all of one run's events sit in one partition. The scheduler creates partitions three months ahead every hour (taskiem_ensure_run_event_partitions), and a test checks that partitions cover new runs.

    Deciding: a pure function, run where the event lands#

    decide.Decide(definition, history) folds the history into per-step facts and returns the events that follow. It reads no clock. Its notion of "now" is the recorded_at of the latest event, so time enters only through the log. Retry jitter comes from a hash of the run id, step and attempt, not from randomness.

    Determinism is tested, not assumed. decide.Verify replays a recorded history and checks that every block of decide-written events is byte-for-byte what decide produces from the events before it. TestDeterminismSuite runs it over real runs, and the crash and PII suites also call it.

    There is no separate orchestrator in the common case. Whoever appends an event decides in the same transaction: ingest after RunStarted, the worker after an outcome, the API after an approval, the scheduler after a timer. The orchestrator role exists for the leftovers. Any run whose decided_seq is behind last_seq is found through a partial index and decided by the sweep.

    Folding a long history on every event would be slow, so each process keeps the folded state of recent runs in a cache (up to 2,048 runs). Only events committed before the deciding transaction began are folded into it, so a rolled-back decision cannot leave phantom events behind.

    Run statuses#

    Spec and code differ

    Waiting: timers, signals, callbacks, approvals#

    Timers#

    Timers are rows in timers with a kind: wait, signal_timeout, approval_timeout or run_timeout. Every tick, the scheduler claims due timers through taskiem_claim_due_timers. For each one it opens a tenant transaction, marks the timer fired only if fired_at is still empty, appends TimerFired, and decides inline. The fired_at guard makes it safe for several schedulers to run at once.

    Signals#

    A signal step waits for an event and a correlation key in the run's environment. Waiting and delivering both take a transaction-scoped advisory lock on (tenant, environment, event, correlation), so a signal can never slip between "is anyone waiting?" and "I'm waiting now" (signalLock).

    • Delivery to waiting runs is a broadcast. Every run waiting on that key gets SignalReceived (deliverSignalTx).
    • A signal that arrives before anyone waits is buffered in signals for seven days. A buffered signal is consumed by the first run that starts waiting, oldest first (registerWait). So the same signal reaches every waiter if they are already waiting, but only one if they start later. Workflows that rely on signals should not depend on more than one run receiving the same one.

    Callbacks and approvals#

    A callback step gives the outside world a unique URL with a secret key to call the run back. The key is sealed in history like personal data. Approvals are rows in approvals, with policy snapshots taken at run start. A decision arrives through the API or a chat channel, is appended, and is decided inline. The Governance and compliance page covers policies and levels.

    Retries, errors and compensation#

    A worker classifies each failure (the Exactly-once effects page has the rules). decide then applies the step's retry policy:

    • Default policy: three retries, exponential from 2 seconds, capped at 5 minutes, plus up to 20% jitter. Code steps get no retries by default.
    • A provider's Retry-After wins if it is longer, up to an hour.
    • max_duration bounds the total time across attempts.
    • When retries run out, finalise fails the step. If any attempt was a write that may have taken effect, it parks it instead.
    • A failed step runs its on_error steps if it has them. Otherwise the run fails, after compensate has run the compensate action of every completed step that declares one, newest first. A compensation that fails parks the run rather than looping.
    Spec and code differ

    The spec says cancelling a run "runs compensation if configured" (spec 4.10). CancelRun appends RunCancelled and ends the run immediately. Pending tasks and timers are deleted, and no compensation runs. A step a worker already holds still records its result. If cancelling a run should reverse transfers it already made, that has to be done by hand or built.

    Admission and concurrency#

    A run can be held as queued for two different reasons, recorded in runs.queue_reason:

When it is full, new runs are refused with a limit error instead of queued.

    Subflows#

    A subflow step starts another workflow of the same business as a child run, in the transaction that records the step (startSubflow). The child inherits the parent's idempotency seed plus the step, so resuming the parent never repeats the child's writes. When the child ends, it delivers a subflow signal to the parent's step, and a parent that ends cancels the children it was waiting for. Chains nest at most five deep.

    Replay, fork and repair#

    Replay needs no special mode: decide over a history always reconstructs the same state. Fork is how a failed run is resumed on a repaired version:

    Forks reuse the decision loop with a much higher bound (4,096 rounds instead of 16), because each replayed outcome takes a round. planFork refuses runs that cannot be resumed safely and says why.

    Retention and archiving#

    When a run ends, endRun sets retain_until from the workflow's settings.retention, the tenant's default, or the platform default, capped by the plan. Every ten minutes the scheduler archives and then deletes up to 500 runs past retention (PurgeExpired). Without an archiver configured (TASKIEM_ARCHIVE_DIR), nothing is deleted: history is never dropped unarchived.

    Spec and code differ

    Two storage promises in the spec are not built:

    • Archives go to object storage after 90 days (spec 4.11). The only archiver is FileArchiver, which writes gzipped JSON lines to a local directory. In a multi-node deployment that directory must be shared storage, or archives end up scattered across machines.
    • Outputs over 256 KB move to object storage, referenced by content hash (spec 4.9). run_events has a payload_ref column, but nothing reads or writes it. Every output is stored inline. HTTP steps truncate responses at 256 KB, but connector, code and AI outputs have no equivalent cap here. A connector that returns a large list will bloat history, the fold cache and every replay.

    What is promised, and on what terms#

    Delivery is at least once. Any step can run twice, because a worker can die after doing the work and before recording it. Taskiem makes the effect happen once by knowing, for every action, what is safe to do when it is unsure whether an earlier attempt reached the provider. That knowledge is the action's class, declared in the connector's manifest. The class alone decides retry behaviour.

    The guarantee therefore depends on the provider. With an idempotency key the provider honours, or a way to ask whether something happened, Taskiem can make an effect exactly-once. With neither, it guarantees at most once: it stops and asks a person rather than risk sending twice.

    The four classes#

    Failures are classified into five kinds. An error a handler does not classify counts as unknown_outcome, because assuming nothing was sent is the unsafe guess (Classify). not_sent is special: it means no byte left the process, such as a DNS failure, a refused connection or a passed deadline. It is the only failure an unsafe_write may retry.

    This is effects.AfterError and OnOpenIntent written out. The last column is what a worker does when it finds an earlier attempt's intent with no outcome, the crash case.

    Steps that are not connector calls#

    The worker gives every step a class before running it (resolveExecutor):

    • http: the workflow author must declare class for any method other than GET and HEAD, and may name an idempotency_header.
    • container: unsafe_write unless declared otherwise.
    • ai: a read.
    • code: a read.
    Risk

    A code step is classed as a read, but its sandbox can call host.fetch with any method (the JavaScript host, code-steps guide). A code step that POSTs a payment is not protected. It records no intent, so if its worker dies after the POST, the task is claimed again and the POST is sent again. Code steps get no automatic retries by default, which narrows this, but crash recovery still re-runs them. Either forbid non-GET fetches from code steps, or let code steps declare a class and record an intent like http steps do.

    Keys: derived, never random#

    An idempotency key is a function of where the effect sits, so every retry and every replay produces the same key:

    • Seed: the step's effect.idempotency_seed if it declares one (say a loan id), otherwise the run id.
    • Step: the step instance id (pay_all[3].pay_employee inside a foreach), or the plain step id when a seed is declared.
    • Attempt group: starts at 0 and changes only when the engine knows the earlier key's effect did not happen (below).

    The digest is then encoded to fit the provider's reference field, as the manifest's idempotency block says: base32_lower, hex_lower or base64url, a length, a prefix and the provider's limits. Spec.Validate refuses an encoding that keeps fewer than 128 bits, or one whose prefix or alphabet the provider would reject. Paystack's transfer gets tsk_ plus 32 base32 characters (160 bits). Fixed test vectors in engine/effects/testdata/vectors.json pin the derivation. Only the Go tests use them today. Any second implementation, such as a TypeScript one, should be checked against them too.

    Connectors without an idempotency block, and http and container steps, use a default encoding, which an http step can send in a header.

    Risk

    When a step declares a seed, the key leaves out the instance id (decide.go), so the key is stable across runs. The contract says why: "the seed is expected to identify the item" (idempotency contract). Nothing checks that it does. In a foreach that pays 50 employees, a seed like =trigger.body.payroll_id gives all 50 payments the same key. Paystack would treat payments 2 to 50 as duplicates of the first, and the run would report 50 successes. Validation should at least warn when a seeded step inside a foreach has a seed that does not use item or index.

    Seeds across runs, forks and subflows#

    • A business seed deduplicates across runs: a second run for the same loan produces the same key.
    • A fork keeps its parent's seed, so a step the parent completed is never paid again. A step the parent attempted and failed for good starts a new attempt group in the fork, so the provider does not just return its cached failure.
    • A subflow's seed is the parent's seed plus the step, so resuming the parent never repeats the child's writes.

    Intent, deadline, reconcile#

    The life of a run shows recordIntent. The intent records the key, its inputs and a digest of the request (IntentPayload), and it commits before the call. Two time rules from decision 0009 make the next part safe:

    • The call deadline. A write's call must start before the intent's time plus the call timeout (30 s), and it is cancelled at that deadline. A worker that stalls past its lease cannot wake up and send late.
    • Reconcile waits for the deadline. A provider's "not found" is trusted only after the original call's deadline has passed. Before that, the task is put back without spending a retry.

    The flow when a reconcilable write has an open intent:

    1. Wait until the earlier attempt's deadline has passed.
    2. Call the reconcile action with the key.
    3. Found: record StepCompleted with the provider's answer, marked as reconciled.
    4. Not found: move to the next attempt group, which gives a new key, record a new intent, and send.
    5. Error: a retryable error reconciles again later. Anything else parks the step.

    Connectors also receive the time the current key was first sent (KeyFirstSent). A provider that only deduplicates for a limited window can then report indeterminate once the window has passed, which parks the step instead of re-sending under a key the provider has forgotten.

    When a person has to decide#

    A parked step sets the run to needs_reconciliation and raises an alert. An operator has two tools:

    • CheckReconcile runs the action's read-only reconcile and shows what the provider says now, with personal data masked. It changes nothing.
    • ResolveStep settles the step in one of three ways. completed means it happened, with an output recorded. failed means it did not happen and should not be retried. retry means it did not happen and should be sent again. The resolution is appended to history and to the tenant's audit chain, then the run is decided again.
    Code and contract differ

    The contract says the attempt group increments "only when a reconcile returns not_found or a human explicitly re-issues the effect" (idempotency contract). An operator's retry resolution records a not_sent failure and the next attempt reuses the old key. The only places the group moves are reconcile's not_found and forks. For an idempotent_write, a provider that did see the first request will answer the re-send from its cache, possibly with the old failure. Decide which behaviour is intended and make the code and contract agree. If a fresh key is intended, ResolveStep must bump the group.

    One more kind of parking has nothing to do with providers. When a tenant's own encryption key (bring your own key) cannot be unwrapped, steps that need secrets park as key_unavailable. When the key works again, ResumeKeyParked resumes them, retrying or reconciling as the step had been doing, without spending its retry budget.

    Where the guarantee ends#

    • Unsafe writes are at most once. A dropped connection on an M-Pesa STK push or an airtime top-up becomes a person's job. That is correct, but at volume it is an operations cost to plan for.
    • The class is only as good as its manifest. A connector that calls an action idempotent_write when the provider does not actually deduplicate on that field will pay twice. The Connector framework page will cover how manifests are reviewed and tested.
    • Calls already in flight at the deadline. Decision 0009 says it plainly: the deadline bounds when a call can start, not when the provider finishes processing it. call_timeout must exceed the provider's own processing time, and worker and database clocks must agree.
    • Code steps (above).

    Migrations create the roles as NOLOGIN NOBYPASSRLS (00001, 00176). In production the engine logs in as a user that is a member of taskiem_app only.     Tenant scope#

    Every tenant table's policy compares tenant_id with the transaction's scope:

    The scope is a transaction-local setting holding an array of tenant ids, read through taskiem_tenant_scope(). When it is unset, the array is empty and every policy matches nothing, so forgetting to set it fails closed.     Partners and sub-tenants#

    A partner, a SaaS company embedding Taskiem, never gets its sub-tenants in its own scope. To act inside one, the API calls taskiem_partner_enter.     The cross-tenant functions#

    Some work has to see every tenant: claiming tasks, firing timers, finding a user by email before anyone knows their tenant, routing an inbound WhatsApp message to its business. That work goes through SECURITY DEFINER functions owned by taskiem_dispatch. The dispatch role has policies of its own on the routing tables only, with column-level grants, so even its functions cannot read payloads:

    The rule each function follows: claim with SKIP LOCKED, return only routing columns, and let the caller open a normal tenant-scoped transaction to read anything else. Every definer function in the migrations pins search_path, which closes the classic hijack of an unqualified name.

    Spec and code differ

    The spec describes "a small set" of four dispatch functions, "reviewed like security code" (spec 5.3). The migrations define 287 SECURITY DEFINER functions. Grouped by name, the largest families are public pages (about 34), authentication (27), the operator console (25), WhatsApp and Telegram (32), the connector catalogue (14) and partners (11).     Risk

    The guard rails around these functions are good but partial:

    • TestEveryTenantTableIsProtected checks every table has RLS enabled and forced, with an app policy, and that partitions are not directly readable.
    • TestDispatchRoleCannotReadPayloads checks that the dispatch role is refused on a hand-kept list of sensitive columns.
    • The public host's test pins the exact set of functions taskiem_public may execute (hosts_db_test.go).

    Two things are missing. Nothing pins the set of functions taskiem_app may execute, so a new definer function only needs a GRANT to become reachable from the API. And the column denylist only covers what someone remembered to add. A test that lists every definer function, requires each to be recorded in an allow-list with a one-line justification, and asserts the search_path pin, would turn review into something CI enforces.

    What the isolation protects against, and what it does not#

    Row-level security here protects against query mistakes: a missing WHERE tenant_id = …, a join to the wrong table, a list endpoint that forgot a filter. Those return nothing from other tenants, and TestTenantIsolation checks it.

    It does not protect against code that sets the wrong scope, or against SQL injection. app.tenant_scope is an ordinary setting that the application role is allowed to change, so a statement running as taskiem_app can name any tenant. The real boundary is therefore InTenantTx and the authentication code that decides which tenant ids to pass it. Those deserve the same review as the definer functions. The scope itself is set with a bound parameter (set_config('app.tenant_scope', $1, true)). Any SQL built from strings elsewhere would be a way around the whole scheme, so string-built SQL deserves a lint rule.

    Migrations#

    Migrations are plain SQL files embedded in the binary and applied by goose with taskiem migrate, as the schema owner (db.migrate). Each file has a Down section, but the CLI only migrates up. Roll back by restoring, or by writing a new migration. CI applies every migration to a fresh database on each push, and the database tests in engine/db/db_test.go check the properties above: append-only tables, immutable versions, distinct sequence numbers under concurrent appends, disjoint claims, fencing, and timers firing once.

    Because a SQL function is replaced by a later migration with the same name, the current definition of anything (taskiem_claim_tasks has five) is the one in the highest-numbered migration. Search from the end.

    The read replica#

    With TASKIEM_DATABASE_READ_URL set, run lists and dashboards read from a replica (decision 0024). The replica pool sets the same role and scope, so RLS applies there too. It is never used for anything that decides, leases or writes. When its lag goes past the limit, or it cannot be reached, reads fall back to the primary.

    Part Z · About

    How the atlas is maintained

    Where the atlas's pages live, how the build reads the code, how to tell which pages the code has moved under, and how to update and publish it.

    What it is made of#

    The atlas lives in docs/atlas next to the code it describes, so a change to one can come with a change to the other in the same pull request.

    PathWhat it is
    pages/*.htmlOne file per page: a JSON header, then the page's HTML. The file name only sets the reading order on disk. The header's part and order set the order in the atlas.
    partials/*.htmlDiagrams used on more than one page or too long to keep inline. {{uid}} in a partial is replaced each time it is included, so marker ids never clash.
    src/The shell, the stylesheet and the page script that every page shares.
    atlas.jsonThe title, the repository URL that code links point to, and the parts.
    atlas.mjsThe build. Node 22 and git, no packages.
    site/index.htmlThe built atlas: one self-contained file. Open it from disk or serve it anywhere. It is committed, so reading it never needs a build.

    A page's header#

    Every page starts with a comment holding JSON:

    • verified is the commit the page was last checked against, line by line. Set it only after reading the code at that commit.
    • sources are the files and directories the page describes. A commit that touches any of them after verified marks the page as moved.
    • status: "planned" with a scope list renders a placeholder that says what the page will cover.

    Elements that read the code#

    The build replaces these elements before writing the page. Anything that names code is resolved against the working tree, and links are pinned to the commit that was built.

    ElementBecomes
    <x-ref path="…" symbol="…">text</x-ref>A link to the first line in the file containing symbol. Without symbol, a link to the file. A path ending in / links to the directory.
    <x-code path="…" start="…" [end="…" | lines="n"] [doc] [max="n"] [caption="…"]/>An excerpt with highlighting and line numbers. It starts at the first line containing start and runs to the line containing end, or for n lines, or by default to the brace that closes the block. doc includes the comment above it.
    <x-packages names="a,b"/>, <x-packages rest/>Package cards with size and doc comment, read from the code. rest lists every engine package that no other x-packages mentions, and the build reports it.
    <x-stat name="…"/>A number counted from the repository: go-lines, engine-packages, connectors, migrations, api-operations and others in stats.
    <x-page id="page[--section]">text</x-page>A link to another page or section, with the page's title when there is no text.
    <x-include name="file.html"/>A partial.

    Attribute values are matched literally. Write &quot; for a quote inside one, as in start="if is(&quot;worker&quot;) {".

    The page script also understands a few classes: callout drift for spec and code that disagree, callout risk, callout note, evt for an event name, stepper with stage items whose data-lit lights the diagram groups marked data-stage, and data-go="page" on any diagram group to make it open that page.

    Keeping it current#

    Run these from the repository root:

    CommandWhat it does
    make atlasBuilds docs/atlas/site/index.html and docs/atlas/dist/artifact.html, and prints every reference that no longer resolves.
    make atlas-staleLists each written page and how many commits have touched its sources since it was checked, with the files.
    node docs/atlas/atlas.mjs checkBuilds in memory and fails if any reference is broken. Use it before committing.

    To bring a page up to date: run make atlas-stale, read the diff of the listed files since the page's verified commit, change what the page says, set verified to the commit you checked, then rebuild. Code excerpts and line links update themselves. Prose, tables and diagrams are what need a person.

    What the checks cannot see

    An excerpt anchored on a symbol keeps working when the code around it changes. A broken anchor is reported, but a change in meaning is not. And a later migration that redefines a SQL function is not noticed while the old migration still exists. That is why each page also lists its sources and turns amber when they change.

    Publishing#

    site/index.html is the atlas. Commit it with the change that updated a page. dist/artifact.html is the same atlas without the document wrapper, for hosts that add their own, such as a claude.ai artifact. It is not committed.
