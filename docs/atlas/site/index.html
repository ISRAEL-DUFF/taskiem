    Engineering atlas

    How Taskiem is built, checked against its code.

    Taskiem is a workflow engine that businesses trust with money movement: durable runs, exactly-once payments, approvals and an audit trail, with connectors for African payment and identity providers. This atlas explains it one feature and one component at a time. It is written for the engineers who maintain it.

    219,916 lines of Go outside tests80 engine packages44 connectors153 migrations

    The system on one page#

    Everything runs from one Go binary. Each box below is a role it can run as, and PostgreSQL in the middle holds the state, the work queue and the audit log. Select a box to read about it.

    Four ideas the rest depends on#

    The history is the run#

    A run is an append-only list of events in run_events. A pure function, decide(), reads that list and returns the next events. It reads no clock and no randomness, so replaying a history always produces the same decisions.

    Follow one run

    Postgres is the queue#

    Tasks, timers and waits are rows. Workers claim them with FOR UPDATE SKIP LOCKED and hold a lease with an epoch number. Every write a worker makes is checked against that epoch, so a stalled worker can never overwrite the result of the worker that replaced it.

    Durable execution

    Intent before effect#

    Before any call that moves money, the worker commits an EffectIntent carrying a key derived from the run. After a crash, the engine knows a call may have gone out, and the connector's action class decides whether to retry, reconcile or stop for a person.

    Exactly-once effects

    The database enforces tenancy#

    Every transaction sets app.tenant_scope, and row-level security checks it on every tenant table. Work that crosses tenants, such as claiming tasks, goes through a few SECURITY DEFINER functions that return only routing columns.

    What Taskiem is#

    Taskiem runs workflows for businesses whose workflows move money. A workflow is a versioned JSON document in the wd/v1 format. It can be drawn on the canvas, written as TypeScript, drafted by the AI builder or built from WhatsApp, and all of these produce the same document. A run of that workflow is an append-only log of events in PostgreSQL. Workers carry out the steps: calling Paystack or Moniepoint, running sandboxed code, asking a model. Every call that moves money carries an idempotency key derived from the run, so a crash or a retry never pays twice.

    The spec names four kinds of customer (spec 1.1):

    SegmentExampleWhat they need from it
    Regulated fintechs and microfinance banksLenders, payroll providers, walletsMoney flows with audit trails and approvals
    SaaS companiesPayroll, HR and accounting toolsAutomation embedded in their own product for their customers
    Small and informal businessesRetailers, cooperatives, agentsSimple automations run from WhatsApp
    Internal operations teamsPortfolio companies of the holding companyBack-office glue without writing services

    The engine is the core, but the repository has grown well past it. It now holds chat channels (WhatsApp, Telegram, USSD, inbound email), a money layer (a money log of every movement on a business's rails, matching payments to invoices, receiving money, reports), a Schools product, and public storefronts and hosted forms. The README puts the project in Phase 2 (hardening). The docs/phase-*-status.md files record later product work as built or in review, and gated on go-live.

    One binary, seven roles#

    taskiem serve --role ROLE (or TASKIEM_ROLE) chooses what a process does. all, the default, runs every engine role in one process, which is how a small install runs. A larger one runs each role on its own and scales each separately. Every role shares one engine built by newEngine: the database pool, the store, the secrets vault, the connector registry and the WebAssembly connector runtime. The exceptions are public and mail. They load a smaller configuration and connect with their own database login, so a fault in the public pages cannot reach engine data.

    RoleWhat runs in it
    apiThe REST API for the web app, CLI, SDKs and partners, plus the web app's static files and the embedded builder's bundle. Also a set of background loops: Git sync, the WhatsApp and USSD sessions, storefronts and their orders, hosted forms, invoices, the inbound email drain, the self-repair queue (when a model is configured) and the outbound SMS and email sender. Lists and dashboards read from a replica when TASKIEM_DATABASE_READ_URL points to one.
    edgeIngest. /hooks for webhooks, connector events and run callbacks, /git-hooks for pushes, and /channels/… for the platform's WhatsApp number, Telegram bot, Slack interactions and USSD aggregators. In all mode the api listener serves /hooks as well.
    orchestratorSweeps runs that were left with events nobody decided on, every 100 ms. It is the scheduler type with SweepOnly set, because most decisions run inline in the transaction that appends the event.
    schedulerFires timers, recovers expired leases, sweeps, admits queued runs, purges runs past retention and creates event partitions. It also runs the cron triggers and about fifteen other periodic jobs: alerts, hourly secret-read digests, partner webhooks, billing, domain and embed-site checks, tenant key health, data-table token renewal, the Paystack event poller, storefront reopening, the money-log and schools mirrors, money summaries, the canary and audit anchoring.
    workerOne worker loop per queue named in TASKIEM_WORKER_QUEUES (by default connector,sandbox,ai). The container queue brings up the container runner and its egress proxy. A worker can serve a dedicated pool for chosen tenants or plans.
    publicThe public host for storefronts and hosted forms. It connects as taskiem_public and never builds the engine.
    mailThe SMTP server for email triggers. It accepts mail only for known addresses and leaves it sealed in an inbox for the api role to read.

    Spec and code differ

    The spec lists five roles (spec 2.1). The code adds public and mail, which the spec only mentions as a proposal. The spec also says schedulers are leader-elected with a session advisory lock (spec 2.3). The code has no leader election. Instead, the scheduler is written to be safe when several run at once: every claim uses SKIP LOCKED and every timer firing is guarded by fired_at. Running several schedulers costs some duplicated work and nothing worse.

    Starting and stopping#

    runTasks runs every loop a role needs as a goroutine. If any loop returns an error, the whole process stops so its supervisor (systemd or Kubernetes) restarts it clean. On SIGTERM, drainOnShutdown fails readiness at once, keeps serving for a delay so load balancers stop sending traffic, and only then stops the loops. Workers let calls already in flight finish (TASKIEM_WORKER_DRAIN, 30 seconds by default) and hand their leases back, so their tasks can be claimed again at once. Every role serves /metrics, /healthz and /readyz on the metrics listener, so roles without an HTTP API can still be probed.

    The architecture map#

    Requests come in at the top. The front roles verify and record them. Nothing important happens in memory: an accepted webhook is already a committed run with its first decision made when the caller gets 202. The core roles pick up work from PostgreSQL, and only workers call out. Every outbound connection, whether a connector call, an HTTP step, a fetch from the sandbox or a database connection, dials through the egress guard.

    Where the spec and the code disagree#

    These are the differences found so far. Each is explained where it matters.

    1. Seven roles, not five, and no scheduler leader election (above).
    2. decide() returns events, not commands. Life of a run
    3. A worker writes StepStarted only for steps that write. Read steps go straight from scheduled to completed. Life of a run
    4. The attempt group, and with it the idempotency key, moves on automatically when a reconcile finds that a payment never happened. The contract says so and the spec's own section 4.4 is out of date. Life of a run
    5. The spec's example workflow uses smileid@2. There is no such connector. Identity checks go through youverify, prembly and dojah.
    6. Several tools named in the stack table are not used (above).
    7. There are 288 SECURITY DEFINER functions that bypass row-level security, not the spec's four. Data model
    8. Large outputs are never moved out of the database: payload_ref is unused and outputs over 256 KB are refused or cut. Durable execution

    These were differences and have been resolved, in the code or by correcting the spec (findings 1 to 5):

    • Postgres is the queue by design. The spec no longer promises an interface to swap for NATS JetStream.
    • Cancelling a run reverses its completed steps (decision 0054). Durable execution
    • Runs past retention can be archived to an S3-compatible bucket, not only a local directory.
    • A run waiting on a timer, signal or approval has status waiting. Run statuses
    • Publish approval can be required per environment. Workflow definitions
    • An operator's retry on a parked write gets a new idempotency key. Exactly-once effects
    • Code steps cannot write through fetch, and seeds inside a foreach must differ per item. Exactly-once effects
    • The cross-tenant functions are pinned to an owned allow-list. Data model

    The code also goes past the spec in places. Workers claim tasks fairly across tenants, with a concurrency cap per tenant and dedicated worker pools. Runs over a tenant's limits are queued and admitted later instead of being refused. The Durable execution page covers both.

    The life of a run

    One webhook followed from the edge, through three transactions and a payment, to the end of the run: what is written where, and what happens when something fails along the way.

    Checked against 80997cf · 2026-10-28

    The fastest way to understand Taskiem is to follow one run from start to end. This page follows the spec's own example, a workflow that pays out an approved loan. It starts with a webhook, checks the borrower's BVN, waits for a credit officer's approval, sends the money with a Paystack transfer, and ends. Each stage names the function that does the work and the rows it writes, so you can open the code beside it.

    The workflow#

    This is the definition as the spec gives it (spec 3.1). Three things matter for this walkthrough. verify_bvn only reads. approve waits for a person. pay moves money, and its effect.idempotency_seed ties the payment's key to the loan rather than to the run, so even a second run for the same loan cannot pay it twice.

    Spec and code differ

    No smileid connector exists. In this repository a BVN check would use youverify@1's verify_bvn, which is also a read action. Nothing below depends on which one is used.

    The pay step calls Paystack's transfer action. Its manifest declares the action class and how the idempotency key is encoded to fit Paystack's reference format. It also names verify_transfer as the action that can ask Paystack, after a crash, whether a transfer happened.

    Follow the run#

    Select a stage to light up its part of the sequence. T1, T2 and T3 are database transactions. Everything a stage writes commits together or not at all.

    1. The delivery reaches the edge#

      The provider posts to /hooks/{tenant}/loans/approved. receive checks the tenant exists and is active, and applies the tenant's two ingest rates. Above the hard ceiling the caller gets 429 with Retry-After. Above the soft rate the delivery is accepted but the run will be queued. The body is capped by the tenant's plan.

      webhook then finds the trigger registered at that path, checks the method and CORS, and verifies the signature: HMAC, basic or JWT (verifyCall). It validates the body against the workflow's inputs schema (422 if it does not match). It computes a dedup key, by default a hash of the body, or the trigger's own expression. The whole request runs under a 5-second budget.

    2. T1: the run starts and is decided#

      Store.Start opens one tenant-scoped transaction, and startIn does everything else inside it. It checks the tenant is active. It inserts into trigger_receipts: if this (trigger, dedup key) was seen before, it returns the original run with duplicate: true and writes nothing more. It then checks billing, quotas and the tenant's hold (tenantHold), inserts the runs row, pins the connector versions and approval policies the run will use, seals personal data, and appends RunStarted.

      If the run is admitted, start arms the run's timeout timer and calls decideInline in the same transaction. That makes the first decision, StepScheduled for verify_bvn, and inserts its tasks row. Only then does the transaction commit and the caller get 202 with the run id.

      RunStartedStepScheduledtrigger_receiptsrunstaskstimerstenant_usage

    3. The worker wakes and claims the task#

      A trigger on tasks calls pg_notify('taskiem_tasks', queue), which wakes idle workers on that queue at once; polling every second is the fallback. Worker.Run has one claimer feeding a fixed set of executors, and it only claims as many tasks as it has free executors.

      The claim calls taskiem_claim_tasks, a SECURITY DEFINER function that can see every tenant's tasks but returns only routing columns. It takes ready tasks with FOR UPDATE SKIP LOCKED, sets a 60-second lease, and increments lease_epoch. That epoch is the fencing token for everything the worker writes about this task. A heartbeat extends the lease while the step runs.

    4. T2: intent is recorded before anything is sent#

      prepare reads the run's history inside the tenant scope. It finds the step's StepScheduled, notices if the step already has an outcome or was cancelled, and resolves the connector action and its class. verify_bvn is a read, so the worker goes straight to the call, with no intent and no StepStarted.

      For pay, a write, the worker derives the idempotency key from the tenant, the seed (here the loan id), the step and the attempt group. It looks at what earlier attempts left behind, then recordIntent checks the fence, locks the run, makes sure the step was not cancelled meanwhile, and appends StepStarted and EffectIntent with the key and a digest of the input. This commits before the call.

      StepStartedEffectIntent

    5. The call to Paystack#

      send resolves secrets and the connection's credentials. It puts the encoded key in the reference field and calls the action through an HTTP client that dials only through the egress guard. For a write, the call must start before the intent's time plus the call timeout, 30 seconds by default (decision 0009). If that deadline has passed, nothing is sent and the attempt fails as not sent, which is always safe to retry.

      The output is compared with the manifest's schema, and any difference is recorded as connector drift. Errors are classified as retryable, fatal, not sent or unknown outcome. The class of the action decides what each of those means.

    6. T3: the outcome is recorded and the next step decided#

      finish releases the task under the fence. If another worker holds the lease now, it records nothing. It scrubs any secret echoed in the output, records a settled payout in the money log, seals personal data, and appends StepCompleted (or StepFailed).

      In the same transaction it calls decideInline. After verify_bvn that writes ApprovalRequested and an approvals row. After pay it writes RunCompleted. finish retries across a database failover: repeating a finish that did commit is fenced out, so it can never record twice.

      StepCompletedApprovalRequestedapprovals

    7. Waiting costs nothing#

      While the approval is open, nothing runs. There is only a row in approvals and, if the step has a timeout, a row in timers. When the credit officer approves, from the web app or WhatsApp, DecideApproval locks the run, checks the approval is still open, appends ApprovalDecided, and decides inline. That writes StepCompleted for approve and StepScheduled for pay. Signals and timers wake runs the same way: one transaction appends the event and makes the next decision.

      ApprovalDecidedStepCompletedStepScheduled

    8. The scheduler is the safety net#

      Every 250 ms Scheduler.Tick fires due timers (the approval's timeout among them), makes expired leases claimable again, and sweeps runs that have events nobody decided on, which happens after a crash between append and decide. It also admits runs that were queued behind tenant limits, purges runs past retention every ten minutes, and creates run_events partitions every hour.

    9. The run ends#

      When decide finds nothing left to do, it writes RunCompleted. applyEffects calls endRun, which sets the status and the retention date, releases the run's concurrency slot, and admits the next run that was waiting for that slot.

      RunCompleted

    Spec and code differ

    The spec says StepStarted is written when "a worker claims the step's task" (spec 4.1). In the code a worker writes it only in recordIntent, so only for steps that write. That is why verify_bvn has no StepStarted above. decide also writes StepStarted for control steps (branch, parallel, foreach) to record which path or how many items it took. A run inspector that treats StepStarted as "a worker picked it up" will be wrong for reads.

    How a decision is made#

    decide is a pure function of the definition and the history. Its package comment states the rule that everything else depends on:

    Retry backoff needs jitter but cannot use randomness, so backoff derives it from a hash of the run id and the step. Replaying a history gives the same delays.

    decideInline is where the pure function meets the database. It locks the run row, folds the history (from an in-process cache of up to 2,048 runs, so a busy run is not re-read from the start every time), asks for the next events, and appends each one with applyEffects turning it into rows: a task, a timer, a signal wait, an approval, a child run. Some effects cause new events. For example, a signal that arrived early and was buffered is delivered as soon as the run starts waiting for it. So the loop runs again, up to 16 rounds, until nothing new happens.

    Spec and code differ

    The spec describes decide as returning commands (ScheduleStep, StartTimer and so on) that are then turned into events (spec 4.2). The code skips that layer. decide returns the events themselves (NewEvent), and applyEffects derives the rows from each event's type. One less translation step means one less place where a replay could come out different.

    Each decision also counts the steps it scheduled. A run that goes past its plan's max_steps_per_run, for example a runaway foreach, is failed in the same transaction, so no step over the cap ever reaches a worker (countSteps).

    How work is claimed fairly#

    Claiming is the one place where a worker has to see every tenant's tasks. It is done by a function owned by the taskiem_dispatch role, so the worker's own login never needs to bypass row-level security. The function does more than the spec asks. It walks the distinct tenants that have ready tasks (a loose index scan, so it stays fast with many tenants). It keeps only tenants routed to this worker's pool. It caps each tenant at its concurrency limit, counting leases it already holds. It then takes tasks round-robin across tenants, so one tenant's backlog cannot starve the others.

    The worker then does all of its real reading inside an ordinary transaction scoped to that one tenant, through db.InTenantTx, which sets app.tenant_scope for row-level security to check.

    Intent, fencing and the call deadline#

    Three mechanisms together make the payment safe, and recordIntent is where they meet. The fence is the first statement. The run lock stops a cancellation from slipping in between the check and the write. The intent records the key and a digest of what is about to be sent.

    The fence itself is a single function call that only succeeds while this worker still owns the task at this epoch. Every write a worker makes about a task goes through it.

    One document, many editors#

    A workflow is one JSON document in the wd/v1 format. The canvas, TypeScript workflow code, the AI builder, the WhatsApp builder, the template gallery and Git sync are all editors of that document. None of them keeps a format of its own. The runtime reads only this document, so whatever produced a workflow, it runs the same way.

    The contract is docs/contracts/wd-v1.md plus the JSON Schema schemas/wd-v1.schema.json. The Go model is in engine/wd/model.go:

    Run-level settings are short: timeout, concurrency_key, max_concurrency and retention. Canvas positions are not part of the definition. They live in a separate layout column that can change without making a new version, so moving boxes around never needs a publish approval.

    Step types#

    The schema allows 18 step types: connector, code, container, http, branch, parallel, foreach, wait, signal, approval, subflow, transform, ai, form, capability, template, callback, respond. They differ in who carries them out:

    Every step can have needs (steps it waits for), when (a condition), retry, timeout, on_error (steps to run if it fails), effect (the idempotency seed) and compensate (the action that undoes it).

    Inside a foreach, validation refuses a write whose seed is the same for every item, since each item would then share one key and only the first would happen (seedPerItem).

    Spec and code differ

    The spec lists 15 step types and marks form as proposed (spec 3.2). The code has form built and adds container, capability and template. Capability and template steps change what "the definition" means at run time: the version that is published is not the exact graph that runs. The run pins its expansion (runs.expansion), and the run inspector has to show the expanded steps.

    Expressions#

    A string that starts with = is a CEL expression. CEL has no side effects, cannot loop forever, and has a bounded cost, so it can run inside decide without breaking determinism. Each evaluation is capped at a cost of 1,000,000, and compiled programs are cached per process in a bounded cache.

    The rules that publishing enforces (checkExpressions):

    • Every expression compiles.
    • steps.<id> may only name steps that are certain to have finished first (rule 5). You cannot read a step in a parallel branch you are not waiting for.
    • item and index exist only inside a foreach.
    • An expression that reads secrets reads nothing else (rule 10, decision 0010). Secrets are resolved by the worker at execution time, so their values never enter history. Mixing them with data would force them into the decision.

    Versions, environments and publishing#

    Every save makes a new immutable version. A database trigger refuses changes to definition or digest once a version exists (00003). The digest is a SHA-256 of the canonical JSON (canonical). Runs pin the version they started on, so editing a workflow never changes a run in flight.

    Versions move through draft, published, deprecated and archived. Each environment (dev, staging, prod, or the tenant's own) runs its own version, recorded in deployments. Publishing deploys to every environment not gated on another. A gated environment only takes a version by promotion from the environment it names. Promotion copies the version and never edits it (00024).

    When a tenant turns on four-eyes publishing, a person asks to publish and a different person approves. API keys cannot ask. Every path that publishes checks the setting: the web app, chat, Git sync, AI repair, partner packages and receive-money (publish).

    The approval can be required in every environment or only in the ones the tenant names, governance_settings.four_eyes_publish_environments, so prod can need a second person while dev publishes freely. A publish needs approval when any environment it deploys to is on the list. Promoting into a listed environment, and connecting Git to one, need it too (approvalNeeded, spec 3.4).

    Code, canvas and Git#

    Workflow code#

    A *.flow.ts file describes the same document with a builder. Arrow functions over the expression context compile to CEL, so authors get TypeScript's checking without the engine running TypeScript at run time:

    taskiem build compiles code to definitions and taskiem codegen goes the other way. Both run inside the Go binary: the SDK is embedded, bundled by esbuild and executed in the QuickJS sandbox, so neither the CLI nor the API needs Node (engine/flowcode). The repository's example and dogfood workflows are kept as both files, and CI validates the definitions.

    Concurrent edits#

    Each save names the version it was based on. If someone else saved in between, wdmerge merges the two three ways against that base. The unit is a top-level field or a top-level step with everything nested in it. Two edits to different steps merge cleanly. Two different edits to the same step are a conflict for a person, never a guess.

    Git#

    Each environment can be connected to one repository on GitHub, GitLab or Bitbucket (engine/gitprovider), in one of two modes (docs/git.md):

    • Platform-led: Taskiem is the source of truth. Publishing a version also opens a pull request with the definition and its generated .flow.ts, so the repository keeps a reviewed history. Publishing does not wait for the merge.
    • Git-led: the repository is the source of truth. A push to the connected branch, received on the edge's /git-hooks, saves and publishes the changed definitions to that environment and loads approval policies kept in the repository. Those workflows are read-only in Taskiem.

    Making an environment Git-led hands its deploys to whoever can push to the branch. So when a tenant's governance is strict (four-eyes publishing or policies, or a gated environment), setting up or changing a Git-led connection needs one person to ask and another to approve, and an API key cannot do it. After that, pushes deploy without a second approval in Taskiem. Review happens in the repository. Git credentials are tenant secrets in a reserved environment that workflows cannot read (api/git.go).

    Testing workflows#

    A workflow test (*.test.json, the wd-test/v1 contract) gives a trigger, mocked step outcomes, signals, approval decisions and form answers, and asserts the path the run took and its outputs. Tests run the real decide over an in-memory history on a virtual clock, so a test of a 72-hour signal timeout takes milliseconds and never calls a provider (engine/wdtest). taskiem test runs them offline, and the AI repair pipeline uses the same machinery for its shadow runs.

    Templates#

    The template library holds 78 ready workflows for small businesses ("every Friday, text my customers who owe me"). Each is a wd/v1 definition with typed parameters, embedded in the binary (templates). Parameter substitution is injection-safe: inside an expression a value becomes a quoted CEL literal, and no value may start with =, so a parameter is always data, never code. Personal data such as an owner's phone number is never a parameter. Templates read it from tenant variables, so no definition carries it.

    Durable execution

    How a run survives crashes: the event log, the pure decision function, the Postgres task queue with leases and fencing, timers and signals, retries and compensation, admission, subflows, forks, and retention.

    A run in Taskiem must survive any process dying at any moment without losing work or repeating a payment. This page explains the machinery that makes that true. The life of a run follows one run through it. This page takes each part in turn and covers the cases that one run does not reach.

    The run is its event log#

    Every run has an ordered, append-only list of events in run_events. Nothing else describes what a run has done. The runs row holds a status, counters and leases for quick lookups, but the history is the source of truth. The application role can only SELECT and INSERT on run_events. UPDATE and DELETE are never granted, so even a bug cannot rewrite history.

    Events are appended through taskiem_append_event. It increments runs.last_seq and inserts the event at that number in one statement. The UPDATE takes the run's row lock, so two transactions can never give out the same sequence number, and there are never gaps.

    run_events is partitioned by month on the run's start time, not the event's time, so all of one run's events sit in one partition. The scheduler creates partitions three months ahead every hour (taskiem_ensure_run_event_partitions), and a test checks that partitions cover new runs.

    Deciding: a pure function, run where the event lands#

    decide.Decide(definition, history) folds the history into per-step facts and returns the events that follow. It reads no clock. Its notion of "now" is the recorded_at of the latest event, so time enters only through the log. Retry jitter comes from a hash of the run id, step and attempt, not from randomness.

    Determinism is tested, not assumed. decide.Verify replays a recorded history and checks that every block of decide-written events is byte-for-byte what decide produces from the events before it. TestDeterminismSuite runs it over real runs, and the crash and PII suites also call it.

    There is no separate orchestrator in the common case. Whoever appends an event decides in the same transaction: ingest after RunStarted, the worker after an outcome, the API after an approval, the scheduler after a timer. The orchestrator role exists for the leftovers. Any run whose decided_seq is behind last_seq is found through a partial index and decided by the sweep.

    Folding a long history on every event would be slow, so each process keeps the folded state of recent runs in a cache (up to 2,048 runs). Only events committed before the deciding transaction began are folded into it, so a rolled-back decision cannot leave phantom events behind.

A run backing off before a retry has its task queued, so it shows running. Waiting runs still count against the plan's running-runs limit and in usage figures.

    Waiting: timers, signals, callbacks, approvals#

    Timers#

    Timers are rows in timers with a kind: wait, signal_timeout, approval_timeout or run_timeout. Every tick, the scheduler claims due timers through taskiem_claim_due_timers. For each one it opens a tenant transaction, marks the timer fired only if fired_at is still empty, appends TimerFired, and decides inline. The fired_at guard makes it safe for several schedulers to run at once.

    Signals#

    A signal step waits for an event and a correlation key in the run's environment. Waiting and delivering both take a transaction-scoped advisory lock on (tenant, environment, event, correlation), so a signal can never slip between "is anyone waiting?" and "I'm waiting now" (signalLock).

    • Delivery to waiting runs is a broadcast. Every run waiting on that key gets SignalReceived (deliverSignalTx).
    • A signal that arrives before anyone waits is buffered in signals for seven days. A buffered signal is consumed by the first run that starts waiting, oldest first (registerWait). So the same signal reaches every waiter if they are already waiting, but only one if they start later. Workflows that rely on signals should not depend on more than one run receiving the same one.

    Callbacks and approvals#

    A callback step gives the outside world a unique URL with a secret key to call the run back. The key is sealed in history like personal data. Approvals are rows in approvals, with policy snapshots taken at run start. A decision arrives through the API or a chat channel, is appended, and is decided inline. The Governance and compliance page covers policies and levels.

    Retries, errors and compensation#

    A worker classifies each failure (the Exactly-once effects page has the rules). decide then applies the step's retry policy:

    • Default policy: three retries, exponential from 2 seconds, capped at 5 minutes, plus up to 20% jitter. Code steps get no retries by default.
    • A provider's Retry-After wins if it is longer, up to an hour.
    • max_duration bounds the total time across attempts.
    • When retries run out, finalise fails the step. If any attempt was a write that may have taken effect, it parks it instead.
    • A failed step runs its on_error steps if it has them. Otherwise the run fails, after compensate has run the compensate action of every completed step that declares one, newest first. A compensation that fails parks the run rather than looping.

    Cancelling#

    Cancelling reverses a run by default (decision 0054). cancelTx appends CancelRequested and decides, and cancelRun takes it from there:

    1. It withdraws every step that started and has not finished (StepCancelled). Approvals, timers, signal waits and forms close.
    2. It cancels, reversing them too, the child runs its subflow steps wait for (childrenToReverse). The children are cancelled after the parent's decision is written, so a child that ends at once is heard in the next round.
    3. It waits for writes already under way, for a write parked for a person, and for each child to end.
    4. It runs the completed steps' compensations, newest first, exactly as a failure does, then appends RunCancelled naming who cancelled it and what was reversed.

    POST /v1/runs/{run}/cancel with {"reverse": false} ends the run at once instead, leaving completed steps as they are. A queued run, which has done nothing, is always cancelled at once.

    Subflows#

    A subflow step starts another workflow of the same business as a child run, in the transaction that records the step (startSubflow). The child inherits the parent's idempotency seed plus the step, so resuming the parent never repeats the child's writes.     Retention and archiving#

    When a run ends, endRun sets retain_until from the workflow's settings.retention, the tenant's default, or the platform default, capped by the plan. HTTP steps cut responses to the same size, and container steps keep their own limit. History can no longer bloat, but a workflow that needs a large output has to return only the fields later steps use.

    What is promised, and on what terms#

    Delivery is at least once. Any step can run twice, because a worker can die after doing the work and before recording it. Taskiem makes the effect happen once by knowing, for every action, what is safe to do when it is unsure whether an earlier attempt reached the provider. That knowledge is the action's class, declared in the connector's manifest. The class alone decides retry behaviour.

    The guarantee therefore depends on the provider. With an idempotency key the provider honours, or a way to ask whether something happened, Taskiem can make an effect exactly-once. With neither, it guarantees at most once: it stops and asks a person rather than risk sending twice.

    Steps that are not connector calls#

    The worker gives every step a class before running it (resolveExecutor):

    • container: unsafe_write unless declared otherwise.
    • ai: a read.
    • code: a read. A code step can therefore only read: host.fetch sends GET and HEAD alone (below).
    Resolved: findings 1

    A code step records no intent, so a worker that died after a POST from a script would run the script, and the POST, again. Since findings 1, host.fetch refuses every method but GET and HEAD before the request leaves the sandbox, in JavaScript and Python (errFetchWrite), with a message that points to an http or connector step, which declare a class and carry a key. TestCodeStepWritesNeverSent crashes, stalls and kills workers around a code step that tries a POST: none reaches the provider. Letting code steps declare a write class and record an intent is left for a later decision.

    Keys: derived, never random#

    An idempotency key is a function of where the effect sits, so every retry and every replay produces the same key:

    • Seed: the step's effect.idempotency_seed if it declares one (say a loan id), otherwise the run id.
    • Step: the step instance id (pay_all[3].pay_employee inside a foreach), or the plain step id when a seed is declared.
    • Attempt group: starts at 0 and changes only when the engine knows the earlier key's effect did not happen (below).

    The digest is then encoded to fit the provider's reference field, as the manifest's idempotency block says: base32_lower, hex_lower or base64url, a length, a prefix and the provider's limits. Spec.Validate refuses an encoding that keeps fewer than 128 bits, or one whose prefix or alphabet the provider would reject. Paystack's transfer gets tsk_ plus 32 base32 characters (160 bits). Fixed test vectors in engine/effects/testdata/vectors.json pin the derivation. Only the Go tests use them today. Any second implementation, such as a TypeScript one, should be checked against them too.

    Connectors without an idempotency block, and http and container steps, use a default encoding, which an http step can send in a header.

    Resolved: findings 2

    When a step declares a seed, the key leaves out the instance id (decide.go), so a seed the same for every item of a foreach would give every item one key, and the provider would pay only the first. Validation now refuses a seeded step inside a foreach, at any depth, whose seed reads neither item nor index (seedPerItem), on save, publish and taskiem validate. Versions published before the rule are not re-checked; a read-only scan lists them.

    Seeds across runs, forks and subflows#

    • A business seed deduplicates across runs: a second run for the same loan produces the same key.
    • A fork keeps its parent's seed, so a step the parent completed is never paid again. A step the parent attempted and failed for good starts a new attempt group in the fork, so the provider does not just return its cached failure.
    • A subflow's seed is the parent's seed plus the step, so resuming the parent never repeats the child's writes.

    Intent, deadline, reconcile#

    The life of a run shows recordIntent. The intent records the key, its inputs and a digest of the request (IntentPayload), and it commits before the call. Two time rules from decision 0009 make the next part safe:

    • The call deadline. A write's call must start before the intent's time plus the call timeout (30 s), and it is cancelled at that deadline. A worker that stalls past its lease cannot wake up and send late.
    • Reconcile waits for the deadline. A provider's "not found" is trusted only after the original call's deadline has passed. Before that, the task is put back without spending a retry.

    The flow when a reconcilable write has an open intent:

    1. Wait until the earlier attempt's deadline has passed.
    2. Call the reconcile action with the key.
    3. Found: record StepCompleted with the provider's answer, marked as reconciled.
    4. Not found: move to the next attempt group, which gives a new key, record a new intent, and send.
    5. Error: a retryable error reconciles again later. Anything else parks the step.

    Connectors also receive the time the current key was first sent (KeyFirstSent). A provider that only deduplicates for a limited window can then report indeterminate once the window has passed, which parks the step instead of re-sending under a key the provider has forgotten.

    When a person has to decide#

    A parked step sets the run to needs_reconciliation and raises an alert. An operator has two tools:

    • CheckReconcile runs the action's read-only reconcile and shows what the provider says now, with personal data masked. It changes nothing.
    • ResolveStep settles the step in one of three ways. completed means it happened, with an output recorded. failed means it did not happen and should not be retried. retry means it did not happen and should be sent again, under a new key. The resolution is appended to history and to the tenant's audit chain, then the run is decided again.
    Resolved: findings 4

    An operator's retry is a person re-issuing the effect, so it sends under a new key, as the contract says (decision 0053). The resolution marks its event reissue, and the worker's next attempt moves to the next attempt group. A provider that kept a failure for the old reference cannot answer the new attempt from its cache. A re-issue does not count against the step's retry budget. The console asks the operator to confirm they checked with the provider first.

    One more kind of parking has nothing to do with providers. When a tenant's own encryption key (bring your own key) cannot be unwrapped, steps that need secrets park as key_unavailable. When the key works again, ResumeKeyParked resumes them, retrying or reconciling as the step had been doing, without spending its retry budget.

    Where the guarantee ends#

    • Unsafe writes are at most once. A dropped connection on an M-Pesa STK push or an airtime top-up becomes a person's job. That is correct, but at volume it is an operations cost to plan for.
    • The class is only as good as its manifest. A connector that calls an action idempotent_write when the provider does not actually deduplicate on that field will pay twice. The Connector framework page will cover how manifests are reviewed and tested.
    • Calls already in flight at the deadline. Decision 0009 says it plainly: the deadline bounds when a call can start, not when the provider finishes processing it. call_timeout must exceed the provider's own processing time, and worker and database clocks must agree.

    Rate limits and versions#

    A manifest's rate_limit (Paystack: 50 requests a second per connection) is kept by every worker together. takeRate draws a token from a bucket in connector_rate_buckets, in the same transaction that records the call's intent. When the bucket is empty the task goes back to the queue until a token is due: nothing was sent, no intent is open, and no retry is spent.

    A run keeps the connector versions it started with. RunStarted records them, and the worker resolves each step through Registry.Pinned, which loads an uploaded connector's recorded version even after a newer one is uploaded or the recorded one is disabled for new runs. A built-in has only the version in the running binary. A catalogue version that was revoked, or a partner's that is no longer shared, gives way to the newest, with a warning in the worker's log.

    Resolved

    Rate limits were declared but not enforced, and runs switched to the newest connector version mid-flight. Both were found while writing this page, and both are fixed.

    Spec and code differ

    The spec says third-party connectors "run out of process as WASM modules". They run in the worker's process, in wazero, with a fresh instance per call.

    WebAssembly connectors#

    A tenant, or a catalogue publisher, writes a connector in any language that compiles to WebAssembly. With Go and connectorsdk it is a manifest, Handle("action", fn) per action, and GOOS=wasip1.     A tenant uploads to POST /v1/tenant-connectors (tenantconnectors.go). The id must start x_, and the manifest goes through the catalogue's lint with tenant rules (Lint).     Resolved

    Uploads were only parsed and compiled, so a write could be labelled a read and retried freely. They now get the lint and the memory check. A conformance run is still for the catalogue only, since a tenant's connector ships no suite.

    Conformance suites#

    A connector's tests are recorded exchanges with the provider. conntest reads testdata/fixtures (a request and its response) and testdata/conformance (an action, an input and the output or error expected). Run serves the exchanges from a local server, in order, and refuses any other host. As well as pass or fail, it reports three things a reviewer needs: actions no case calls, idempotent writes whose key never reached the provider, and reads that sent something other than GET or HEAD. Ten built-ins have conformance suites. Paystack and others test with fixtures and capability cases instead.

    The public catalogue#

    A publisher ships a package: the manifest, the module, a licence, a source URL, its conformance suite, and an attestation that it is original work. The package is signed with the publisher's Ed25519 key over its format, id, version and digest (connpkg). On submission, Checker.Run checks, within three minutes:

    1. The signature.
    2. A strict lint (Lint): HTTPS only, no IPs, private names or wildcards, a read must not be named like a write, and personal fields must be declared.
    3. The module loads and stays within its memory.
    4. The licence is on the allow-list, and the attestation is given.
    5. Every host resolves to public addresses only.
    6. The version follows semantic versioning against the versions already published.
    7. Every case passes, every action is covered, and every write's key reaches the provider.

    A package that passes waits for a reviewer, who must not belong to the publisher, must tick every item on the checklist, and must leave a note (taskiem_catalogue_review). Installing it asks the tenant to consent to its hosts and writes, and an upgrade asks again when those grow (Compare). A revoked version stops resolving within 10 seconds, and every tenant that installed it is told.

    Drift#

    After every successful call the worker compares the output with the action's output schema (drift.Check). A wrong type, an enum value not listed or a missing required field is recorded in connector_drift, counted in a metric, raised as an alert, and offered to AI repair as a cause. The step still completes, because the output is what the provider said. The check is shallow on purpose: it ignores oneOf, formats, ranges and extra fields, and stops at 20 findings.

    JavaScript and TypeScript in QuickJS#

    JavaScript runs in QuickJS compiled to WebAssembly, from a vendored copy of fastschema/qjs (decision 0011). The fork makes four changes, each marked "Taskiem fork": a hard memory cap, an interrupt whenever the context is cancelled, no filesystem at all, and the run's logical time as the script's clock (runtime.go).

    When a workflow is validated, Compile strips TypeScript with esbuild into a single function and refuses anything that still calls require(, so a script cannot import a package. Compiled scripts are cached, 2,048 per process, keyed by a hash of the source.

    Run builds a fresh runtime for every execution, so nothing a script does to globals or prototypes reaches the next one (TestRunsAreIsolated). Before the script runs, a prelude removes QuickJS's own std and os modules and installs the one object a script may use:

    Errors come out in four kinds (classify): timeout, out of memory, output too large, and a script error with its first line. All are fatal. A code step is not retried, because running the same code on the same input gives the same failure.

    Python in CPython#

    Python runs CPython 3.12 built for WASI, embedded gzipped with its SHA-256 checked on load (pywasm). Each run is a new instance of the module, started with -I -S so it reads no environment, with no directories mounted and the run's logical time as its wall clock:

    The script and the host talk over JSON lines on stdin and stdout (pyIO.handle), and print goes to the step's logs. An import hook refuses socket, subprocess, threading and others (pythonBlocked). That hook only gives a clearer error. The boundary is WASI, which has no sockets to open.

    • CPU time is "metered by fuel". No fuel exists in the code: a script that waits on fetch uses its whole timeout.
    • "A warm pool of instantiated QuickJS runtimes per worker" is not built; each run starts fresh, as above.
    • Uploaded WebAssembly modules as code steps are accepted by the schema and refused by the worker (compileStep).

    What a script can reach#

    The host gives a script four things (Host): log, now (the run's logical time), secret (only the secrets the step declares) and fetch. runCode wires fetch through the same egress guard as connectors. The guard allows only the environment's hosts, resolves the name and refuses any private, loopback or metadata address before it dials the address it checked, so a DNS answer cannot change between the check and the call (Guard.DialContext). Redirects are checked the same way.

    Since findings 1, fetch refuses anything but GET and HEAD. A code step is recorded as a read, with no intent before it, so a write from one would be sent again whenever a worker died mid-step:

    Resolved

    Code gets "no clock except through host functions" (spec 7). QuickJS used to get the host's clock, so Date.now() was the time the step happened to run and differed on a retry or a fork. The fork now takes a wall clock (Option.Walltime), and Date is the run's logical time, the same as host.now() and Python's time.time() (TestDateIsTheLogicalClock).

    Secrets, and keeping them out of history#

    A script reads a declared secret as plain text through host.secret, so it can put it in a header. Taskiem cannot stop a script from printing or returning it. Instead, before the step's event is written, scrubSecrets replaces every value the step could read with [secret] throughout the output, logs and error, in plain, query-escaped and path-escaped form (TestCodeStepSecretsAndFetchCap). Connection credentials and secrets used in input expressions go on the same list.

    Risk

    The scrubber matches exact text, so a determined script can get a secret past it. Values under 6 characters are left alone (minScrub). A secret that is base64-encoded, reversed or split survives. Object keys are not rewritten, only values (scrubValue). The scrubber stops accidents, such as a token in an error message. It does not stop a tenant's own code from leaking that tenant's secret, and a script can also send it to any host on the allow-list. Both are the tenant's own data, so this matters most for who in a tenant may write code steps.

    Container steps#

    A container step names an image by digest. Tags are refused, so the image cannot change under a published workflow (ImageProblem). It takes defaults of 1 CPU, 512 MB, 5 minutes and 256 KB of output, up to 4 CPUs, 4 GB, 30 minutes and 1 MB.

    The runner is chosen by TASKIEM_CONTAINER_RUNNER (containerSetup). kubernetes is the production runner. local runs a process on the worker's own machine for development, and it needs a second variable to switch on because it is not a security boundary. Without either, container steps fail as not enabled. At start-up the Kubernetes runner checks that its namespace, registry allow-list, shim image and NetworkPolicy are in place.

    Each attempt is one Pod, with this security context:

    The input, the declared secrets and the proxy address go in a Secret owned by the Pod, so deleting the Pod deletes it. An init container copies in the shim, which runs the tenant's program, passes it the input, caps its output and logs, kills its whole process group at the timeout, checks the output is JSON, and prints one line: TASKIEM-RESULT and the outcome in base64. The worker reads the Pod's log, finds that line from the end (ParseOutcome), and turns it into a result:

    A Pod that could not pull its image or start counts as not sent, and is safe to retry. One that ran out of memory or past its deadline is an unknown outcome, which for the default unsafe_write class parks the step for a person. The Pod is always deleted, and every minute each worker removes Pods that a dead worker left behind (Sweep).

    Network#

    A container has no network unless the step asks for network: egress. Then the worker issues a one-time token for the proxy, valid only for hosts on both the step's list and the environment's, and revokes it when the step ends, which also closes its open connections:

    The proxy listens on port 3128 in the worker. It allows CONNECT tunnels and plain HTTP requests on ports 443 and 80, and dials through the same guard as everything else. The token is scrubbed from history like a secret. A write from a container gets TASKIEM_IDEMPOTENCY_KEY in its environment, so the program can pass it to the provider.

    Risk
    • The shim runs as the same user as the program, so a program can print its own result line. The docs say so. It matters only in that a tenant can lie to itself about its own step.
    • The worker reads at most (output + 16 KB) × 4/3 + 8 KB of log. The result line is JSON in base64, and Go's JSON escapes <, > and & to six bytes each. An output near its cap made mostly of HTML can therefore be cut off, and the step then ends as "no result", an unknown outcome. The escaping was confirmed; the whole failure was not reproduced.
    • Minutes are checked before a step starts, so one run can go up to 30 minutes past a plan's monthly allowance. Some failures record no elapsed time and are not counted at all.
    • The start-up check confirms the NetworkPolicy exists by name, not what it allows.

    Workflow code in the same sandbox#

    A workflow can be written in TypeScript as a *.flow.ts file instead of JSON. flowcode bundles it with esbuild, linked into the binary, against an embedded copy of the SDK, so no Node is needed. Only @taskiem/sdk and @taskiem/connectors can be imported. The bundle then runs in QuickJS with no fetch and no secrets, and returns the workflow definition as JSON, which is validated like any other. Through the API this runs in the API process, behind a gate of at least two at a time and half that per tenant (codeGate).

    Triggers, ingest and channels

    How work gets in: every /hooks route and how it is verified, registration with providers, platform apps routed by account, polling and cron, rates and back-pressure, and the WhatsApp, Telegram, USSD and email channels.

    Checked against 8141a20 · 2026-10-28No changes to its code since

    Ways in#

    A run starts, or a waiting run wakes, when something arrives from outside. The edge role takes HTTP from providers and callers. The scheduler role fires cron schedules and polls providers that send no webhooks. The mail role is an SMTP server. Chat and USSD are served by the edge under /channels/..., with the conversation logic in api/. Whatever the way in, the rule is the same as on the Life of a run page: by the time the caller gets an answer, the run is committed.

    3. Above the softer ingest rate the delivery is taken, but the runs it starts are queued and admitted later in order.
    4. A body over the tenant's cap gets 413.

    Signals to waiting runs are never throttled: a payment confirmation for a run that is already under way is always let through.

    Duplicates#

    A provider that does not hear back sends again. Each trigger has a dedup key: the manifest's expression for connector events (Paystack uses the event and the transfer's reference), or the SHA-256 of the body for a plain webhook. A second delivery with the same key starts nothing and answers "duplicate": true. The key is held in trigger_receipts in the same transaction as the run (store.go), so a crash cannot record one without the other.

    A key dedups for 30 days, well past any provider's retries. After that the same delivery is new again: the old receipt is taken over (insertReceipt). Every hour the scheduler deletes receipts past the window through taskiem_purge_trigger_receipts. That function fixes the window itself, so no caller can clear a fresh receipt and have a delivery replayed. The receipt is also the only replay defence for schemes that sign no timestamp (plain HMAC, bearer, basic and the secret schemes), so 30 days covers any retry period.

    Resolved

    Receipts were never deleted: the table grew with every delivery, and a body sent again months later was dropped as a duplicate.

    Registering triggers#

    Publishing a workflow version rewrites its triggers rows for each environment it deploys to, in the same transaction (SyncEnvironments, decision 0012). A webhook path is unique within a tenant and environment. A schedule fires in prod only. A USSD service code belongs to one workflow per environment. Form and email endpoints keep their public address across versions.

    Some providers must be told where to send events. engine/remote keeps those subscriptions in step with what is deployed (decision 0021). A deploy declares the subscription it wants and a removal marks it absent, both in the publishing transaction. Then a reconciler, every 5 seconds in the scheduler, makes the provider match. It creates, updates or deletes the subscription, adopts one it finds under its own name after a crash, and renews it before it expires. The signing secret goes in the vault before the row records the provider's id, so a crash in between cannot leave a subscription whose deliveries Taskiem cannot verify. Fatal errors back off from an hour to a day, transient ones from 10 seconds to an hour (backoff).

    One app, many tenants#

    For Slack, Meta and QuickBooks, a tenant connects through Taskiem's own app, and the provider sends every event for every customer to one address. appEvent verifies the delivery with the app's secret, reads the account it is about (a Slack team, a Meta page, a QuickBooks company), and finds every connection made for that account (decision 0051):

    Each matching tenant's own gate then applies, and the event is delivered as if it had come to that tenant's own address. An event for an account nobody holds is counted and acknowledged with 200, since a provider such as Slack wants plain success within three seconds.

    Routing trusts the account recorded on the connection. For QuickBooks that account is the company id, taken from the realmId in the OAuth redirect, which passes through the person's browser (manifest). So before a connection is saved, linking asks the provider about any field from the callback: it runs the connector's test action (QuickBooks' get_company) with the new token. If the provider refuses, the token is revoked and nothing is saved (oauthconnections.go). A manifest that takes fields from the callback must declare a test.

    Resolved

    The callback's realmId used to be saved unchecked. Someone who edited the redirect could register another company's id and receive that company's Intuit change notifications. The QuickBooks test now shows such a link refused.

    Two smaller points on this path. The per-app rate limit is spent before the signature is checked, so a flood of unsigned requests can cause the provider's real deliveries to get 429. The platform-client path counts only after verifying. And one target tenant that is suspended or over its ceiling fails the whole delivery, so the provider retries it for everyone. The others then see duplicates, which are dropped.

    Polling and cron#

    Some providers send no webhooks, and Paystack's can go missing, so a trigger can also poll. Every minute Poller.Tick calls the manifest's list action for each trigger whose interval is due, looking back 10 minutes past the last poll. Each record is signed with the connection's own secret and replayed through the hooks handler in-process, so the ceiling, dedup and signals all apply exactly as for a webhook. A record already delivered by webhook is a duplicate and does nothing. The first poll only marks where to start: nothing earlier is replayed.

    Cron runs in the scheduler every second. It claims due schedules with SKIP LOCKED, at most 10 per tenant in a batch of 100, and starts each run with the slot's time as its dedup key, so two schedulers cannot both start it (fire). A schedule missed while its tenant was suspended is skipped. After downtime a schedule fires once and moves on to the next time after now.

    Spec and code differ
    • Decision 0012 and the comment in cron.go say a schedule fires once "for its latest missed time". It fires for the earliest missed time, since that is the stored next_fire_at, and then skips ahead. The run's scheduled_time is therefore the oldest missed slot. No test covers it.
    • The spec gives the schedule's time zone as "the tenant's time zone". It is the trigger's own timezone, defaulting to Africa/Lagos.
    • The spec says webhooks get "202, never 5xx". A database or vault error answers 503 with Retry-After: 5, which is better: the delivery was not recorded, and a 202 would lose it.
    • The spec says signatures are checked "before touching the database". The tenant lookup and limits come first, and connector deliveries read the registry and vault before verifying. Only the app, platform, WhatsApp and Telegram paths verify first.
    • The database-change trigger in spec 8.1 is not built, and is refused at publish.

    WhatsApp#

    Taskiem has one platform WhatsApp number, and a business can connect its own. Meta's webhook is verified with HMAC-SHA256 over the raw body, and each message is claimed by its id before it is handled (waReceive). Handling is therefore at most once: an error after the claim is logged, and the message is not handled again.

    A person binds their number to their Taskiem account with a six-digit code sent as an authentication template, valid for 10 minutes. After that, converse finds the tenant, the person and their language, and continues the session. A session is idle, collecting inputs, waiting for "yes", or waiting for a step-up check before an approval. Starting a workflow from chat checks that the person may start runs, collects the inputs field by field or in a WhatsApp Flow (personal fields are sealed in the session), asks for confirmation, and starts the run with the confirmation's nonce as its dedup key.

    WhatsApp only lets a business send free text within 24 hours of the person's last message. Send sends text inside that window and an approved template outside it, or refuses if there is no template. A message that must arrive, such as a run's outcome, goes through an outbox that tries 8 times over about 18 hours and stores nothing personal. Buttons that approve or reject carry a signed, single-use token bound to the tenant, run, step and person.

    Spec and code differ

    Sessions expire after 30 minutes, not with the 24-hour window as spec 11.3 says. 24 hours is only the cap. A business's own number is connected by an admin by hand: embedded signup (spec 11.4) answers 501.

    Telegram, USSD and email#

    Telegram#

    Telegram works like WhatsApp and shares converse, with three differences. The webhook is checked by a secret header before the body is read. An account is bound by a one-time /start link that only someone who has proved their identity can make. There is no 24-hour window. Only private chats are answered.

    USSD#

    A USSD session is a phone menu: the network waits about two seconds per screen and drops the session after a few minutes. ussdCallback works to a two-second budget. It checks the channel's token and optional IP range, limits by tenant and by number, and walks the workflow's menu inline from the session, without starting a run. When the caller confirms, it locks the session, seals the caller and the inputs, answers with an 8-character reference, and starts the run in the background with the session as its dedup key. The outcome is sent by SMS.

    Spec and code differ

    Spec 8.4 hands "only side-effecting steps" to the engine and shows the result on the next screen. The code starts the whole run after confirmation and always sends the result by SMS. Given the two-second budget, that is the safer design.

    Email#

    The mail role is an SMTP server on port 2525 (mailTask). It connects as taskiem_public, the same limited role as the public host. It accepts mail only for known 12-character addresses on Taskiem's domain, checks SPF, DKIM and DMARC, and seals the message with a public key whose private half only the api role holds (Data). The api role drains the inbox every 2 seconds (handle). It drops auto-replies and bounces, answers forwarding confirmations, requires the sender to be aligned with DKIM or SPF when the trigger lists senders, scans attachments, and starts the run with the message's id as its dedup key. Addresses and bodies are sealed in the run's history.

    Languages and voice notes#

    Chat speaks English, Nigerian Pidgin, Yoruba, Hausa and Igbo (engine/lang). Everything but English is a draft. A person's chosen language wins, then one detected from their message, then the tenant's default. USSD and SMS get plain ASCII. A voice note is transcribed only if the platform has a transcription provider and the tenant turns it on (engine/voice). It is limited to 1 MB and 60 seconds by default, the recording is discarded after transcription, and the transcript is sealed and kept for 7 days.

    Risk

    A voice note goes to an outside transcription service, OpenAI's by default, which then processes a customer's voice. That needs to be in the data-processing terms and the privacy notice. Only Ogg files have their length checked. Other formats are limited by size only.

    Four kinds of caller#

A different prefix for each kind means one can never be taken for another: the tenant middleware ignores operator tokens, and the operator console refuses any Authorization header at all (operatorAuth).

    Signing in#

    A person signs in with a password, a passkey, or their company's identity provider over OIDC or SAML. There is no emailed sign-in link; emailed links exist only for invitations, password resets and verifying an address.

    • Password. Hashed with argon2id (2 passes, 19 MiB). An unknown email is checked against a dummy hash, so timing does not tell whether an account exists. Sign-in takes JSON only, which a cross-site form cannot send, and is limited per IP and per email: a burst of 10, then one try every 6 seconds (limiter).
    • Passkey. WebAuthn with user verification required, ES256, EdDSA or RS256. A signature counter that does not move forward marks a cloned authenticator and is refused (webauthn).
    • OIDC. Authorization code with PKCE, RS256, PS256 or ES256 only, with issuer, audience, nonce and expiry checked, and an unverified email refused (oidc.Verify).
    • SAML. Signed assertions, audience, recipient and time checked, and only in answer to a request Taskiem made: a response the identity provider sends unasked is refused (saml).

    Both SSO flows set a cookie that ties the callback to the browser that started it. finishSSO then requires the email's domain to be one the tenant has proved it owns through DNS, finds or creates the person, and keeps their roles in step with the identity provider's groups. A tenant can enforce SSO, which refuses its members password and passkey sign-in, except owners, so a broken identity provider cannot lock a business out. SCIM provisioning (/scim/v2) takes only an API key holding scim.provision, and can never make an owner.

    Risk

    A person signed in through SSO is matched to an existing account by email alone. The identity provider's subject is not recorded or checked (the operator console's SSO does pin it). The domain must be the tenant's, proved through DNS, so the reach is limited to people whose mailbox the tenant already controls.

    Sessions#

    createSession makes a fresh token for every sign-in, so a session cannot be fixed in advance, and records how the person signed in. The browser gets it as an HttpOnly, Secure, SameSite=Lax cookie that lasts 12 hours; a script or the CLI gets it as a bearer token instead, never both. A session is revoked on sign-out, on a password change or reset (all the person's other sessions), when their last role is removed, when SCIM deactivates them, and when a partner suspends the sub-tenant.

    A cookie session must send the X-Taskiem-Request header on anything but GET and HEAD. A cross-site page cannot add a custom header without a CORS preflight, and /v1 answers none, so the header is enough to stop cross-site requests (CSRF check).

    Roles are read from the database on every request (loadRoles), so removing someone's role takes effect at once even while their session lasts.

    Spec and code differ

    The spec says "Sessions are short-lived with refresh rotation; sensitive actions require recent authentication" (spec 13.2). A session lasts a fixed 12 hours with no refresh. Recent authentication is asked for only on specific operations, through step-up below.

    API keys#

    A key is tsk_key_ and 256 random bits, shown once, and lasts 90 days by default and a year at most. It carries a list of permissions and, optionally, one environment; a key limited to an environment cannot reach routes that span them all. Its creator cannot give it a permission they do not hold. Most importantly, a key acts within what its owner may do now: each request takes the key's permissions and keeps only those the owner still holds, and a key whose owner has left stops working (resolve).

    Some things a key can never do: decide an approval, change the tenant's encryption keys, or reach the operator console. Approvals and keys need a person, and step-up.

    Spec and code differ

    Keys are "scoped (workspace, environment, permissions)" in spec 13.2, and role assignments "can be scoped to a workspace or a folder" in 13.3. Neither workspaces nor folders exist: a key is scoped to its tenant, an environment and permissions, and a role to the whole tenant. There is no endpoint to rotate a key; rotating is making a new one and revoking the old.

    Roles and permissions#

    There are 34 permissions (access.All), and eight built-in roles bundle them:

    RoleCanCannot
    ownerEverything
    adminBuild, publish, run, manage members, roles, secrets, connections, connectors, policies, Git and alertsDecide approvals, reveal or erase personal data, billing, encryption keys, partner management
    builderRead and edit workflows and tables, start runsPublish
    operatorRun, cancel and resolve runs, invoices, schoolsEdit workflows

    Admin is deliberately not a superset. Approving payments and seeing personal data stay with the owner and with people the owner chooses, so an admin who manages members cannot make themselves an approver. The rule that holds this together is canGrant: nobody can grant a role carrying a permission they do not hold, and granting a role that an approval policy names needs approval.decide. A tenant can also define custom roles from the same permissions (a plan feature), and use business roles, such as credit_officer, that carry no permissions and only qualify someone for the approvals that name them.

    Every /v1 request passes authenticate, then the route's need(permission), then the handler's transaction, which sets the tenant for row-level security.

    Spec and code differ

    The spec's builder can "publish only to dev" (spec 13.3); the code's builder cannot publish at all. The spec's auditor has "read-only access to everything"; the code's reads workflows, runs, tables, invoices and the audit log, not secrets, connections or members.

    Step-up#

    Some actions need a second proof, given with the request itself:

    • Approvals, when the policy rule asks for it: a WhatsApp PIN, an authenticator code (TOTP) or a passkey, in rising strength, and any stronger method satisfies a weaker requirement (StepUpSatisfies).
    • Changing encryption keys: always.
    • Changing your own sign-in factors (adding a passkey, setting up TOTP, changing your password): your passkey or code if you have one, otherwise your password.

    A passkey challenge is bound to one operation and one target, such as approving step pay of one run. The last 16 bytes of the challenge are the hash of that scope, and the server checks it again when the challenge is used, so a passkey signature collected for one approval cannot approve another (issueChallenge, decision 0026). An authenticator code is not bound this way: it is used once and locks after 5 wrong tries in 15 minutes.

    When there is a public URL, anyone holding an administrative permission (members, roles, secrets, policies, Git, connectors, personal data) is held to passkeys: signed in with a password, they can only enrol a passkey, and once they have one, password sign-in is refused.

    Risk: worth fixing
    • A person with no factor of their own changes factors without proof. Someone created by SSO has no password, passkey or code. For them proveFactor asks for nothing, so whoever holds their session can enrol a passkey. That passkey belongs to the person, outlives the session, signs in to their tenants that do not enforce SSO, and satisfies passkey step-up on approvals. Asking for a recent SSO sign-in (say, within 10 minutes) would close it.
    • The passkey rule for administrators skips SSO sign-ins. It applies to password sessions only (resolve), so an owner or admin who signs in by SSO is never asked to enrol one. Decision 0026 says owners are held to passkeys by default.
    • The spec says passkeys are the default "for admins and approvers". Approvers are not on the list; their approvals need a passkey only when the policy says so.

    Tenants and partners#

    Every query a request makes runs inside db.InTenantTx, which sets app.tenant_scope for the transaction, and row-level security then shows only that tenant's rows. The Data model page covers the policies and the functions that cross tenants.

    A partner (a bank, a payroll company) has sub-tenants for its own customers, one level deep. A membership never reaches a sub-tenant. A partner reaches one only with a full-tenant API key on the partner API, and each call enters exactly one sub-tenant through taskiem_partner_enter, which checks the parent, records the access in both tenants' audit logs, and narrows the scope to that sub-tenant:

    Risk

    A partner with partner.manage can invite its own staff into a sub-tenant as admin at any time, and can define custom roles there with any permission except the partner ones, including revealing personal data and managing secrets. The person must accept the invitation, both audit logs record it, and the sub-tenant's people can see who is a member. The threat model accepts this, as a partner usually operates the product for its customers, but a sub-tenant has no way to refuse it.

    Embedding#

    A partner can put Taskiem inside its own product (decision 0015). It registers an embed app with the origins allowed to frame it, and its server mints a short-lived end-user token, 15 minutes by default and an hour at most (also a database constraint), for one sub-tenant. Such a token can only ever hold a few permissions, whatever the partner asks for:

    Embedded requests use their own routes, /v1/embed/{app}, where embedAuth checks that the token belongs to that app and that the request comes from an allowed origin. White label, a custom domain proved through DNS and the partner's own branding, is a capability Taskiem grants per partner.

    Taskiem's own staff#

    Operators are made only from the command line, never through the API (decision 0027). Their sessions last an hour, at most eight, with a strict-same-site cookie scoped to /v1/ops, and every write needs a passkey bound to that write. Their actions go to a platform audit log of their own, anchored outside the database like a tenant's. What they can do is narrow: review catalogue submissions and storefronts, post status incidents, manage field agents, and read a list of tenants. They cannot act inside a tenant's workflows or see its secrets.

    Risk

    The threat model says every operator "sign-in, write and tenant view" is recorded. Opening one tenant is (tenant.view). The tenant list, a storefront's stored photos, submissions and reports are read without a record. Some writes (status incidents, and adding or disabling an operator from the CLI) are recorded in a second transaction after the change, so a failure there leaves a change with no record.

    Part D · Trust and compliance

    Security architecture

    How secrets and personal data are encrypted and erased, how a tenant brings its own key, how outbound traffic is fenced, the HTTP hardening, and the threat model the team reviews against.

    Checked against 6df1072 · 2026-10-28No changes to its code since

    What is protected, and against whom#

    A tenant trusts Taskiem with three kinds of thing: credentials (API keys, OAuth tokens, database passwords), the personal data that passes through its runs (BVNs, account numbers, names), and the ability to call out to the world. The design keeps each of those safe from the other tenants, from someone who gets a copy of the database, and from the tenant's own workflows reaching places they should not. The threat model lists 19 boundaries, B1 to B19, and says what holds at each; a change that adds an entry point, a role, a secret store or a way to run tenant code updates it in the same pull request.

    Keys#

    Nothing secret is stored in the clear. Every value is encrypted under its own key, and keys are wrapped by keys above them:

    KeyEncryptsKept
    Data key, one per valueThe value: AES-256-GCM, bound to its tenant, environment, name and id, so a ciphertext copied to another row will not openBeside the value, wrapped
    Tenant key (KEK), versionedEach data key, bound to the tenanttenant_keys, wrapped by the root key
    Root keyEach tenant keyOpenBao's transit engine, or for a small install a key in the process's environment
    The tenant's own key (BYOK)The tenant key, a second timeThe tenant's KMS: OpenBao or Vault, AWS KMS, Google Cloud KMS or Azure Key Vault

    Every read of a secret is recorded with why it was read, a secret_reads row in the same transaction as the decryption: which run, step and attempt, or which person (WithUse). Each hour's reads are hashed into the tenant's audit log, so deleting a read afterwards shows.

    Rotating makes a new tenant-key version, and a background job re-wraps the data keys under it, 500 at a time; values themselves are never re-encrypted. Old versions are destroyed a day after nothing uses them.

    Spec and code differ

    The spec puts the root key "in an HSM or KMS" (spec 14.1). The choices are OpenBao, or a key in the process's environment, which is the default (TASKIEM_KMS=local). A cloud KMS is supported only for a tenant's own key. A production install should set TASKIEM_KMS=openbao.

    Bringing your own key#

    A tenant can add its own key, so that revoking it in its own KMS makes its data unreadable to Taskiem (EnableBYOK). Taskiem first proves it can wrap and unwrap with the key, then wraps a new tenant-key version twice, by the root key and then by the tenant's, so the tenant's KMS only ever sees ciphertext. Every minute a job asks the tenant's KMS to unwrap a test value. After two failures in a row the key is marked unavailable: the API answers 503 key_unavailable, and steps that need a secret are parked before anything is sent, then resume by themselves when the key comes back.

    Risk

    Revocation is not instant. Unwrapped tenant keys are cached in memory for 5 minutes by default (up to an hour) in every process, so a revoked key keeps working that long. Versions made before BYOK was turned on stay readable without the tenant's key until the re-wrap finishes, and a database backup taken before then stays readable without it until the backup expires. The BYOK guide says so.

    Personal data#

    A field marked as personal, in the workflow's inputs or in a connector's manifest, is sealed before an event is written. Each person, a subject, gets their own key, and the subject's id is a keyed hash of the value, so the same BVN always has the same subject and the same key (SealTx). sealPayload seals declared fields, then any copy of a known value it finds elsewhere in the payload, then values it recognises by shape: emails, Nigerian phone numbers, BVNs and NINs, card numbers, and account numbers beside a bank code. If a connector's personal fields cannot be known, the event is not written at all.

    Erasing a person destroys their key (Erase). Every sealed copy, in events, archives and backups, then reads as [erased]. A trigger in the database makes this one-way, and the application cannot delete the key rows.

    Risk: worth fixing
    • A value built from personal data is stored in the clear. A step whose output is 'ref-' + bvn or 'Dear ' + name writes ref-22298765432 and Dear Adaeze Okafor to the run's history unsealed, while a plain copy of the BVN is sealed. Checked by running it and reading the stored event. Sealing finds copies only by exact match, so erasure cannot reach these. Sealing any string that contains a known value would close most of it.
    • An erased person cannot be processed again. Their subject's key is gone, so a new run with the same BVN fails with "subject erased". That may be intended, but nothing documents it, and a customer who leaves and later returns would need a way back.
    • Erasure needs no second proof. It is irreversible, yet needs only pii.erase, while changing an encryption key needs a passkey or code.
    • The spec says erasure "is never applied under a running workflow" (spec 9.4). Nothing checks for runs in flight; a waiting run sees [erased] when it resumes.
    • Log lines are masked for emails, phones, BVNs, NINs and cards, but not names or account numbers, and not secret values. Keeping secrets out of logs depends on code not logging them.

    Outbound traffic#

    Every call out of Taskiem made for a tenant goes through egress.Guard: connector calls, HTTP steps, code steps' fetch, alerts, partner webhooks, and calls to a tenant's KMS. A connector may reach only its manifest's hosts, and an HTTP step only its environment's allow-list. The guard resolves the name once, refuses if any address is private, loopback, link-local, a cloud metadata address, or one of the IPv6 forms that hide an IPv4 address, and then dials the address it checked, not the name, so a second DNS answer cannot redirect it. Redirects are followed at most five times, each checked the same way, and proxies from the environment are ignored.

    Where a network requires an explicit proxy, Taskiem connects through it by IP address with CONNECT, never by name, so the proxy cannot resolve the name differently (decision 0028). Each connection is logged with the tenant, purpose, host, address and port.

    Spec and code differ

    The spec's egress "logs every request" (spec 14.2). It logs every connection, so several requests over one kept-alive connection log once. Some platform calls do not go through the guard, by design: the OpenBao client, billing, Git, and a self-hosted model. A few IPv6 forms are not on the list (::ffff:0:0/96 and two new documentation ranges); reaching anything through them needs a translation path a normal Linux host does not have.

    The HTTP surface#

    httpsec.Set gives every API and edge response nosniff, no-referrer, X-Frame-Options: DENY and a content security policy that allows nothing but the app's own origin and refuses framing. Embedded frames get a policy naming the partner's allowed origins, and public pages a stricter one with no inline script or style. HSTS is a year, sent when the public URL is HTTPS.

    Rate limits are token buckets in each API process: sign-in, password reset and re-authentication at a burst of 10 and then one every 6 seconds, per IP and per email; passkey challenges and SSO starts at a burst of 30; and ingest per tenant by plan (Triggers and channels).

    Spec and code differ

    The spec has "Rate limits per IP, user, API key, and tenant" (spec 14.3). Limits exist on the endpoints above, but there is no general limit per API key or per tenant on the rest of /v1, and every limit is per process, so several API replicas allow several times the rate. The app's policy also allows inline styles.

    Secrets in outputs#

    A step's output, logs and error are scrubbed of every secret the step could read before they are written (scrubSecrets). The Sandbox page covers what it catches and what it does not.

    Self-review#

    Security is reviewed in rounds, recorded in self-review.md. Four reviewers each take one area: sign-in and sessions; tenancy and authorisation; untrusted input, egress and sandboxes; secrets, personal data and audit. Findings are numbered by round (S1 to S35, then K1 to K8 for BYOK, then R1 to R10), each with a severity, a status and, when fixed, the regression test that proves it. What a round leaves open is carried to the next. Two are open now: R7, undeploying without a second person, and R9. The repository has no secret scanner such as gitleaks; the linter's security rules and signed, SBOM-listed images in CI are what exist.

    How the atlas is maintained

    Where the atlas's pages live, how the build reads the code, how to tell which pages the code has moved under, and how to update and publish it.

    What it is made of#

    The atlas lives in docs/atlas next to the code it describes, so a change to one can come with a change to the other in the same pull request.

    PathWhat it is
    pages/*.htmlOne file per page: a JSON header, then the page's HTML. The file name only sets the reading order on disk. The header's part and order set the order in the atlas.
    partials/*.htmlDiagrams used on more than one page or too long to keep inline. {{uid}} in a partial is replaced each time it is included, so marker ids never clash.
    src/The shell, the stylesheet and the page script that every page shares.
    atlas.jsonThe title, the repository URL that code links point to, and the parts.
    atlas.mjsThe build. Node 22 and git, no packages.
    site/index.htmlThe built atlas: one self-contained file. Open it from disk or serve it anywhere. It is committed, so reading it never needs a build.

    A page's header#

    Every page starts with a comment holding JSON:

    • verified is the commit the page was last checked against, line by line. Set it only after reading the code at that commit.
    • sources are the files and directories the page describes. A commit that touches any of them after verified marks the page as moved.
    • status: "planned" with a scope list renders a placeholder that says what the page will cover.

    Elements that read the code#

    The build replaces these elements before writing the page. Anything that names code is resolved against the working tree, and links are pinned to the commit that was built.

    ElementBecomes
    <x-ref path="…" symbol="…">text</x-ref>A link to the first line in the file containing symbol. Without symbol, a link to the file. A path ending in / links to the directory.
    <x-code path="…" start="…" [end="…" | lines="n"] [doc] [max="n"] [caption="…"]/>An excerpt with highlighting and line numbers. It starts at the first line containing start and runs to the line containing end, or for n lines, or by default to the brace that closes the block. doc includes the comment above it.
    <x-packages names="a,b"/>, <x-packages rest/>Package cards with size and doc comment, read from the code. rest lists every engine package that no other x-packages mentions, and the build reports it.
    <x-stat name="…"/>A number counted from the repository: go-lines, engine-packages, connectors, migrations, api-operations and others in stats.
    <x-page id="page[--section]">text</x-page>A link to another page or section, with the page's title when there is no text.
    <x-include name="file.html"/>A partial.

    Attribute values are matched literally. Write &quot; for a quote inside one, as in start="if is(&quot;worker&quot;) {".

    The page script also understands a few classes: callout drift for spec and code that disagree, callout risk, callout note, evt for an event name, stepper with stage items whose data-lit lights the diagram groups marked data-stage, and data-go="page" on any diagram group to make it open that page.

    Keeping it current#

    Run these from the repository root:

    CommandWhat it does
    make atlasBuilds docs/atlas/site/index.html and docs/atlas/dist/artifact.html, and prints every reference that no longer resolves.
    make atlas-staleLists each written page and how many commits have touched its sources since it was checked, with the files.
    node docs/atlas/atlas.mjs checkBuilds in memory and fails if any reference is broken. Use it before committing.

    To bring a page up to date: run make atlas-stale, read the diff of the listed files since the page's verified commit, change what the page says, set verified to the commit you checked, then rebuild. Code excerpts and line links update themselves. Prose, tables and diagrams are what need a person.

    What the checks cannot see

    An excerpt anchored on a symbol keeps working when the code around it changes. A broken anchor is reported, but a change in meaning is not. And a later migration that redefines a SQL function is not noticed while the old migration still exists. That is why each page also lists its sources and turns amber when they change.

    Publishing#

    site/index.html is the atlas. Commit it with the change that updated a page. dist/artifact.html is the same atlas without the document wrapper, for hosts that add their own, such as a claude.ai artifact. It is not committed.
